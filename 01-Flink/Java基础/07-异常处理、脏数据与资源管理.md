# 07 异常处理、脏数据与资源管理

## 1. 异常是什么

异常表示程序运行期间出现非正常情况。

```java
int amount = Integer.parseInt("abc");
```

这会抛出 `NumberFormatException`。

## 2. 异常体系

```text
Throwable
├── Error
└── Exception
    ├── RuntimeException
    └── 其他受检异常
```

### Error

通常表示 JVM 或系统层面的严重问题，如 `OutOfMemoryError`。业务代码一般不尝试恢复。

### RuntimeException

运行时异常，也称非受检异常，例如：

- `NullPointerException`
- `IllegalArgumentException`
- `NumberFormatException`
- `IndexOutOfBoundsException`

编译器不强制捕获。

### 受检异常

例如 `IOException`。编译器要求捕获或继续声明抛出。

## 3. `throw` 和 `throws`

`throw` 真正抛出一个异常：

```java
if (amount < 0) {
    throw new IllegalArgumentException(
        "amount must not be negative");
}
```

`throws` 声明方法可能抛出异常：

```java
public Order parse(String line) throws Exception {
    ...
}
```

## 4. try-catch-finally

```java
try {
    return parse(line);
} catch (NumberFormatException e) {
    System.err.println("invalid line: " + line);
    return null;
} finally {
    // 无论成功或失败，通常都会执行
}
```

不要随意吞掉异常：

```java
try {
    ...
} catch (Exception e) {
    // 什么都不做：危险
}
```

至少要记录上下文，或者明确地将数据发送到异常数据处理流程。

## 5. Flink 函数为什么允许抛异常

```java
public interface MapFunction<T, O> {
    O map(T value) throws Exception;
}
```

如果算子抛出未处理异常，Task 通常会失败，Flink 根据重启策略尝试恢复。恢复点通常来自最近成功的 Checkpoint。

这不是坏事。对于无法继续保证正确性的错误，让任务失败并恢复可能比静默丢数据更合适。

## 6. 脏数据处理策略

假设输入：

```text
o-1,u-1,20.0
bad-line
o-2,u-2,abc
```

可以选择：

### 策略一：遇到错误直接失败

适合严格数据链路。优点是不会悄悄丢数据；缺点是单条坏数据可能持续导致任务重启。

### 策略二：过滤并记录

适合允许少量异常数据的场景。需要监控异常数量。

### 策略三：侧输出流

将正常数据和脏数据分开处理。后续学习 `ProcessFunction` 和 Side Output 时重点掌握。

伪代码：

```java
try {
    out.collect(parse(line));
} catch (Exception e) {
    ctx.output(dirtyTag, line);
}
```

## 7. null 的处理

Java 中常见错误：

```java
order.getUserId().length();
```

如果 `userId` 是 null，会抛出 `NullPointerException`。

可使用前置校验：

```java
Objects.requireNonNull(userId, "userId");
```

或明确过滤：

```java
orders.filter(order -> order.getUserId() != null);
```

## 8. try-with-resources

实现 `AutoCloseable` 的资源可自动关闭：

```java
try (BufferedReader reader =
         Files.newBufferedReader(path)) {
    return reader.readLine();
}
```

即使发生异常，资源也会被关闭。

## 9. Flink 中的资源生命周期

对于数据库客户端、HTTP 客户端等外部资源，通常使用 RichFunction：

```java
public class EnrichOrder
        extends RichMapFunction<Order, Order> {

    private transient SomeClient client;

    @Override
    public void open(Configuration parameters) {
        client = new SomeClient();
    }

    @Override
    public Order map(Order order) {
        return enrich(order, client);
    }

    @Override
    public void close() {
        if (client != null) {
            client.close();
        }
    }
}
```

连接对象通常设为 `transient`，在 TaskManager 上通过 `open()` 创建。

## 11. 阅读时常见问题

### 问题 1：遇到脏数据时，直接捕获异常并返回 null 可以吗？

通常不推荐。返回 null 容易把错误推迟到下游，最后变成更难定位的 `NullPointerException`。

更清晰的选择是：

1. 让任务失败，保证严格正确性。
2. 明确过滤，并记录指标和日志。
3. 使用侧输出流单独保存脏数据。

### 问题 2：是不是所有异常都应该捕获？

不是。只有当你知道如何处理时才捕获。无法恢复且会破坏正确性的异常，继续抛出往往更合适，让 Flink 按重启策略恢复。

### 问题 3：一条固定的坏数据让任务不断重启，Checkpoint 能解决吗？

不一定。Checkpoint 能帮助任务从已保存进度恢复，但如果恢复后再次读到同一条坏数据，任务仍会失败。

这时需要明确的数据质量策略，例如将坏数据发送到侧输出流，或在 Source 端进行治理。

### 问题 4：为什么不能在 `map()` 中每条数据都创建一次数据库连接？

连接建立通常很慢。如果每条数据都新建连接：

1. 延迟会明显升高。
2. 数据库连接数可能迅速耗尽。
3. 作业吞吐量会下降。

通常在每个算子实例的 `open()` 中创建一次，在 `close()` 中释放。

### 问题 5：把客户端放在 `open()` 中初始化后，访问外部系统就一定合理吗？

仍然不一定。同步外部请求会阻塞算子线程。如果请求耗时较长，应进一步学习 Flink Async I/O、超时、重试和限流设计。

### 问题 6：日志中应该记录什么，才方便排查脏数据？

至少记录：

- 原始输入。
- 失败原因。
- 关键业务标识。
- 异常数量指标。

但要注意敏感信息和日志量，避免将密码、令牌或大量原始数据直接写入日志。
