# 02 接口、抽象类、继承与多态

## 1. Flink API 为什么大量使用接口

Flink 框架负责数据流转、并行调度和容错；开发者只负责填写业务逻辑。接口就是双方约定的合同。

例如 `MapFunction<IN, OUT>`：

```java
public interface MapFunction<T, O> extends Function, Serializable {
    O map(T value) throws Exception;
}
```

你只需要告诉 Flink：每收到一条输入数据，如何产生一条输出数据。

```java
public class ParseOrder
        implements MapFunction<String, Order> {

    @Override
    public Order map(String line) {
        String[] fields = line.split(",");
        return new Order(fields[0], fields[1],
            Double.parseDouble(fields[2]));
    }
}
```

## 2. 接口

接口描述能力，不关心具体实现。

```java
public interface Formatter {
    String format(Order order);
}
```

一个类通过 `implements` 实现接口：

```java
public class CsvFormatter implements Formatter {
    @Override
    public String format(Order order) {
        return order.getOrderId() + "," + order.getAmount();
    }
}
```

## 3. 抽象类

接口描述“会什么”，抽象类描述“是什么，并且已经自带一部分能力”。

抽象类不能直接实例化，可以同时包含抽象方法和已有实现。

```java
public abstract class AbstractParser<T> {
    public abstract T parse(String line);

    protected String[] split(String line) {
        return line.split(",");
    }
}
```

接口更像能力约定；抽象类更像带有部分实现的父类模板。

## 4. 继承

继承表达“是一种”关系。

```java
public class VipOrder extends Order {
    private double discount;
}
```

不要为了复用几行代码就滥用继承。业务建模中，组合通常更灵活：

```java
public class Order {
    private DiscountPolicy discountPolicy;
}
```

## 5. 方法重写和方法重载

重写 `Override`：子类重新实现父类或接口中的方法。

```java
@Override
public String format(Order order) {
    return order.getOrderId();
}
```

重载 `Overload`：同一个类中，方法名相同但参数列表不同。

```java
public Order parse(String line) { ... }
public Order parse(String line, String delimiter) { ... }
```

## 6. 多态

多态可以简单理解为：

> 使用同一种父类型或接口类型接收不同对象，调用相同方法时，执行各自不同的实现。

### 6.1 一个直观例子

先定义统一接口：

```java
public interface Formatter {
    String format(Order order);
}
```

提供 CSV 实现：

```java
public class CsvFormatter implements Formatter {
    @Override
    public String format(Order order) {
        return order.getUserId()
            + "," + order.getAmount();
    }
}
```

再提供 JSON 实现：

```java
public class JsonFormatter implements Formatter {
    @Override
    public String format(Order order) {
        return "{\"userId\":\""
            + order.getUserId() + "\"}";
    }
}
```

两个类都实现了 `Formatter`，因此可以使用接口类型接收它们：

```java
Formatter csvFormatter = new CsvFormatter();
Formatter jsonFormatter = new JsonFormatter();
```

调用方式完全一致：

```java
csvFormatter.format(order);
jsonFormatter.format(order);
```

但实际执行的逻辑不同：

- `csvFormatter` 调用 `CsvFormatter` 的 `format()`。
- `jsonFormatter` 调用 `JsonFormatter` 的 `format()`。

### 6.2 父类型引用与实际对象

观察下面这行代码：

```java
Formatter formatter = new CsvFormatter();
```

可以拆成两部分理解：

| 部分 | 含义 |
| --- | --- |
| 左侧 `Formatter formatter` | 引用变量的声明类型 |
| 右侧 `new CsvFormatter()` | 实际创建的对象类型 |

用父类型或接口类型接收子类对象，称为向上转型：

```java
Formatter formatter = new CsvFormatter();
```

这是安全的。因为 `CsvFormatter` 实现了 `Formatter` 约定的全部能力。

### 6.3 左边决定能调用什么，右边决定实际执行什么

```java
Formatter formatter = new JsonFormatter();
formatter.format(order);
```

编译时，Java 查看左侧声明类型 `Formatter`。因此，变量只能调用 `Formatter` 接口中声明的方法。

运行时，Java 查看右侧实际对象 `JsonFormatter`。因此，最终执行 `JsonFormatter` 中重写的 `format()`。

这称为动态绑定。

可以记住：

> 左边决定“可以调用什么”，右边决定“实际执行什么”。

### 6.4 为什么需要多态

假设有一个打印订单的方法：

```java
public void printOrder(
        Formatter formatter,
        Order order) {

    System.out.println(formatter.format(order));
}
```

这个方法不依赖任何具体实现。调用时可以自由传入不同格式化器：

```java
printOrder(new CsvFormatter(), order);
printOrder(new JsonFormatter(), order);
```

以后增加 XML 格式时：

```java
public class XmlFormatter implements Formatter {
    @Override
    public String format(Order order) {
        return "<order>...</order>";
    }
}
```

原有的 `printOrder()` 不需要修改：

```java
printOrder(new XmlFormatter(), order);
```

这带来两个好处：

1. 调用方只依赖稳定的接口，不依赖具体实现。
2. 新增实现时，已有调用逻辑通常不需要改动。

### 6.5 多态与方法重写的关系

多态通常配合方法重写：

```java
Formatter formatter = new JsonFormatter();
formatter.format(order);
```

`JsonFormatter` 重写了接口中的 `format()`。运行时根据实际对象决定调用哪个实现。

但要注意：多态不等于方法重载。

方法重载是同一个类中，方法名相同但参数列表不同：

```java
parse(String line);
parse(String line, String delimiter);
```

重载通常在编译时根据参数列表决定调用哪个方法。

### 6.6 子类独有方法不能直接通过父类型调用

假设 `JsonFormatter` 还有一个独有方法：

```java
public void prettyPrint() {
    ...
}
```

下面的代码无法编译：

```java
Formatter formatter = new JsonFormatter();
// formatter.prettyPrint();
```

原因是左侧声明类型 `Formatter` 没有约定 `prettyPrint()`。

如果确实需要调用，可以进行类型判断和向下转型：

```java
if (formatter instanceof JsonFormatter) {
    JsonFormatter jsonFormatter =
        (JsonFormatter) formatter;
    jsonFormatter.prettyPrint();
}
```

但如果业务代码频繁向下转型，通常说明接口设计需要重新考虑。

### 6.7 Flink 中的多态

Flink 中也是如此：

```java
MapFunction<String, Order> parser = new ParseOrder();
DataStream<Order> orders = lines.map(parser);
```

`lines.map(...)` 接收的是统一接口：

```java
MapFunction<IN, OUT>
```

你可以传入不同实现：

```java
lines.map(new ParseOrder());
orders.map(new ExtractUserId());
```

也可以使用 Lambda：

```java
lines.map(line -> line.toUpperCase());
```

Flink 不需要知道每种业务逻辑的内部细节。它只要求传入对象符合 `MapFunction` 约定，并在处理数据时调用对应实现。

## 7. Flink 中的普通函数和 RichFunction

普通 `MapFunction` 适合纯转换：

```java
public class ToUpperCase
        implements MapFunction<String, String> {
    @Override
    public String map(String value) {
        return value.toUpperCase();
    }
}
```

需要生命周期、运行时上下文或状态时，使用 `RichMapFunction`：

```java
public class EnrichOrder
        extends RichMapFunction<Order, Order> {

    @Override
    public void open(Configuration parameters) {
        // 每个并行子任务初始化一次资源
    }

    @Override
    public Order map(Order value) {
        return value;
    }

    @Override
    public void close() {
        // 释放资源
    }
}
```

常见生命周期：

- `open()`：初始化连接、配置或状态。
- `map()`：对每条数据执行。
- `close()`：释放资源。

不要在 `map()` 中为每条数据重复创建数据库连接。

## 8. 高频 Flink 函数接口

| 接口 | 输入输出关系 | 用途 |
| --- | --- | --- |
| `MapFunction<IN, OUT>` | 一条输入变一条输出 | 字段转换、解析 |
| `FlatMapFunction<IN, OUT>` | 一条输入变零到多条输出 | 分词、拆分、过滤兼转换 |
| `FilterFunction<T>` | 一条输入决定保留或丢弃 | 条件筛选 |
| `KeySelector<IN, KEY>` | 从数据提取 key | `keyBy()` 分组 |
| `ReduceFunction<T>` | 两条同类型数据合并为一条 | 滚动聚合 |

## 10. 阅读时常见问题

### 问题 1：为什么框架喜欢让开发者实现接口，而不是直接修改框架代码？

框架负责通用流程，开发者只填入变化的部分。Flink 已经处理了调度、网络传输、容错和并行执行，你只需要实现：

```java
OUT map(IN value)
```

这样业务逻辑与框架机制分离。Flink 可以在不理解业务细节的情况下调用你的函数。

### 问题 2：`implements MapFunction<String, Order>` 中两个泛型分别表示什么？

第一个类型是输入，第二个类型是输出：

```java
MapFunction<String, Order>
```

表示输入一条字符串，输出一个订单对象。对应方法：

```java
Order map(String value)
```

如果写成 `MapFunction<Order, String>`，含义就变成输入订单，输出字符串。

### 问题 3：什么时候用 Lambda，什么时候实现接口类？

逻辑非常短时，Lambda 更清楚：

```java
orders.filter(order -> order.getAmount() >= 100);
```

逻辑较长、需要复用、需要测试、需要状态或生命周期方法时，使用显式类更合适：

```java
public static class EnrichOrder
        extends RichMapFunction<Order, Order> {
    ...
}
```

### 问题 4：`RichMapFunction` 比 `MapFunction` 更强，是不是应该全部使用 RichFunction？

不需要。简单的纯转换使用 `MapFunction` 更轻量，也更容易阅读。只有需要运行时上下文、生命周期、指标、广播变量或状态时，才使用 RichFunction。

### 问题 5：`open()` 是整个作业只调用一次吗？

不是。更准确地说，它通常在每个并行算子实例初始化时调用一次。

如果算子并行度是 4，通常会有 4 个算子实例，各自执行自己的 `open()`。因此，不要假设多个并行实例会共享同一个连接对象。

### 问题 6：多态是不是“父类对象变成了子类对象”？

不是。实际创建的对象从一开始就是子类对象：

```java
Formatter formatter = new JsonFormatter();
```

这里创建的是 `JsonFormatter`。只是使用 `Formatter` 类型的引用指向它。对象本身没有发生变化。

### 问题 7：多态是不是只能通过继承实现？

不是。常见方式有两种：

1. 子类继承父类。
2. 类实现统一接口。

Flink API 中大量使用接口多态。例如不同业务函数都可以实现：

```java
MapFunction<IN, OUT>
```

框架只依赖接口，不依赖具体业务类。
