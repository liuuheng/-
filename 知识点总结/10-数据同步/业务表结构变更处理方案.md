# 数据同步中的业务表结构变更处理

> 适用范围：业务数据库向 ODS、数据仓库或数据湖同步数据时，上游业务表发生建表、加列、改类型、改名、删列、改主键等结构变化。

## 1. 核心结论

业务表结构变更的处理方式，主要取决于同步工具是否具备“动态 Schema”能力，以及 Sink Connector 是否能修改目标端表结构。

| 同步方式 | Schema 特征 | 目标表结构处理 | 历史数据处理 |
| --- | --- | --- | --- |
| Flink SQL + CDC | 静态 Schema，提交 Job 时确定 | 修改 Flink SQL DDL 和目标表后重新发布 Job | 新增字段通常单独回补 |
| Flink CDC Pipeline 直写支持 Schema Evolution 的 Sink | 动态 Schema | Pipeline 捕获 DDL，并通过 Sink 的 `MetadataApplier` 自动建表或执行 DDL | 默认不回补历史数据 |
| Flink CDC Pipeline → Kafka → ODS | Kafka 不执行目标表 DDL | 下游 ODS Loader/DDL 服务消费 Schema 信息并修改 ODS | 由独立回补任务处理 |
| DataX 全量同步 | 配置中的字段映射通常固定 | 调度前检查并修改目标表、重新生成字段映射 | 下一次全量可自然回补 |
| DataX 增量同步 | 配置中的字段映射通常固定 | 调度前检查并修改目标表、重新生成字段映射 | 必须单独回补历史数据 |
| Flink CDC Pipeline 直写不支持 Schema Evolution 的 Sink | Pipeline 能识别 Schema，但 Sink 无法自动应用 | 自研 `MetadataApplier`，或使用外部 DDL 服务 | 单独回补 |

需要特别区分：

1. **Schema Evolution**：保证结构变更之后的数据能够按照新结构继续同步。
2. **历史数据回补**：重新处理结构变更之前已经存在的数据。

Schema Evolution 不等于历史数据回补。比如源表增加 `remark` 字段后，Pipeline 可以自动给 ODS 增加该字段，但历史行的 `remark` 通常仍然是 `NULL`。

---

## 2. 所有同步方式都应遵循的通用流程

无论使用哪种工具，可靠的表结构变更处理都应该包含以下阶段：

```text
发现结构变化
  ↓
生成并标准化 Schema Diff
  ↓
判断变更风险和处理策略
  ↓
阻止采用新 Schema 的数据提前写入
  ↓
修改目标端表结构
  ↓
更新同步任务的字段映射或内部 Schema
  ↓
继续同步增量数据
  ↓
按需回补历史数据
  ↓
执行数据校验和变更审计
```

其中最关键的是顺序：

> 必须先让目标端具备新 Schema，再写入采用新 Schema 的数据。

如果只有“DDL 通知”，但没有暂停、缓冲、版本控制或确认机制，就可能发生新字段数据先到、目标表字段尚未创建，从而造成写入失败或字段丢失。

## 3. 场景一：Flink SQL + CDC

### 3.1 特点

Flink SQL 表的字段在 Job 提交时已经确定，例如：

```sql
CREATE TABLE source_user (
    id BIGINT,
    name STRING,
    PRIMARY KEY (id) NOT ENFORCED
) WITH (
    'connector' = 'mysql-cdc'
);
```

运行期间源表新增 `remark` 字段，运行中的 Flink SQL Job 不会自动把该字段加入表定义和数据处理拓扑。

### 3.2 推荐处理步骤

1. 监控或人工发现源表 DDL 变更。
2. 判断旧 Job 面对新 Binlog 事件时的行为：忽略新字段、反序列化失败或继续处理旧字段。
3. 记录当前同步位点，并按作业要求触发 Checkpoint 或 Savepoint。
4. 暂停或停止旧 Job，避免新旧 Schema 数据持续混用。
5. 修改目标 ODS 表结构。
6. 修改 Flink SQL 中 Source、Transform、Sink 的字段定义。
7. 检查状态兼容性：
   - 是否修改了有状态算子的字段类型；
   - 是否修改了主键、聚合键或 Join Key；
   - 是否还能从原 Savepoint 恢复。
8. 重新发布 Job，并从正确位点继续消费。
9. 校验新字段的数据是否正常进入 ODS。
10. 如果历史数据也需要该字段值，启动独立回补任务。

### 3.3 主要风险

- 修改字段后不能假定原 Savepoint 一定兼容。
- 停旧 Job、改表、发新 Job 之间必须保存好 CDC 位点。
- 新字段参与计算、聚合、Join 或主键时，影响的不只是表定义，还包括算子状态。
- 字段变更窗口内的数据可能需要重新消费或补数。

### 3.4 适用场景

- 表结构相对稳定。
- 同步链路包含复杂 SQL 计算。
- 可以接受表结构变更时重新发布 Job。

## 4. 场景二：Flink CDC Pipeline 直写 ODS

### 4.1 特点

Flink CDC Pipeline 将事件分为：

- `DataChangeEvent`：INSERT、UPDATE、DELETE。
- `SchemaChangeEvent`：建表、加列、改类型、重命名、删列、清表、删表等。

当 Sink Connector 实现了 `MetadataApplier` 时，Pipeline 可以把源端结构变化自动应用到目标端。

### 4.2 推荐处理步骤

1. Source 从 Binlog 等日志中捕获 DDL。
2. Source 将 DDL 解析为语义化的 `SchemaChangeEvent`，而不是简单传递一段 SQL 文本。
3. SchemaOperator/SchemaRegistry 协调受影响的数据流。
4. 刷出 Sink 中仍按旧 Schema 缓存的数据。
5. 调用 Sink Connector 的 `MetadataApplier`。
6. `MetadataApplier` 通过 JDBC、Catalog API 或目标系统 SDK 执行建表或 Schema 变更。
7. DDL 成功后更新 Pipeline 内部 Schema 状态。
8. 放行采用新 Schema 的后续 DML。
9. 校验目标端 Schema 和新字段数据。
10. 按业务要求决定是否回补历史数据。

### 4.3 配置策略

生产环境建议使用保守策略：

```yaml
pipeline:
  schema.change.behavior: lenient

sink:
  exclude.schema.changes:
    - drop.column
    - drop.table
    - truncate.table
```

常见策略含义：

| 策略 | 含义 |
| --- | --- |
| `exception` | 捕获到 Schema 变化就失败 |
| `evolve` | 严格应用到 Sink，失败则 Job 失败 |
| `try_evolve` | 尝试应用，失败时尽量转换后续数据 |
| `lenient` | 优先保证不丢数据，以兼容方式处理，通常适合作为默认策略 |
| `ignore` | 不向 Sink 应用 Schema 变化，只处理仍兼容的字段 |

### 4.4 已有官方 Schema 处理能力的常见 Sink

不同版本支持范围不同。Flink CDC 3.6 官方文档中，以下 Sink 明确提供自动建表和 Schema 同步能力：

- Doris
- StarRocks
- OceanBase
- Paimon
- Iceberg
- Hudi
- MaxCompute

不能仅根据“存在 Sink Connector”判断其支持全部 DDL。每个 Connector 支持的事件类型、数据类型映射和目标端版本都需要单独核对。

### 4.5 主要风险

- Source 能捕获 DDL，不代表 Sink 一定支持对应 DDL。
- 数据类型从源端映射到目标端时可能发生精度变化。
- 类型缩窄、改主键、删列、删表等操作通常不宜自动执行。
- 自动加列不会重新计算历史记录。

## 5. 场景三：Flink CDC Pipeline → Kafka → ODS

### 5.1 特点

Kafka 没有关系表，不能替 ODS 执行 `ALTER TABLE`。即使 Kafka 消息中携带了 Schema，目标 ODS 的结构仍需要由 Kafka 后面的消费程序处理。

```text
业务库
  ↓
Flink CDC Pipeline
  ↓
Kafka：数据事件 + Schema 信息
  ↓
ODS Loader / DDL 服务
  ↓
ODS
```

### 5.2 推荐处理步骤

1. CDC 捕获源端 Schema 变更。
2. 将 Schema 信息写入 Kafka 消息、独立 DDL Topic 或 Schema Registry。
3. 为每次 Schema 变化生成单调递增的 `schema_version`。
4. 后续数据携带其所依赖的 `schema_version`。
5. ODS Loader 收到新版本数据时，检查目标表当前 Schema 版本。
6. 如果目标表版本落后，暂停或缓存该表的新版本数据。
7. DDL 服务修改 ODS 表结构。
8. DDL 成功并记录新版本后，继续消费对应数据。
9. DDL 失败时进入重试、告警或死信流程，不能静默跳过字段。
10. 独立执行历史数据回补。

### 5.3 顺序保证

建议做到：

- 同一张表的 DDL 和 DML进入同一有序通道；或者
- DDL 使用独立 Topic，但 DML 必须通过 Schema 版本门禁；
- 只有确认 ODS DDL 成功后，才能写入新版本数据。

仅仅在 Debezium JSON 中携带 Schema 描述，并不能自动完成 ODS Schema Evolution。

### 5.4 适用场景

- 一个 CDC 数据源需要供多个下游消费。
- 需要解耦数据采集和 ODS 写入。
- 希望保留原始 CDC 事件用于重放和审计。

## 6. 场景四：DataX 全量同步

### 6.1 特点

DataX 通常在配置中固定 Reader 和 Writer 字段：

```json
{
  "reader": {
    "column": ["id", "name", "remark"]
  },
  "writer": {
    "column": ["id", "name", "remark"]
  }
}
```

DataX 本身不持续监听并传播业务库 DDL，因此适合在每次批量调度前增加 Schema 检查。

### 6.2 推荐处理步骤

1. 调度开始前读取源表元数据。
2. 读取目标 ODS 表元数据。
3. 把两端数据类型转换成统一的内部类型模型。
4. 计算字段、类型、可空性、主键等 Schema Diff。
5. 通过安全策略判断是否允许自动执行。
6. 对安全变更自动修改目标表。
7. 按字段名称和类型重新生成 DataX Reader/Writer 映射。
8. 运行全量同步或覆盖写入。
9. 校验行数、主键重复、空值、SUM/HASH 等指标。
10. 保存本次 Schema 版本、DDL 和 DataX 配置快照。

### 6.3 历史数据

如果任务是真正的全量覆盖，并且全表重新读取，那么新增字段会在下一次同步中自然回补。

但应确认“全量”具体含义：

- 全表覆盖：历史数据可自然回补。
- 目标端先清表再导入：需评估同步窗口和失败恢复。
- 按分区覆盖：只有本次覆盖的分区会得到新字段值。
- 伪全量或基于条件抽取：未读取的数据仍不会回补。

## 7. 场景五：DataX 增量同步

### 7.1 推荐处理步骤

1. 调度前比较源表和目标表 Schema。
2. 对安全变更先执行目标端 DDL。
3. 动态更新 DataX 字段映射。
4. 从既有增量位点继续同步。
5. 校验新产生或新更新记录的字段值。
6. 为历史记录创建独立回补任务。
7. 回补完成后执行全表或抽样校验。

### 7.2 为什么必须单独回补

增量任务通常只读取：

```sql
WHERE update_time > 上次同步时间
```

因此没有发生更新的历史记录不会再次被读取。新增字段后，即使目标表已经增加该列，历史行仍然没有新字段值。

### 7.3 回补方式

- 全表回补新增字段。
- 按主键范围分批回补。
- 按日期或业务分区回补。
- 只回补业务确实需要的历史范围。

回补任务必须与实时/增量写入协调，避免旧快照覆盖新值。常见做法是按主键 Upsert，并规定“较新的业务版本优先”。

## 8. 场景六：Pipeline Sink 不支持自动 Schema Evolution

### 8.1 常见情况

- Kafka：没有物理目标表。
- Elasticsearch：新增字段可能依赖动态 Mapping，但复杂类型变化、改名、删除通常需要重建索引。
- Fluss：应按具体版本核对运行期 Schema Change 支持范围。
- MySQL、PostgreSQL、Oracle、SQL Server、DB2、TiDB 等：在部分 Flink CDC 版本中不是官方 Pipeline Sink，不能直接假定具有 `MetadataApplier`。
- 企业内部自研数据库或存储系统。

### 8.2 可选方案

#### 方案 A：实现自定义 MetadataApplier

自研 Pipeline Sink 通常包含：

```text
DataSink
├── EventSink：写入 DataChangeEvent
└── MetadataApplier：应用 SchemaChangeEvent
```

`MetadataApplier` 至少需要处理：

- 事件能力声明；
- Flink CDC 类型到目标类型的映射；
- 自动建库、建表；
- 加列、改类型、改名等 DDL；
- 幂等检查；
- 目标端 DDL 状态轮询；
- 超时、重试和异常传播。

#### 方案 B：外部 DDL 服务

Pipeline 将 Schema 事件发送给独立的 Schema 管理服务，由该服务：

1. 做安全策略检查；
2. 生成目标端 DDL；
3. 执行并确认结果；
4. 更新 Schema 版本；
5. 通知同步链路继续写数据。

#### 方案 C：人工变更

高风险或低频场景可以直接阻断 Job，人工修改目标表和同步配置后恢复。

## 9. 场景七：多 Source、多表合并到同一张 ODS 表

### 9.1 额外问题

多张源表写入同一张目标表时，单张源表的 DDL 不能直接等价传递到目标端。

例如：

```text
center_a.order_01 ┐
center_a.order_02 ├→ ods.order
center_b.order_01 ┘
```

如果 `center_a.order_01` 删除 `remark` 字段，但其他表还在使用该字段，就不能从 `ods.order` 中自动删除它。

### 9.2 推荐处理步骤

1. 每张源表独立维护 Source Schema 版本。
2. 根据 Route 找到它对应的目标表。
3. 以目标表为单位计算所有源表的合并 Schema。
4. 新增字段通常采用字段并集。
5. 同名字段类型不同，只允许安全的公共类型提升。
6. 主键、分区键必须满足预先定义的兼容规则。
7. 使用目标表级别的锁串行执行 Schema 变化。
8. 更新目标表后，重新生成每张源表到目标表的字段映射。
9. 无法合并的冲突进入人工审批，不能任意选择某一个源表 Schema。

### 9.3 建议补充的元数据字段

多中心汇聚时建议为 ODS 增加：

- `source_id`
- `center_id`
- `source_database`
- `source_table`
- `schema_version`
- `op_ts`
- `ingest_time`

这样可以避免不同中心主键碰撞，并支持问题追踪和历史回放。

## 10. Schema 变更风险分级

| 变更类型 | 建议级别 | 推荐动作 | 历史数据影响 |
| --- | --- | --- | --- |
| 新建表 | 低到中 | 满足命名、主键和类型规范时自动建表 | 通常需要执行初始全量 |
| 新增可空字段 | 低 | 自动增加目标字段 | 历史值为 `NULL`，按需回补 |
| 新增带默认值字段 | 中 | 核对目标端默认值语义后自动或审批 | 默认值不一定代表真实历史值 |
| `INT → BIGINT` 等安全扩宽 | 中 | 验证 Sink 支持后自动执行 | 通常无需回补，但要校验精度 |
| `VARCHAR(100) → VARCHAR(500)` | 中 | 可自动执行 | 通常无需回补 |
| 类型缩窄 | 高 | 阻断并人工审批 | 可能截断或溢出 |
| 字符串与数值/时间互转 | 高 | 阻断，先做数据质量检查 | 可能存在无法转换的历史值 |
| 字段重命名 | 高 | 人工确认，必要时采用新增字段、双写、回补、下线旧字段 | 需要迁移历史值 |
| 删除字段 | 高 | 默认禁止自动执行 | 可能永久丢失历史数据 |
| `TRUNCATE TABLE` | 极高 | 默认禁止传播 | 目标数据会被清空 |
| `DROP TABLE` | 极高 | 默认禁止传播 | 目标表和历史数据会被删除 |
| 修改主键 | 极高 | 新表迁移或重新全量同步 | 影响 Upsert、去重和状态兼容性 |
| 修改分区键 | 极高 | 通常新表重建并切换 | 需要重写历史数据 |

## 11. 自动化 Schema 管理方案

对于 DataX、Kafka 中转和不支持 MetadataApplier 的 Sink，可以建设统一的 Schema 管理服务。

### 11.1 核心组件

```text
Metadata Collector
  ↓
Type Normalizer
  ↓
Schema Diff Engine
  ↓
Policy Engine
  ↓
DDL Generator / Executor
  ↓
Config Generator
  ↓
Data Sync Orchestrator
  ↓
Validation & Audit
```

### 11.2 状态机

每次变更建议记录以下状态：

```text
DETECTED
  → REVIEWING
  → APPROVED / REJECTED
  → APPLYING
  → APPLIED
  → SYNCING
  → VALIDATING
  → COMPLETED / FAILED
```

### 11.3 自动化安全要求

- DDL 必须幂等。
- 同一张目标表同时只能执行一个 Schema 变更。
- 自动化只执行明确白名单中的安全变更。
- DDL 成功必须以目标端实际 Schema 为准，不能只依赖 SQL 返回成功。
- 记录源 Schema、目标 Schema、Diff、生成的 DDL、操作者和执行结果。
- 失败后禁止数据任务带着错误 Schema 继续运行。
- 保留人工审批、强制阻断和紧急恢复入口。

---

## 12. ODS 推荐默认策略

对于业务数据库同步到 ODS，可以采用以下默认策略：

1. 自动允许：新建表、新增可空字段、经过验证的类型扩宽。
2. 条件允许：新增非空字段、字段长度扩大、精度扩大。
3. 人工审批：字段改名、复杂类型修改、默认值变化。
4. 默认禁止：删列、删表、清表、主键变化、分区键变化、类型缩窄。
5. Schema 变更和数据写入必须有顺序保证。
6. Schema Evolution 与历史数据回补分别管理。
7. 所有变更都应包含数据校验和审计记录。
8. 多源合表以目标表的合并 Schema 为准，不能直接复制单个源表 DDL。

## 13. 快速决策表

| 当前链路 | 业务表变更后首先做什么 | 是否重启 Job | 谁修改 ODS | 是否自动回补 |
| --- | --- | --- | --- | --- |
| Flink SQL + CDC | 修改 SQL DDL并评估状态兼容性 | 通常需要 | 人工或外部 DDL 服务 | 否 |
| Pipeline → Doris/StarRocks/OceanBase 等 | 检查 Connector 和策略是否支持该 DDL | 通常不需要 | `MetadataApplier` | 否 |
| Pipeline → Paimon/Iceberg/Hudi | 检查 Catalog 和具体 Schema 操作支持 | 通常不需要 | Sink Connector/Catalog | 否 |
| Pipeline → Kafka → ODS | 先让 ODS Loader 应用 Schema 版本 | CDC Job 通常不需要 | 下游 Loader/DDL 服务 | 否 |
| DataX 全量 | 调度前 Schema Diff并更新目标表和配置 | 不适用 | 前置 Schema 管理任务 | 通常可以随全量完成 |
| DataX 增量 | 调度前 Schema Diff，之后单独安排回补 | 不适用 | 前置 Schema 管理任务 | 否 |
| 不支持 Schema Evolution 的 Pipeline Sink | 阻断或接入自研 Schema 管理能力 | 视实现而定 | 自研 `MetadataApplier` 或 DDL 服务 | 否 |

## 14. 一句话总结

> Flink SQL + CDC 使用静态 Schema，表结构变化通常需要改 SQL、改目标表并重新发布；Flink CDC Pipeline 可以动态捕获 Schema 变化，但只有 Sink 实现对应的 `MetadataApplier` 才能自动修改目标端，而且不会自动回补历史数据；DataX 适合在每次调度前自动比较 Schema、先改表和字段映射，再执行全量或增量同步，其中增量场景必须额外安排历史回补。
