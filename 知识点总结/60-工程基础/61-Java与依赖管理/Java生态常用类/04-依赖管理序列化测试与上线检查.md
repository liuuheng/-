# 依赖管理、序列化、测试与上线检查

> 目标：作业在 IDE 中能跑并不代表集群可运行；首次提交成功也不代表升级后能从 checkpoint/savepoint 恢复。本篇把依赖、ClassLoader、序列化和测试放在同一条上线证据链中。

## 1. Maven Scope 的真实含义

| Scope | 编译可见 | 测试可见 | 默认进入运行时/Fat JAR | Flink 常见用途 |
| --- | --- | --- | --- | --- |
| `provided` | 是 | 是 | 否 | Flink 核心 API、由集群提供的日志实现 |
| `compile` | 是 | 是 | 是 | 业务第三方库、通常是 connector/format/client |
| `runtime` | 否 | 是 | 是 | 只在运行时需要的实现 |
| `test` | 否 | 是 | 否 | JUnit、AssertJ、Flink test utils |

Flink 官方建议：Flink Java/DataStream API 和 runtime 由集群提供，不要打进作业 Uber JAR；业务所需的 connector、format 和第三方依赖通常需要随作业打包。实际边界仍取决于集群 `/lib`、Application Mode 镜像和平台部署规范。

### `provided` 的常见误解

`provided` 不是“这个依赖不重要”，而是“部署环境承诺提供兼容版本”。如果把某库设为 `provided`，必须能回答：

1. 哪个集群目录或镜像层提供它？
2. 具体版本是什么？
3. 所有 TaskManager 是否一致？
4. 升级集群时谁负责兼容性测试？

回答不了，就不能仅为缩小 JAR 而随意标 `provided`。

## 3. 是否需要 Shade Relocation

Relocation 能把作业的第三方包改到私有命名空间，例如：

```xml
<relocations>
    <relocation>
        <pattern>com.google.common</pattern>
        <shadedPattern>com.example.job.shaded.guava</shadedPattern>
    </relocation>
</relocations>
```

但不要默认重定位所有库。以下场景可能失败：

- 类名写在配置字符串中；
- Java SPI 文件没有正确转换；
- JSON 多态类型记录了全限定类名；
- JNI/native library 依赖固定包名；
- connector 与业务需要共享同一类型。

判断原则：先用 `dependency:tree` 证明存在版本冲突，再对冲突边界最小化 relocation，并做集群集成测试。

## 4. 依赖检查命令

```powershell
mvn -pl Flink -am dependency:tree -Dverbose
mvn -pl Flink -am dependency:tree -Dincludes=com.fasterxml.jackson.core
mvn -pl Flink -am dependency:tree -Dincludes=com.google.guava
mvn -pl Flink -am package -DskipTests
```

检查 Fat JAR：

```powershell
jar tf .\Flink\target\your-job.jar | Select-String `
    'org/apache/flink|com/fasterxml/jackson|org/slf4j'
```

预期：Flink core 类通常不在作业 JAR；业务明确打包的 Jackson 在；日志 binding 是否存在由部署规范决定，通常不应在作业中额外塞入一个与集群不同的 binding。

常见错误的含义：

| 错误 | 通常说明 | 排查方向 |
| --- | --- | --- |
| `ClassNotFoundException` | 类根本不可见 | Scope、JAR 内容、集群 `/lib`、插件目录 |
| `NoClassDefFoundError` | 类在初始化或依赖加载时失败 | 前置异常、传递依赖、静态初始化 |
| `NoSuchMethodError` | 编译和运行加载了不同版本 | dependency tree、ClassLoader 来源、重复 JAR |
| `ClassCastException: X cannot be cast to X` | 同名类由不同 ClassLoader 加载 | connector/plugin 隔离、重复打包 |
| multiple SLF4J bindings | 打入了多个日志实现 | 排除作业 binding，统一由集群提供 |

## 5. 两类序列化必须分开

### 5.1 用户函数/闭包序列化

目的：把函数从客户端/JobManager 发送到 TaskManager。

```java
public final class MyFunction extends RichMapFunction<Input, Output> {
    private final SerializableConfig config;
    private transient NonSerializableClient client;

    @Override
    public void open(Configuration parameters) {
        client = new NonSerializableClient(config);
    }
}
```

- 小而稳定的配置可以实现 `Serializable`；
- 网络连接、线程池、`ObjectMapper`、文件句柄等运行时资源使用 `transient` 并在 `open()` 创建；
- `serialVersionUID` 有助于明确 Java 序列化版本，但不能替代 savepoint 兼容设计。

### 5.2 数据和 State 序列化

目的：数据在网络、内存、checkpoint/savepoint 中编码。Flink 会提取 `TypeInformation` 并选择自己的 `TypeSerializer`。对象实现 `Serializable` 并不保证会成为 Flink POJO。

Flink 1.17 POJO 典型要求：

- public 独立类；
- public 无参构造器；
- 字段 public，或有规范 getter/setter；
- 字段非 final，字段类型可序列化。

未识别为 POJO 时可能退化为 Kryo。开发/测试环境可使用：

```java
env.getConfig().disableGenericTypes();
```

它能把意外的 Generic Type 提前变成失败，但如果作业确实依赖 Kryo，需要先制定显式注册和升级策略。

## 6. Lambda 捕获陷阱

```java
public final class JobBuilder {
    private final NonSerializableClient client = new NonSerializableClient();

    public DataStream<String> build(DataStream<String> input) {
        return input.map(value -> client.query(value));
    }
}
```

Lambda 捕获了 `this`，等价于尝试序列化整个 `JobBuilder`，其中又包含不可序列化客户端。即使当前 closure cleaner 恰好清理成功，这种代码也很脆弱。

改为显式函数类和最小配置：

```java
return input.map(new QueryFunction(clientConfig));
```

排查闭包时关注：

- 非静态内部类隐式持有外部类；
- 匿名类捕获局部变量；
- 方法引用 `service::method` 捕获 `service`；
- Logger 通常应为 `private static final`；
- 测试 Fixture 不要被生产 Lambda 捕获。

## 7. State 演进与 Operator UID

生产作业中的每个有状态或需要稳定追踪的算子都应设置明确、稳定的 UID：

```java
stream
    .keyBy(OrderEvent::getOrderId)
    .process(new OrderStateFunction())
    .name("order-state")
    .uid("order-state-v1");
```

显示名称可以改，UID 不应随意改。变更以下内容前必须做 savepoint 恢复测试：

- State 中 POJO 字段增加、删除、改名或改类型；
- Kryo/Avro/Protobuf/Jackson 版本；
- 自定义 serializer 及 snapshot；
- operator UID、拓扑结构和最大并行度；
- Java 类包名和类名。

“新代码能从空状态启动”不能证明“能从旧 savepoint 恢复”。

## 8. 测试金字塔

### 8.1 纯业务单元测试

把金额、时间、字段校验从 Flink 函数中提取为普通 Java 类，使用 JUnit 5 + AssertJ。它们运行最快，应覆盖绝大部分业务分支。

```java
@Test
void shouldCalculatePayableAmountWithDefinedRounding() {
    BigDecimal result = Pricing.calculate(
            new BigDecimal("19.90"),
            3,
            new BigDecimal("0.01"));

    assertThat(result).isEqualByComparingTo("59.69");
}
```

### 8.2 Flink 函数测试

无状态 `MapFunction`/`FilterFunction` 可以直接实例化调用。涉及 Context、Side Output、State 和 Timer 时使用 Flink test harness。示意：

```java
@Test
void invalidJsonShouldGoToDeadLetter() throws Exception {
    OrderEventParseFunction function = new OrderEventParseFunction();
    OneInputStreamOperatorTestHarness<String, OrderEvent> harness =
            ProcessFunctionTestHarnesses.forProcessFunction(function);
    try {
        harness.open();
        harness.processElement("{not-json", 1000L);

        ConcurrentLinkedQueue<StreamRecord<DeadLetter>> sideOutput =
                harness.getSideOutput(OrderEventParseFunction.DEAD_LETTER_TAG);
        assertThat(sideOutput).hasSize(1);
        assertThat(sideOutput.peek().getValue().getReasonCode())
                .isEqualTo("MALFORMED_JSON");
    } finally {
        harness.close();
    }
}
```

Test Harness 部分 API 在不同 Flink 版本间可能变化，测试依赖必须与生产 Flink 版本严格一致。

### 8.3 集成测试

使用 MiniCluster 验证 JobGraph、序列化、并行执行和 checkpoint；使用 Testcontainers 启动 Kafka/MySQL 等依赖。集成测试至少验证：

- 作业能提交，而不仅是类能编译；
- 数据从 source 到 sink 的完整结果；
- checkpoint 成功；
- 故障后恢复且输出满足幂等/事务预期；
- 作业 JAR 与目标集群运行环境一致。

### 8.4 Savepoint 兼容测试

升级流程：

1. 用旧版本代码写入具有代表性的 State；
2. 触发 savepoint；
3. 用新版本 JAR 从该 savepoint 恢复；
4. 继续输入数据，验证 State、timer、输出和指标；
5. 再验证回滚路径是否可行。

## 9. 当前项目的具体风险观察

基于当前 `Flink/pom.xml`：

- Flink 版本是 1.17.0，维护线已有 1.17.2；
- 编译目标为 Java 17，但 Flink 1.18 才正式准备好 Java 17；
- 使用 `fastjson:1.2.83`，应做安全审计并评估迁移；
- 使用旧的 `slf4j-log4j12:1.7.25` 且为 `provided`，实际日志绑定取决于集群；
- `hadoop-client`、`hive-exec`、Hive connector、Table planner 为 compile 范围，可能让 Fat JAR 很大并增加 Guava/Jackson/日志冲突；
- 官方对 Hadoop/Hive 依赖有特殊部署建议，不能仅靠把全部 Hadoop/Hive 打入用户 JAR 解决；
- Shade Plugin 版本较旧，且构建已经产生 `dependency-reduced-pom.xml`；
- 当前 POM 未见 JUnit/AssertJ/Flink test utils，生产代码缺少可见的自动化验证基线。

### 2026-08-31 实际依赖树证据

```powershell

  "-Dincludes=com.fasterxml.jackson.core:*,com.google.guava:guava,org.slf4j:*,log4j:*"
```

构建成功，但依赖树确认了以下事实：

| 依赖族 | Maven 最终选择 | 被覆盖的版本/来源 | 风险解释 |
| --- | --- | --- | --- |
| SLF4J API | 1.7.36 | 显式 binding 带 1.7.25；Hive/Hadoop 链还出现 1.6.x、1.7.5、1.7.7、1.7.10 等 | API 最终统一不等于 binding 唯一 |
| 日志 binding | 来源包括 `slf4j-log4j12`、`slf4j-reload4j`、`log4j-slf4j-impl` | 分别来自显式依赖、Hadoop、Hive | 当前 Shade 只排除 `org.slf4j:*` 和 `log4j:*`，不会匹配 groupId 为 `org.apache.logging.log4j` 的 Log4j2 binding，需要检查最终 JAR |
| Jackson | 2.12.0 | Hadoop 3.3.4 多处要求 2.12.7；更老链路还要求 2.7.x、2.8.x、2.9.x | Maven 选中 2.12.0，低于 Hadoop 所声明的 2.12.7，存在方法兼容、安全修复和行为差异风险 |
| Guava | 27.0-jre | Hive/Calcite/Arrow/Hadoop 子链要求 11.0.2、16.0.1、18.0、19.0 等 | 版本跨度很大；只看“最终选中 27”不能证明旧组件运行兼容 |

因此这里已经不是抽象的“可能有依赖冲突”，而是**确定存在版本仲裁和多个日志实现来源**；是否真正在线上报错，还需要最终 Fat JAR 内容、目标集群 `/lib`、实际类加载来源和功能回归测试共同证明。

当前模块执行 `mvn -f Flink\pom.xml -DskipTests compile` 已成功，但输出为 `Nothing to compile - all classes are up to date`。它证明 Maven 模型和现有增量产物没有阻断构建，不等于完成了 clean rebuild、测试、Fat JAR 或集群提交验证。

### 实际 Fat JAR 审计

随后执行：

```powershell
mvn -f Flink\pom.xml -DskipTests package
```

本次实际重新编译了 112 个 Java 源文件并成功打包，但结果暴露出比依赖树更直接的问题：

| 检查项 | 实际结果 | 结论 |
| --- | --- | --- |
| JAR 大小 | 222,276,118 bytes，约 212 MiB | 对普通 Flink Job 明显偏大，主要由 Hadoop/Hive/Table Planner 及其传递依赖造成 |
| JAR 条目数 | 115,942 | 类与资源面非常大，冲突和漏洞审计成本高 |
| Flink Core | 包含 `org/apache/flink/api/common/JobID.class` | 当前 Fat JAR 确实打入了 Flink core，不符合“核心由集群提供”的目标 |
| 日志 binding | 包含 `org/apache/logging/slf4j/Log4jLoggerFactory.class` | `org.apache.logging.log4j:log4j-slf4j-impl` 未被现有 `org.slf4j:*`/`log4j:*` 排除规则覆盖 |
| Jackson | 包含 `com/fasterxml/jackson/databind/ObjectMapper.class` | 作业携带非 shaded Jackson 2.12.0，同时还有 Flink shaded Jackson，必须确认边界 |
| Guava | 包含 `com/google/common/collect/ImmutableList.class` | 作业携带 Guava 27.0-jre，旧 Hive/Calcite 组件是否兼容需实测 |

Shade 还报告了大量重复类，包括 Protobuf、Parquet、ORC、Hive、Calcite Avatica、Commons Lang、Joda-Time 等。尤其值得立即处理的是：

```text
Flink/src/main/java/org/apache/flink/api/common/eventtime/
    BoundedOutOfOrdernessWatermarks.java
```

项目源码自己定义了 `org.apache.flink.*` 包下的同名类，Shade 明确报告它与 `flink-core-1.17.0.jar` 中的类重复。业务代码不应复制或覆盖 Flink 官方包名；不同 ClassLoader/打包顺序下可能加载不同实现。应把自定义实现移动到业务命名空间，例如 `com.atguigu.flink...`，或者直接使用官方类。

本次 JAR 的 SHA-256 为：

```text
2667EB55B0364B9CBF2AAD91B66D5BDE7EDF44762BF0B744CB0517566AE396E5
```

该哈希只用于记录本次审计产物，不代表该 JAR 已通过生产验收。综合证据表明，当前 JAR **不应因为 `BUILD SUCCESS` 就直接提交生产集群**；应先收敛依赖范围、移除官方包名下的复制类、统一日志边界，并重新进行 clean package、JAR 检查和集群测试。

## 10. 上线门禁清单

### 配置

- [ ] 所有必填参数在提交阶段校验；
- [ ] Secret 不在 args、日志、Global Job Parameters 和异常中；
- [ ] 配置优先级有测试；
- [ ] 所有 timeout 都带单位并且层级合理。

### 依赖

- [ ] `dependency:tree -Dverbose` 无未经解释的冲突；
- [ ] Fat JAR 不含 Flink core 和额外日志 binding；
- [ ] Connector/format 在目标部署模式下可见；
- [ ] 漏洞扫描和许可证检查通过；
- [ ] 集群所有节点依赖一致。

### 序列化和状态

- [ ] 数据类型是预期 POJO/Avro/显式 serializer；
- [ ] 没有意外的 Kryo fallback；
- [ ] 运行时客户端为 `transient` 且在 `open()` 创建；
- [ ] Operator UID 稳定；
- [ ] 从真实旧 savepoint 恢复测试通过。

### 外部系统

- [ ] 总连接数和总并发按并行度核算；
- [ ] 连接、请求、operator timeout 有层级；
- [ ] 重试只覆盖瞬态错误且有总预算；
- [ ] 写操作有服务端幂等或事务保证；
- [ ] 限流、熔断和重启不会形成放大风暴。

### 数据质量与观测

- [ ] 脏数据分类、侧输出、Sink、保留和脱敏策略完整；
- [ ] 日志不逐条打印完整事件；
- [ ] 成功、失败、超时、重试、脏数据和延迟有指标；
- [ ] 告警阈值经过压测/历史基线校准。

### 测试

- [ ] 纯业务单测覆盖边界；
- [ ] Flink harness 覆盖 State/Timer/Side Output；
- [ ] MiniCluster/外部系统集成测试通过；
- [ ] 故障恢复、重复输入、乱序、慢请求和容量压测通过。
