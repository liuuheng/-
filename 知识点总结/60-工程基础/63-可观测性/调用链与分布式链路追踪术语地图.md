# 调用链与分布式链路追踪术语地图

> 相关笔记：[[单点登录语境与开发人员常用术语地图]]

## 1. 核心认识

“调用链”通常有两种含义。**代码调用链**描述一个进程内部函数之间的调用关系，例如 Controller 调用 Service，Service 再调用 Repository；**分布式调用链**描述一次请求跨越网关、微服务、缓存、数据库、消息队列和第三方服务的完整路径。开发人员说“查一下调用链”时，通常指后者，也就是 Distributed Tracing。

调用链不等同于日志。链路追踪擅长回答“请求经过了哪里、哪一步最慢、错误从哪里开始”；日志擅长解释某个步骤内部具体发生了什么；指标用于判断问题的规模和趋势；Profiler 则继续深入到进程内部，分析哪些函数消耗 CPU、内存或等待时间。

```text
指标发现异常
   ↓
调用链定位到服务或依赖
   ↓
日志解释具体事件
   ↓
Profiler深入代码内部
```

## 2. 一条典型调用链

```text
用户
  → 前端页面
  → CDN / 负载均衡
  → API Gateway
  → 认证服务
  → 订单服务
      ├─→ Redis
      ├─→ MySQL
      └─→ 消息队列 → 库存服务
  → 第三方支付平台
```

整条请求通常共享一个 `Trace ID`，每个处理步骤拥有独立的 `Span ID`：

```text
Trace ID: abc-123
├── Span 1：网关接收请求
├── Span 2：认证服务校验Token
├── Span 3：订单服务处理业务
│   ├── Span 4：查询Redis
│   ├── Span 5：写入MySQL
│   └── Span 6：发送订单消息
└── Span 7：调用支付服务
```

## 3. 核心数据模型

| 术语 | 英文 | 含义 |
|---|---|---|
| 调用链 | Call Chain | 请求经过多个函数、组件或服务的路径。 |
| 链路追踪 | Distributed Tracing | 采集并还原跨服务请求路径的机制。 |
| Trace | Trace | 一次请求从开始到结束的完整追踪记录。 |
| Span | Span | Trace 中的一次具体操作或调用。 |
| Trace ID | Trace Identifier | 唯一标识整条 Trace。 |
| Span ID | Span Identifier | 唯一标识一个 Span。 |
| Root Span | Root Span | 一条 Trace 的起始 Span。 |
| Parent Span | Parent Span | 当前 Span 的直接上游步骤。 |
| Child Span | Child Span | 由当前 Span 产生的下游步骤。 |
| Span Link | Span Link | 关联不存在直接父子关系的 Span，常见于异步和批处理。 |
| Attribute | Attribute | 描述 Span 的键值属性，例如接口名、状态码和数据库类型。 |
| Event | Span Event | Span 执行期间发生的瞬时事件，例如异常或重试。 |
| Status | Span Status | 表示 Span 是否成功以及错误状态。 |
| Resource | Resource | 产生遥测数据的服务、实例、容器等资源信息。 |
| Service Name | Service Name | 标识 Span 属于哪个服务。 |

父子关系表达的是调用结构，不一定表示严格的时间顺序。多个 Child Span 可能并行执行；因此总耗时不一定等于所有 Span 耗时简单相加。

## 4. 上下文传播

链路追踪能够跨服务连续，依赖 **Context Propagation（上下文传播）**。调用方在请求中携带 Trace ID、当前 Span 等信息，下游读取后创建新的 Child Span。如果上下文没有被正确传递，下游通常会生成新的 Trace，表现为“链路断了”。

| 术语 | 含义 |
|---|---|
| Trace Context | 当前请求的追踪上下文。 |
| Context Propagation | 在进程、线程和服务之间传递上下文。 |
| Propagator | 负责注入和提取追踪上下文的组件。 |
| Inject | 把上下文写入 HTTP Header 或消息属性。 |
| Extract | 从收到的请求或消息中读取上下文。 |
| Baggage | 随调用链传播的附加业务信息。 |
| Correlation ID | 用于关联多条相关记录的通用标识。 |
| Request ID | 标识某一次请求，范围可能只限于网关或单个服务。 |
| MDC | Java 日志中常用于保存 Trace ID 等线程上下文的机制。 |
| Async Context | 在异步任务和线程切换中保持上下文。 |

常见传播载体：

- HTTP：通过请求 Header 传播。
- gRPC：通过 Metadata 传播。
- 消息队列：通过 Message Header 或 Properties 传播。
- 进程内部：通过线程上下文、协程上下文或显式参数传播。

常见 Header：

```text
traceparent
tracestate
baggage
X-Request-ID
X-B3-TraceId
X-B3-SpanId
```

`traceparent` 和 `tracestate` 属于 W3C Trace Context；`X-B3-*` 常见于 Zipkin 体系；`X-Request-ID` 没有统一规定，不应默认它一定等于 Trace ID。

## 6. 延迟与性能

| 术语 | 含义 |
|---|---|
| Latency | 完成一次请求所需的时间。 |
| Duration | 某个 Span 从开始到结束的持续时间。 |
| Response Time | 调用者实际感知到的响应时间。 |
| Queue Time | 请求等待线程、连接或执行资源的时间。 |
| Processing Time | 程序真正执行处理的时间。 |
| Network Latency | 网络传输消耗的时间。 |
| Serialization Time | 数据序列化和反序列化耗时。 |
| QPS | 每秒处理的请求数量。 |
| TPS | 每秒完成的事务数量。 |
| Throughput | 单位时间内系统完成的工作量。 |
| P50/P95/P99 | 相应百分比请求不超过的延迟值。 |
| Tail Latency | 少量最慢请求的延迟。 |
| Critical Path | 真正决定整条调用链总耗时的串行路径。 |
| Bottleneck | 限制整体性能的环节。 |
| Hotspot | 流量或资源高度集中的位置。 |
| Fan-out | 一个请求向多个下游发起调用。 |
| Fan-in | 多个调用结果汇集到同一个节点。 |

平均响应时间可能掩盖少量严重慢请求。排查偶发超时时，P95、P99和异常慢Trace通常比平均值更有价值。

## 8. 同步与异步调用链

同步调用通常表现为上游等待下游响应：

```text
订单服务 → 库存服务 → 数据库
```

异步调用通常跨越消息队列，生产者发送消息后不等待消费者完成：

```text
订单服务 → 消息队列 → 库存服务
```

| 术语 | 含义 |
|---|---|
| Synchronous Call | 调用方等待下游返回结果。 |
| Asynchronous Call | 调用方不在原位置等待最终结果。 |
| Message Queue | 在生产者和消费者之间保存并传递消息。 |
| Producer | 发送消息的一方。 |
| Consumer | 接收并处理消息的一方。 |
| Topic | 消息所属的逻辑主题。 |
| Message ID | 唯一标识一条消息。 |
| Consumer Group | 共同分担消息的一组消费者。 |
| Event-Driven | 通过事件产生和消费推动系统协作。 |
| Message Backlog | 生产速度超过消费速度形成的消息积压。 |
| Duplicate Delivery | 同一条消息被投递多次。 |
| Dead Letter Queue | 保存无法正常处理的消息。 |

异步链路不一定适合强行表示成单一父子关系。批处理或“一条消息影响多条链路”的场景，可以使用 Span Link 表达关联。消费者创建 Span 时还应注意不要无限继承已经失效的上游超时。

## 9. 采样、存储与成本

全量保存所有Trace可能产生较高的网络、存储和查询成本，因此生产环境通常需要采样策略。

| 术语 | 含义 |
|---|---|
| Sampling | 只保留部分Trace。 |
| Sampling Rate | 被采集请求所占比例。 |
| Head Sampling | 请求开始时决定是否采样。 |
| Tail Sampling | 请求结束后根据耗时和结果决定是否保留。 |
| Error Sampling | 优先保留包含错误的Trace。 |
| Slow Trace Sampling | 优先保留超过耗时阈值的Trace。 |
| Adaptive Sampling | 根据流量和系统状态动态调整采样率。 |
| Trace Drop | Trace因采样、拥塞或队列限制被丢弃。 |
| Retention | 遥测数据的保存时间。 |
| Cardinality | 属性可能产生的不同值数量。 |

高基数字段会产生大量不同值，例如用户ID、订单号和完整URL。它们可能适合作为日志字段或可检索的Span属性，但不适合作为普通指标标签；同时必须考虑隐私、合规和成本。

## 11. 超时、重试与故障传播

| 术语 | 含义 |
|---|---|
| Timeout | 等待下游超过限定时间后终止。 |
| Deadline | 整个操作必须完成的最终时间点。 |
| Timeout Budget | 在不同下游之间分配总超时时间。 |
| Retry | 调用失败后重新尝试。 |
| Exponential Backoff | 每次重试逐步增加等待时间。 |
| Jitter | 在重试间隔中加入随机量，避免大量请求同时重试。 |
| Retry Storm | 大量请求同时重试，进一步压垮下游。 |
| Circuit Breaker | 下游持续失败时暂时停止调用。 |
| Fallback | 主流程失败时使用备用结果。 |
| Degradation | 关闭次要功能，优先保住核心能力。 |
| Bulkhead | 隔离线程池、连接池等资源，防止故障扩散。 |
| Rate Limiting | 限制单位时间内允许的请求数量。 |
| Idempotency | 相同操作重复执行不会产生额外业务副作用。 |
| Failure Propagation | 下游错误逐层影响上游。 |
| Cascading Failure | 一个局部故障引发大范围连锁故障。 |
| Partial Failure | 一次分布式操作中只有部分步骤失败。 |

上游超时时间通常不应短于其预期下游耗时，也不应让每层服务都进行无边界重试。若网关、服务A和服务B各重试三次，最坏情况下可能把一次用户请求放大成大量下游调用。

## 12. 数据库与缓存Span

| 术语 | 含义 |
|---|---|
| DB Span | 一次数据库访问对应的Span。 |
| SQL Statement | 实际执行的SQL语句。 |
| Query Duration | 查询执行耗时。 |
| Slow Query | 超过预期时间的查询。 |
| Execution Plan | 数据库选择的查询执行方式。 |
| Full Table Scan | 查询检查大量或全部记录。 |
| Lock Wait | 等待其他事务释放锁。 |
| Deadlock | 多个事务循环等待对方持有的锁。 |
| Pool Exhaustion | 连接池中的连接全部被占用。 |
| Transaction | 需要作为整体成功或失败的一组操作。 |
| Cache Hit | 从缓存直接找到目标数据。 |
| Cache Miss | 缓存中没有目标数据，需要访问后端数据源。 |
| Redis Command | 对Redis执行的一次命令。 |

数据库Span适合记录数据库类型、操作类型、表或逻辑语句等信息，但不应不加处理地记录密码、Token、完整个人信息或敏感SQL参数。

## 13. 代码内部调用链

| 术语 | 含义 |
|---|---|
| Function Call | 一个函数调用另一个函数。 |
| Call Stack | 当前线程中尚未返回的嵌套函数调用。 |
| Stack Frame | 某一次函数调用在调用栈中的记录。 |
| Stack Trace | 异常或采样时记录的调用栈快照。 |
| Caller | 调用当前函数的代码。 |
| Callee | 被当前代码调用的函数。 |
| Entry Point | 程序或流程开始执行的位置。 |
| Recursion | 函数直接或间接调用自身。 |
| Call Depth | 函数嵌套调用的深度。 |
| Stack Overflow | 调用层级过深导致调用栈耗尽。 |
| Callback | 某项操作完成后执行的函数。 |
| Future/Promise | 表示未来才会得到的异步结果。 |

需要区分：Call Stack是某个时刻单线程内的函数嵌套；Stack Trace是它的一次记录；Distributed Trace则跨越多个进程、服务和基础设施。

## 14. 高频故障及检查方向

| 现象 | 优先检查 |
|---|---|
| 完全没有Trace数据 | SDK或Agent是否启用、Exporter和Endpoint配置、采样是否关闭。 |
| 只显示网关Span | 网关是否向下游注入Trace Context。 |
| 从某个服务开始断链 | 客户端库是否埋点、代理是否删除Header、下游是否提取上下文。 |
| 消息发送后断链 | Trace信息是否写入消息Header，消费者是否提取。 |
| 日志找不到对应Trace | 日志格式是否包含Trace ID，异步执行是否丢失上下文。 |
| Trace ID中途变化 | 下游是否错误创建了新的Root Span。 |
| Trace耗时大于可见Span | 是否存在未埋点等待、排队、网络或并行空隙。 |
| 大量Span缺失 | 采样策略、Collector压力、导出队列和后端限流。 |
| Span数量突然增加 | 循环调用、扇出扩大或过度埋点。 |
| 接口偶发超时 | 查看异常慢Trace和P99，而不是只看平均值。 |
| 数据库Span耗时高 | 慢SQL、锁等待、连接池、执行计划和数据库负载。 |
| 第三方调用耗时高 | DNS、建连、TLS、网络、限流、超时和重试。 |

## 15. 开发人员高频表达

| 表达 | 实际在问什么 |
|---|---|
| “把Trace ID给我。” | 需要请求标识来检索完整链路。 |
| “链路断了。” | 追踪上下文没有继续传递到下游。 |
| “这个服务没埋点。” | 该步骤没有产生可查询的Span。 |
| “看一下最慢的Span。” | 找出请求中耗时最大的步骤。 |
| “问题从哪一跳开始？” | 确认哪个服务或依赖最早出现异常。 |
| “日志和链路串起来了吗？” | 能否通过Trace ID关联日志与Trace。 |
| “异步链路接上了吗？” | 消息生产者和消费者是否建立追踪关联。 |
| “采样率是多少？” | 有多少比例的请求会被保存。 |
| “上游超时还是下游慢？” | 区分调用方限制与被调用方性能问题。 |
| “连接池是不是打满了？” | 请求是否因没有可用连接而排队。 |
| “有没有扇出调用？” | 一个请求是否产生大量并行下游调用。 |
| “关键路径在哪里？” | 哪些串行步骤真正决定总耗时。 |
| “是不是重试放大了？” | 重试是否增加了下游压力。 |
| “错误传播上来了吗？” | 下游失败是否被正确返回和记录。 |
| “全链路压测。” | 在接近真实的完整调用路径上进行压力测试。 |
| “全链路灰度。” | 让灰度请求经过的各个服务保持在对应版本。 |

## 16. 易混淆概念

### Trace ID与Request ID

Trace ID通常贯穿多个服务；Request ID可能只标识网关或单个服务接收的一次请求。部分系统让两者相同，但这不是通用规则。

### Trace与服务拓扑

Trace是一条具体请求的路径；服务拓扑是大量Trace汇总后形成的整体依赖关系。拓扑显示“通常怎样调用”，Trace显示“这一次实际怎样调用”。

### Trace与Profiler

Trace可以定位到“订单服务很慢”，Profiler继续定位到订单服务内部的具体函数、CPU、内存、锁或I/O等待。

### Parent-Child与Span Link

父子Span适合表达直接调用关系；Span Link适合消息、批处理、多来源聚合等难以表示为单一父子的关系。

### 同步、异步、阻塞和非阻塞

同步/异步描述结果如何返回和协作；阻塞/非阻塞描述等待期间执行单元能否继续工作。它们属于不同维度。

## 17. 实用排查顺序

1. 获取问题请求的时间、接口、用户或业务标识以及Trace ID。
2. 查看整条Trace的状态、总耗时和服务路径。
3. 找到错误Span、关键路径和最慢Span。
4. 判断耗时来自处理、排队、网络、连接池还是重试。
5. 使用Trace ID查找对应服务日志。
6. 查看该时间段的CPU、内存、线程池、连接池和错误率。
7. 检查数据库、缓存、消息队列和第三方依赖。
8. 对比一条正常Trace和一条异常Trace。
9. 提出多个可能原因，逐项用数据或实验验证。
10. 修复后对比P95、P99、吞吐量和错误率，确认没有转移问题。

## 18. 判断原则

- 不要仅凭最慢Span直接认定根因；它可能只是在等待更深层但未埋点的依赖。
- 不要把相关性当因果关系；调用链定位的是异常位置，根因仍需结合日志、指标和实验确认。
- 不要只看平均值；偶发故障通常需要检查P95、P99和异常Trace。
- 不要无限制增加埋点；优先覆盖网络边界、数据库、消息和关键业务阶段。
- 不要在Trace中记录密码、Token、完整个人信息等敏感数据。
- 链路断裂优先检查上下文是否被注入、传输和提取，而不是先怀疑追踪后端。

一句话总结：**指标发现问题的规模，调用链定位问题所在的服务或依赖，日志解释具体事件，Profiler继续深入代码内部；最终根因必须由证据验证。**
