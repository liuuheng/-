# SaaS 线索域、MQL、SQL 与 CRM

## 1. 线索域是什么

线索域是围绕潜在客户从产生、识别、分配、跟进、转商机到成交全过程的数据主题域。

它关注的核心问题是：

- 线索从哪里来
- 线索是谁，属于什么客户类型
- 线索是否有效
- 是否值得销售跟进
- 销售是否已跟进
- 是否转成商机
- 是否最终成交

在 SaaS / B2B 公司中，线索域通常连接市场获客、销售转化、客户增长和收入分析。

## 2. 线索域常见对象

| 对象 | 含义 |
|---|---|
| Lead 线索 | 一个潜在客户记录，可能来自官网、广告、活动、销售录入等 |
| Contact 联系人 | 客户公司里的具体联系人，如老板、采购、设计主管 |
| Account 客户/企业 | 线索背后的公司主体 |
| Source 来源 | 线索来自哪个渠道、媒介、广告或活动 |
| Campaign 活动 | 线索所属市场活动或投放计划 |
| Follow-up 跟进记录 | 销售或运营的触达、沟通、拜访、演示记录 |
| Opportunity 商机 | 已确认有明确成交可能的销售机会 |
| Customer 成交客户 | 最终签约或付费的客户 |

## 3. MQL 是什么

MQL 是 Marketing Qualified Lead，中文可理解为“市场认可线索”。

它表示：市场或运营认为这个线索质量达到标准，值得交给销售继续跟进。

MQL 更偏市场/运营口径，通常可以通过客户画像、来源渠道、行为场景和线索评分自动判断。

常见判断条件包括：

- 联系方式有效
- 非重复、非测试、非同行线索
- 客户类型属于目标客群
- 行业、地区、规模符合业务要求
- 来源渠道质量较高
- 发生过高意向行为

高意向行为示例：

- 申请试用
- 预约演示
- 咨询价格
- 提交企业信息
- 下载报价或方案资料
- 参加指定获客活动
- 持续使用核心功能

示例规则：

```text
MQL = 联系方式有效
  AND 非重复/非测试/非无效线索
  AND 属于目标客户画像
  AND 命中至少一个高意向行为
```

也可以采用评分制：

| 行为或属性 | 示例分值 |
|---|---:|
| 填写手机号 | +10 |
| 填写公司名称 | +10 |
| 行业属于目标行业 | +20 |
| 申请试用 | +30 |
| 预约演示 | +40 |
| 咨询价格 | +40 |
| 7 天内多次活跃 | +15 |
| 来源为高质量渠道 | +10 |

示例：

```text
lead_score >= 60
AND 联系方式有效
AND 非无效线索
则判定为 MQL
```

## 4. SQL 是什么

SQL 是 Sales Qualified Lead，中文可理解为“销售认可线索”。

它表示：销售经过有效触达后，确认这个线索有真实业务需求，值得进入正式销售流程。

SQL 更偏销售口径，通常需要销售跟进后确认，也可以结合 CRM 中的销售动作自动识别。

常见判断条件包括：

- 已完成有效触达
- 确认客户存在真实业务需求
- 有采购可能或试用意愿
- 找到决策人或关键联系人
- 有明确下一步动作

下一步动作示例：

- 建立商机
- 安排产品演示
- 发送报价单
- 开通试用
- 进入合同沟通
- 约定下一次会议

示例规则：

```text
SQL = 已是 MQL
  AND 销售完成有效触达
  AND 确认真实业务需求
  AND 存在明确下一步销售动作
```

## 5. MQL 和 SQL 的区别

| 阶段 | 主要判断方 | 判断重点 | 是否适合自动化 |
|---|---|---|---|
| MQL | 市场/运营 | 线索质量、画像匹配、行为意向 | 较适合自动规则或评分判定 |
| SQL | 销售 | 真实需求、采购可能、销售下一步 | 需要销售确认，可结合 CRM 动作自动打标 |

简单理解：

- MQL：市场认为值得销售跟进
- SQL：销售确认值得进入销售流程

漏斗关系：

```text
原始线索 Lead
→ 有效线索 Valid Lead
→ MQL 市场认可线索
→ SQL 销售认可线索
→ 商机 Opportunity
→ 成交客户 Customer
```

## 6. CRM 是什么

CRM 是 Customer Relationship Management，中文通常叫客户关系管理系统。

在 SaaS / B2B 公司中，CRM 用来管理从潜在客户到成交客户的全过程，包括线索、客户、联系人、商机、跟进、合同、订单和销售负责人。

CRM 中常见数据模块：

| 模块 | 说明 |
|---|---|
| 线索 Lead | 官网留资、广告线索、活动报名等潜在客户 |
| 客户 Account | 公司或客户主体 |
| 联系人 Contact | 客户公司里的具体人 |
| 商机 Opportunity | 有明确成交可能的销售机会 |
| 跟进记录 Activity | 电话、微信、拜访、演示、报价等 |
| 合同 Contract | 签约金额、服务周期、套餐版本 |
| 订单 Order | 实际购买、续费、增购、退款等 |
| 销售 Owner | 客户或商机负责人 |

## 7. 数仓提表建议

数仓中不要只保留一个 `lead_status`，建议拆成可分析的判定字段和过程字段。

建议字段：

| 字段 | 说明 |
|---|---|
| lead_id | 线索 ID |
| is_valid_lead | 是否有效线索 |
| lead_score | 线索评分 |
| is_mql_rule_hit | 是否命中 MQL 规则 |
| mql_time | 首次成为 MQL 的时间 |
| mql_reason | 成为 MQL 的原因，如预约演示、申请试用 |
| is_sql_confirmed | 是否销售确认 SQL |
| sql_time | 成为 SQL 的时间 |
| sql_reason | 成为 SQL 的原因，如已建商机、已报价 |
| assigned_sales_id | 分配销售 ID |
| first_follow_time | 首次跟进时间 |
| sales_follow_status | 销售跟进状态 |
| disqualify_reason | 不合格或无效原因 |
| opportunity_id | 关联商机 ID |

建议主题表：

| 表 | 用途 |
|---|---|
| 线索主表 | 记录线索基本信息、来源、状态 |
| 联系人表 | 记录联系人、职位、联系方式 |
| 企业/客户表 | 识别线索背后的公司主体 |
| 线索来源表 | 渠道、媒介、广告计划、活动 |
| 线索分配表 | 记录线索分配给哪个销售或团队 |
| 跟进记录表 | 记录销售触达、沟通结果和下一步动作 |
| 商机表 | 判断线索是否转为明确销售机会 |
| 合同/订单表 | 判断是否最终成交、续费、增购 |

## 8. 分析价值

拆清 MQL 和 SQL 后，可以分析：

- 哪些渠道带来的 MQL 多
- 哪些渠道 MQL 到 SQL 转化率高
- 哪些活动线索少但质量高
- 哪些销售跟进及时率低
- 哪些来源线索被销售大量否决
- 哪些客户画像最容易转商机和成交
- 市场认为高质量的线索，销售是否认可

## 9. 关键结论

MQL / SQL 不是纯运营主观判断，也不是完全依赖行为自动判断。

更合理的方式是：

```text
MQL = 市场/运营定义规则 + 用户画像 + 来源渠道 + 行为场景 + 线索评分
SQL = MQL 基础上 + 销售有效触达 + 真实需求确认 + 下一步销售动作
```

也就是说，MQL 更适合规则化和数据化，SQL 更依赖销售确认，但可以通过 CRM 行为进行辅助自动打标。
