# Flink P0 任务故障恢复 SOP 与适用边界

## 结论

P0 故障 SOP 的作用是在高压环境下缩短决策链：告警触达后，Oncall 不从零开始分析，而是根据已登记的任务和故障场景执行经过演练的恢复预案，在约定时间内恢复数据链路，再处理根因。

一份可执行的 SOP 至少要同时定义：任务等级、告警入口、恢复步骤、验证标准、升级时点、数据风险、故障记录和演练机制。任务进入 `RUNNING` 只说明进程恢复；Lag、Checkpoint、输出 TPS 和下游数据都恢复正常，才能确认业务链路恢复。

原文把目标设为 5 分钟完成快速恢复，这适合作为团队 RTO（Recovery Time Objective，恢复时间目标）的示例，不是所有 Flink 任务都能直接套用。大状态恢复、外部依赖故障、Checkpoint 损坏或下游非幂等时，数据正确性应优先于机械满足 5 分钟。

## SOP 的职责边界

故障响应阶段负责：

- 快速识别任务和故障场景；
- 执行预先验证过的恢复动作；
- 判断任务与数据链路是否恢复；
- 在规定时间内升级；
- 明确数据重复、丢失和延迟风险。

故障响应阶段不承担完整根因分析、代码修复和架构改造。这些工作放到恢复后的复盘中，避免 Oncall 在业务中断期间长时间试错。

“不临场分析”也不能理解成无条件执行命令。Oncall 仍需完成预案要求的场景识别、安全前置检查和停止条件；未命中预案、证据冲突或操作可能扩大数据影响时，应升级而不是猜测。

## 角色与责任

| 角色 | 故障期间的职责 | 日常职责 |
| --- | --- | --- |
| 一线 Oncall | 接收告警、匹配预案、执行恢复、快速验证、按时升级 | 熟悉任务清单与操作平台，参加演练 |
| 二线 Oncall / 技术负责人 | 处理预案未覆盖的问题，决定降级、回滚或扩大协作范围 | 审核预案，主持复盘，跟踪改进项 |
| 任务负责人 | 提供业务语义、状态和下游影响判断 | 上线前登记任务、绑定预案、维护告警与恢复条件 |
| 业务负责人 | 确认业务影响和可接受的数据风险 | 参与 P0 定级、降级方案和恢复验收 |

新 Oncall 上岗前应完整走通一次演练。平台升级、任务拓扑变化、Kafka 分区调整、状态后端或 Sink 变化后，需要重新验证相关预案。

## 5 分钟响应框架

原文给出的时间划分：

```text
0:00～1:00  接收告警，打开平台，确认任务和故障场景
1:00～3:00  执行绑定的恢复预案
3:00～5:00  完成快速验证
5:00       未通过快速验证则升级，同时继续处置
```

快速验证只回答“链路是否开始恢复”，不代替完整验收：

- [ ] Job 状态为 `RUNNING`；
- [ ] Lag 开始下降，不要求立即归零；
- [ ] 输出 TPS 大于 0。

实际团队应通过演练和历史事故测量恢复时间分布，再制定 RTO。状态规模很大的任务如果正常恢复就需要十几分钟，把 RTO 写成 5 分钟只会制造虚假达标或诱导跳过数据检查。

## P0 任务清单

每个 P0 任务上线前登记以下信息：

| 字段 | 内容 |
| --- | --- |
| 任务名与 Job ID | 能在告警和平台中唯一定位任务 |
| 业务含义 | 任务中断影响哪些业务指标或接口 |
| Owner 与 Oncall | 一线、二线和业务联系人 |
| Source / Sink | Kafka Topic、数据库或湖表等依赖 |
| 状态规模与恢复基线 | 正常启动时间、Checkpoint 大小、恢复耗时 |
| 默认预案 | 当前场景优先执行的预案编号 |
| 备用预案 | 默认预案失败后的路径 |
| 数据风险 | 是否允许重放，Sink 是否幂等或支持事务 |
| 降级方案 | 无法恢复时如何停止影响或切换链路 |

告警必须携带任务标识、环境、故障时间和预案入口。只有告警，没有任务到预案的映射，Oncall 仍然需要现场搜索资料。

## 恢复预案

### 预案 A：从最新 Checkpoint 重启

适用于任务 `FAILED`、持续 `RESTARTING`，且最新 Checkpoint 已确认可用的场景。

```text
停止任务
→ 等待 STOPPED
→ 选择最新可用 Checkpoint 启动
→ 等待 RUNNING
→ 执行快速验证
```

“最新 Checkpoint”不能只按时间选择，还要检查它是否成功完成、外部化文件是否存在、状态后端是否可访问，以及 Source 和 Sink 是否能从该状态一致恢复。

### 预案 B：调整并行度后重启

适用于已经确认处理能力不足、Source 或算子吞吐构成瓶颈的场景。原文示例是把并行度提高到当前值的 1.5 倍，并且不超过 Kafka 分区数。

这个上限只直接约束 Kafka Source 的有效读取并行度。中间算子和 Sink 是否能扩展，还取决于 Key 分布、下游连接数、写入限流、状态重分布成本和资源余量。若 Lag 来自外部 Sink 变慢或热点 Key，单纯增加并行度可能无效，甚至扩大下游压力。

执行扩容前至少确认：

- [ ] 哪个算子出现反压或 Busy；
- [ ] Source 分区数是否允许增加有效并发；
- [ ] TaskManager Slot、CPU、网络和内存是否充足；
- [ ] Sink 能否承受更高并发；
- [ ] Rescale 后的状态恢复时间是否满足 RTO。

### 预案 C：从旧 Checkpoint 回滚

适用于最新 Checkpoint 损坏、近期变更导致启动失败，且已找到问题发生前的可用 Checkpoint。

从旧 Checkpoint 恢复通常会形成数据重放窗口，但“重放”不等于最终一定重复。最终结果取决于：

- Source 是否从 Checkpoint 中保存的 Offset 恢复；
- Sink 是否参与 Flink Checkpoint 事务；
- Sink 是否支持幂等 Upsert 或业务去重；
- 外部副作用是否处于 Flink 一致性边界之外。

操作前记录目标 Checkpoint、回放起点和预计时间窗口；恢复后按该窗口核查下游。无法证明 Sink 幂等或 Exactly-Once 时，应提前通知业务方可能出现重复或不一致。

### 预案 D：OOM 后调整资源

原文给出的示例是增加 TaskManager 内存后重启。该动作只能作为经过验证的临时恢复手段，不能把所有 OOM 都归因于“内存太小”。

先区分日志和容器信号：

- JVM Heap OOM：检查对象堆积、算子缓存和堆内状态；
- Direct Memory OOM：检查网络缓冲、序列化和堆外使用；
- RocksDB / Managed Memory：检查状态大小、写缓冲和 Compaction；
- Container OOM / Exit 137：检查进程总内存与 `memoryOverhead`；
- Metaspace OOM：检查类加载和依赖问题。

增加内存后仍持续线性上涨，或相同流量下内存不断逼近上限，应升级处理，不要循环扩容掩盖泄漏。

### 预案 E：外部依赖故障

适用于数据库、缓存、检索服务或远程接口超时造成的吞吐下降。

恢复动作不能默认等同于“让组件负责人扩容 50%”。先确认依赖端的错误率、延迟、限流、连接池和容量，再由依赖 Owner 执行已批准的扩容、切流或降级预案。Flink 侧同时观察算子状态、Checkpoint 和 Lag，避免依赖恢复后瞬时流量压垮下游。

## 快速验证与完整验证

快速验证通过后，应在约定窗口内完成完整验证：

- [ ] Checkpoint 重新成功，持续时间回到可接受范围；
- [ ] Lag 回落到历史正常水位；
- [ ] 反压消失，Busy、BackPressured、Idle 分布恢复；
- [ ] 输入和输出 TPS 回到同时间段基线；
- [ ] 抽样核对下游记录及业务字段；
- [ ] 按恢复点计算重放或缺口窗口；
- [ ] 验证 Sink 的事务、幂等或去重结果；
- [ ] 确认外部依赖没有继续报错。

“任务 RUNNING”和“TPS > 0”都是必要信号，但不是数据正确的充分条件。

## 升级机制

升级条件应量化并写入值班规范：

| 条件 | 动作 |
| --- | --- |
| 到达 RTO 仍未通过快速验证 | 通知二线 Oncall 和业务负责人 |
| 默认与备用预案都失败 | 扩大到任务 Owner、平台负责人和依赖 Owner |
| 发现数据丢失、重复或外部副作用风险 | 立即通知业务方，不等任务恢复 |
| 操作需要突破资源或权限上限 | 启用审计过的紧急授权或升级审批 |
| 故障持续超过降级阈值 | 执行业务降级、切流或停写方案 |

通知模板至少包含任务、告警时间、当前状态、已执行动作、数据风险、所需支持和 Oncall 联系方式。

## 权限设计

故障期间临时等待普通审批会拖慢恢复，但“零审批”不应等同于无限权限。更稳妥的设计是：

- Oncall 预先获得限定任务和限定操作的权限；
- 高风险动作使用 Break-glass 紧急授权；
- 所有停止、回滚、扩容和配置变更保留审计记录；
- 每季度复核人员、任务范围和权限；
- 离岗或轮值变化时及时回收权限。

## 故障记录与复盘

恢复后记录：

```text
任务与业务：
告警时间 / 响应时间 / 恢复时间：
是否满足 RTO：
执行的预案及每一步结果：
使用的 Checkpoint / Savepoint：
重放或缺口时间窗口：
数据影响：
临时恢复措施：
根因：
改进项、负责人、截止时间：
```

出现以下任一情况应复盘：未满足 RTO、发生数据问题、预案执行失败、同类故障重复出现、人工操作扩大影响。复盘不只写根因，还要检查告警为什么没有更早发现、预案为什么未覆盖，以及改进项是否真正更新到监控、平台和 SOP。

## 日常保障检查

- [ ] P0 定级有业务影响和可量化 SLA，不按主观重要程度决定；
- [ ] 告警能在规定时间触达当前 Oncall；
- [ ] Checkpoint 间隔、超时和并发参数经过状态规模与存储压测；
- [ ] 已记录正常 Checkpoint 时长、大小和恢复基线；
- [ ] Source Offset、Sink 事务和幂等边界有文档；
- [ ] 默认、备用和降级预案均绑定到任务；
- [ ] Oncall 权限可用且操作可审计；
- [ ] 每月或重大变更后执行演练；
- [ ] 演练包含 Checkpoint 损坏、外部依赖异常和数据重放核查；
- [ ] 复盘改进项有负责人和截止日期。
