# Doris 精讲（十一）：沿执行计划与 Profile 定位查询瓶颈

一条订单报表按日期取某个用户的已支付订单，关联用户表，按城市汇总。慢在读取了过多数据、Join 前的数据交换，还是汇总结果返回？这需要把执行计划和同一次 SQL 的 Query Profile 对齐。

```sql
EXPLAIN
SELECT u.city, SUM(o.amount) AS paid_amount
FROM t_order AS o
JOIN user_profile AS u ON o.user_id = u.user_id
WHERE o.dt = '2026-05-15'
  AND o.user_id = 42
  AND o.status = 'PAID'
GROUP BY u.city;
```

假定 `t_order` 有按日分区及按 `user_id` 的 Hash 分布，包含日期、用户、状态和金额。此处使用独立报表示例的表结构。若表保存的是多条订单状态事件，汇总前必须确认 `PAID` 记录的业务粒度和是否重复。见 [[01-Doris 精讲（一）：订单明细、当前状态与汇总表怎么选|订单明细、当前状态与汇总表怎么选]]。

## 一、从计划看扫描范围，再到 Profile 查实际花费

先检查日期谓词是否把候选范围缩到 5 月 15 日。分区裁剪成功后，再看 `user_id = 42` 能否裁剪到当天相应桶。若 Hash 分布改为 `(user_id, order_id)`，只有 `user_id` 的等值条件通常不足以确定一个桶。更多 Bucket 也不会直接增加本次查询的有效并行度。

进入候选 Tablet 后，仍要过滤 `status = 'PAID'`，读取用于连接与汇总的列。此处可检查排序、索引与谓词是否匹配。

| 能力 | 在报表中减少的工作 | 需要观察的条件 |
| --- | --- | --- |
| 前缀索引 | 按前导排序列限制候选范围 | 过滤与排序前缀是否匹配 |
| BloomFilter | 跳过确定没有目标值的数据页 | 支持的等值或 IN 谓词，目标值是否集中在少量页 |
| 倒排索引 | 根据匹配值或词项定位候选行 | 类型、谓词下推与分词是否匹配 |
| 历史 Bitmap 索引 | 辅助低基数等值过滤 | 版本支持及与倒排索引的替代关系 |

如果每个数据页都有 `PAID`，普通 BloomFilter 几乎无法排掉任何页。高基数等值过滤通常更有机会跳过页，但仍可能误判，保留的页要继续检查。普通 BloomFilter 也不用于范围过滤。倒排索引可以服务数值和日期等过滤，也能匹配文本，某列建了倒排索引不代表所有 `LIKE` 写法都可使用。Bitmap 索引用于过滤，`BITMAP` 类型和 `BITMAP_UNION` 用于表达集合及精确去重，按 `COUNT(DISTINCT)` 选型时不能混用两者。

审查计划上的分区、Tablet 与谓词，再看 Profile 中实际扫描量、过滤贡献及实例长尾。索引增加构建、存储和后台维护成本，需要把减少的扫描与新增维护量一起衡量。

## 二、把 Join 重分布与聚合成本拆开

如果 Profile 的主要花费在 Exchange 或 Hash Join，先看两侧**过滤后**的大小、基数估计、内存与分布。小表 Broadcast 会把构建侧复制到多个执行节点，可以减少另一侧为这次 Join 重分布的成本。若用户表较大且两表已兼容分桶，可以检查 Join 是否用了 Colocation。

共位需要组 Schema、位置稳定和对应分桶列的等值关系同时满足。检查 Hash Join 的 `colocate: true`，并区分具体 Join 的 Exchange 与后续城市聚合的 Exchange。即使 Join 已共位，按城市汇总仍可能交换数据。Hash Key 倾斜造成的实例长尾也要单独看。见 [[09-Doris 精讲（九）：从两张表的桶布局推导 Colocation Join|从两张表的桶布局推导 Colocation Join]]、[[07-Doris 精讲（七）：Tablet 热点如何形成，怎样定位和缓解|Tablet 热点如何形成，怎样定位和缓解]]。

如果相同的报表反复计算，且业务允许复用结果，可以考虑物化视图。同步物化视图随基表写入维护，主要服务受支持的单表投影、排序和聚合，会增加写入维护。多表 Join 后按城市汇总的模式可评估异步物化视图。异步视图需要检查刷新是否成功、与基表分区的映射、查询能否透明改写，以及业务接受的数据时效。分区增量刷新是重算受影响分区，逐行增量维护属于另一个能力范围。物化视图将一部分查询工作转移到写入或刷新。

## 三、区分引擎执行完成与客户端取完结果

这个按城市汇总的例子返回行数通常较少。如果改为大批量导出订单明细，客户端取数、网络和解析就可能成为主要花费。Arrow Flight SQL 可以减少结果链路中的格式转换与序列化成本。扫描、Join、聚合与结果输出可能重叠，不能简单累加各算子时间，也不能以结果协议改变推断前面的扫描量下降。

JDBC 是接口。`jdbc:mysql` 与 `jdbc:arrow-flight-sql` 可以走不同协议，Flight JDBC 仍可能以行式 `ResultSet` 返回数据。ADBC 是否直取 Arrow 列批取决于驱动版本和路径，是否发生额外转换要按实际客户端检查。

## 四、复验时比较同一种证据

比较前后使用语义相同的 SQL 和相同扫描范围，记录数据规模、并发、缓存与计算资源。针对减少扫描，看保留范围和实际读取量。针对 Join，查看交换量、分布策略与实例长尾。针对物化视图，检查改写与刷新状态。针对传输，分开记录引擎执行与客户端消费。各实例的平均值、最大值和总量回答不同问题。

涉及表模型、NULL、盐值和聚合粒度的变更，还要检查重复、覆盖、空值和汇总结果。Doris 与 Spark 都可以沿扫描、Shuffle 和内存观察瓶颈。Doris 的 Bucket 属于长期存储布局，运行期任务并行属于执行策略，两者需要按不同证据调整。
