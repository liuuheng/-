# Doris 精讲（十二）：共享 UDF Jar 如何引发校验失败

两个 Java UDF 共用一个 Jar 下载地址。只发布其中一个函数后，新执行节点可能报另一个函数校验失败。这里以 StarRocks 为例推演函数定义、Jar 内容和执行节点缓存如何产生差异。Doris 的函数属性与部署流程应按相应版本区分。

## 一、更新一个函数，为什么另一个函数会失败

假设同一地址原来返回 Jar v1，FE 为 UDF-A 和 UDF-B 的定义记录的 checksum 都是 C1。发布时在原地址覆盖 Jar v2，随后只重建 UDF-A。

| 状态 | 同一地址返回 | UDF-A 记录的 checksum | UDF-B 记录的 checksum |
| --- | --- | --- | --- |
| 发布前 | v1，C1 | C1 | C1 |
| 覆盖 Jar 后 | v2，C2 | C1 | C1 |
| 重建 UDF-A 后 | v2，C2 | C2 | C1 |

StarRocks 的 FE 校验 Jar 并计算 checksum，执行节点下载 Jar 执行。此时如果新 CN 下载到 v2 并按 UDF-B 的定义校验，就可能出现期望 C1、实际 C2 的错误。先前的节点若继续命中 v1 缓存，问题可能在新节点或缓存未命中时才显现。部分节点成功只能说明该节点走通了自己的执行路径。

## 二、让函数定义与对应 Jar 一起发布

将 v2 发布到新的不可变路径，重建 UDF-A 后让它引用 v2。UDF-B 继续引用 v1，旧定义和旧文件仍然匹配。要能回滚，需保留各函数的签名、Jar 版本和 checksum 对应关系。

多个函数可以共享一个不可变版本的 Jar。函数需要独立升级时，分包可以减少共同变更的范围，但也会增加包数量和依赖维护。若覆盖已经发生，应优先判断能否恢复旧路径的旧文件。只有确定所有引用方都要一起升级且确认兼容，才适合重建全部引用该地址的函数。

## 三、把校验不一致与下载失败分开

排查时比对 UDF-A 与 UDF-B 的函数定义、参数签名、记录的 checksum、执行节点实际下载文件的校验值和错误日志。若同地址返回的文件与记录值不同，才能支持内容变化的解释。若节点根本没有下载到文件，或下载后类与依赖无法加载，则依据日志分别追踪访问和依赖问题。
