# Doris 精讲（三）：从订单分布反推分桶键与桶数

订单明细表按天分区。假设一天约产生 256 GB 单副本压缩数据，查询经常按用户过滤或关联用户表。这时需要回答两个不同的问题：哪些记录应进入同一个 Tablet，以及这一天需要多少个 Tablet。

## 一、先用订单分布检验分桶键

同一分区里，相同 Hash 分桶列值会路由到同一个桶。候选列的去重值数量称为基数。高基数只说明不同值多，无法说明每个值的数据量都接近。

| 候选分桶列 | 写入后数据怎样分布 | 查询时要付出的代价 |
| --- | --- | --- |
| `province` | 不同省份有限，一个省内的订单聚在同一桶 | 容易使部分桶较大，许多桶无法充分利用 |
| `user_id` | 多个用户有机会分布到多个桶，单个热点用户仍在同一个桶 | 等值过滤或按用户 Join 可利用分布，仍需查看头部用户占比 |
| `user_id, order_id` | 同一用户的不同订单有机会落到多个桶 | 只按用户过滤通常不能唯一定位桶，按用户 Join 也不能直接凭该列保证共位 |

Duplicate 表可以从 Key 或 Value 列选分桶列。Unique 和 Aggregate 表的分桶列必须属于 Key 列，以保证同 Key 的记录能按模型处理。若明细只追加、服务的谓词和 Join 没有稳定分布键，则可评估 Random。Doris 4.x 的 Random 分桶适用于 Duplicate 模型，不能按 Hash 值做桶裁剪。

### 分桶列的类型限制

`BIGINT`、`LARGEINT` 是整数，`INT` 和 `VARCHAR` 也有 Hash 分桶用法。SQL 类型 `STRING` 是 Value 列类型，不能作为 Key、分区列或分桶列。业务字段说成“字符串”时，需要区分 `CHAR`、`VARCHAR`、`STRING`。其他类型的可用性还受目标版本和表模型约束。

`DECIMAL(p, s)` 是精确定点数，`p` 是总精度，`s` 是小数位数。日期和日期时间需要区分精度。`DATE` 表示 `2026-05-13`，`DATETIME`、`DATETIME(3)`、`DATETIME(6)` 分别可表达 `2026-05-13 15:30:45`、`2026-05-13 15:30:45.123`、`2026-05-13 15:30:45.123456`。历史资料可能使用 `DATETIMEV2`、`DATETIMEV2(3)`、`DATETIMEV2(6)`，需按目标版本检查解析。能表示某个值与能作分桶列是不同条件。

## 二、从单分区大小计算起步桶数

假设目标是每个 Tablet 约 8 GB，先用 256 GB ÷ 8 GB 得到 32 桶。若同时有三份副本，应按同一份逻辑数据的压缩体积估算，即使三份数据共占约 768 GB，也不会由此把桶数推到 96。估算时还要统一是否包含索引的大小口径。

这项估算假设数据分布均匀。如果用户 42 一个人就产生 64 GB，`HASH(user_id)` 会将这些记录交给同一个 Tablet。桶数即使翻倍，该用户在当天仍只落到一个桶。应查看最大的 Tablet、头部用户频率、节点和磁盘分布。一般可将 1～10 GB 用作试算尺度。Doris 4.x 的容量规划建议通常是每 Tablet 1～20 GB 压缩数据，Unique Key 建议不超过 10 GB。高压缩率也不能消除 MOW 物理行数多和 Compaction 内存压力。具体表现见 [[07-Doris 精讲（七）：Tablet 热点如何形成，怎样定位和缓解|Tablet 热点如何形成，怎样定位和缓解]]。

`BE 节点数 × 2～4` 可以作为另一个粗估，但分区大小、增长速度、并发和磁盘数都可能使该估计失效。过少的桶会限制分布和恢复粒度，过多的桶会增加 FE 目录、调度和后台合并成本。若每天 32 桶，保留 30 天，基表共有约 960 个逻辑 Tablet，三副本约 2,880 份物理副本。同步物化视图／Rollup 对应物化索引另算，BloomFilter、倒排索引不会为每个索引各建一套 Tablet，异步物化视图是独立表。

## 三、区分自动算桶数与变更已有布局

`BUCKETS AUTO` 决定新建分区的桶数，Random 决定记录怎样选择桶。自动算桶数不会将已存在的热点 Tablet 拆开。日后如果要增大桶数，先分清要改变的是未来分区，还是要重写历史布局。见 [[04-Doris 精讲（四）：已有分区、新分区与副本的变更边界|已有分区、新分区与副本的变更边界]]。
