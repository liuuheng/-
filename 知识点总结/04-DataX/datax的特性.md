
简单总结：**DataX 全量同步不是 CDC，它是用 SQL 去扫业务表，所以同步期间业务表变化会带来不一致风险。**

主要情况：

| 业务表变化 | DataX 同步结果 |
|---|---|
| 新增 insert | 如果 DataX 还没扫到，可能同步进去；如果已经扫过，就同步不到 |
| 修改 update | 如果修改前被读到，目标端是旧值；如果修改后才读到，目标端是新值 |
| 删除 delete | 如果删除前已被读到，目标端仍有；如果删除后才读取，目标端没有 |

所以最终结果可能是：

```text
不是 0 点快照
也不是任务结束时快照
而是同步过程中的混合状态
```

另外还会有这些问题：

1. **影响线上库性能**
   DataX 会执行大量 `SELECT`，可能占用 CPU、磁盘 IO、网络、连接数、缓存。

2. **大表同步时间长**
   比如你 240G 跑 11 小时，期间业务变化越多，快照不一致风险越高。

3. **并发越高，压力越大**
   `channel` 开高后速度会变快，但对源库读压力也更大。

4. **没有合理切分会很慢**
   如果没有 `splitPk`，或者切分字段没有索引，可能导致大范围全表扫描。

5. **无法天然处理删除**
   DataX 每天增量同步时，如果只按 `update_time` 拉数据，物理删除的数据很难同步到数仓。

6. **不是严格事务快照**
   多通道、多连接读取时，各个分片可能看到不同时间点的数据。

7. **失败重跑成本高**
   大表同步中途失败，可能要重跑整张表或某些分片，耗时较长。

一句话概括：

> **DataX 适合批量全量搬数据，但同步期间业务表还在变化时，结果可能不完全一致；表越大、同步越久、业务变化越频繁，问题越明显。**
