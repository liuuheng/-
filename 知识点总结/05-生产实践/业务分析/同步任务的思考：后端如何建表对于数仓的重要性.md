
背景：最近反复观察来ods的表结构 发现一个比较有意思的情况
每张表中都会有

```sql
`created` timestamp comment '创建时间',
`lastmodified` timestamp comment '最后修改时间',
`deleted` boolean comment '删除标志，0表示未删除，1表示已删除'
```

经了解，相关字段主要用于后端审计，用于记录数据在何时发生变更、变更了哪些字段。后端同学反馈，该要求属于硬性规范，但在实际业务中使用频率较低。

但从数仓角度来看，这几个字段在数据同步过程中较为重要。根据业务表建表规范，所有核心表都应包含此类字段。对于数仓而言，核心价值在于使用 DataX 进行数据同步时，可基于 `lastmodified` 等字段实现增量更新。

由于 DataX 本质上是通过 SQL 查询进行数据同步，因此查询条件会直接影响同步效率。例如，若需增量同步 3 号的数据，可使用如下条件：

```sql
lastmodified >= '3号' AND lastmodified < '4号'
```


在同一个 MySQL 实例、同一个主键范围内，使用 `binlog_file + binlog_pos + binlog_row` 判断事件先后顺序是比较合适的方式。

在 Flink CDC 同步数据时，也建议基于这三个字段判断事件顺序。虽然 binlog 本身是有序的，Flink 在读取时通常也是按顺序消费，但在需要显式判断同一主键下多次变更的先后关系时，使用 binlog 位点信息会更加准确。

具体字段含义如下：

`binlog_file = source.file`  
例如：`mysql-bin.000123`      判断的时候需要提取 后缀 000123
表示该条变更所在的 binlog 文件。

`binlog_pos = source.pos`  
例如：`457020`  
表示该条变更在 binlog 文件中的位置。

`binlog_row = source.row`  
例如：`0、1、2`  
表示同一个 binlog event 中的第几行变更。由于一条 SQL 可能影响多行数据，因此需要通过 `row` 区分同一 event 内多行变更的顺序。

判断标准：
binlog_file -> binlog_pos -> binlog_row
谁更大，谁就更新。
不过建议更严谨一点：不要直接按 binlog_file 字符串排序，而是把文件编号取出来排序。
binlog 顺序就是按文件编号、文件内位置、event 内行号依次比较；取最新就按这三个字段倒序排。

即使业务表中已经有 `created`、`lastmodified`、`deleted` 等字段，这些字段的时间粒度也可能不够细。在同一时间点发生多次更新时，仅依赖这些业务时间字段，可能无法准确判断事件的先后顺序。

如果你的`lastmodified` 是秒级别 ，那一秒内可能会修改多次，无法判断先后。


Q1:FlinkCDC同步时：会将所有的字段都同步过来吗  还是仅仅是变更的字段
A1:这取决于 MySQL 的 binlog_row_image 配置，以及 CDC 处理方式。
如果是 binlog_row_image=FULL
通常会拿到完整行数据。
所以做 CDC 同步快照，强烈建议：
binlog_format=ROW
binlog_row_image=FULL

Q2:flinkCDC实际同步的情况是什么样的
A2:
binlog_file -> binlog_pos -> binlog_row
这个是mysql的binlog 可以获取到的

但是flinkCDC中没有这个数据 只有 ts_ms​  但问AI还是 说 会有重复的情况
所以最好的 还是使用下面的 字段：
`created` timestamp comment '创建时间',
`lastmodified` timestamp comment '最后修改时间',
`deleted` boolean comment '删除标志，0表示未删除，1表示已删除'

Q3: `lastmodified `如何更精确
A3:
`lastmodified` 的精度 如果是秒级别的 那会有 `lastmodified` 相同 但是会有两条变更记录
一般现在是 毫秒级别 三个 0 

微秒级 timestamp(6) 风险最低，但仍不是绝对顺序；真正不会被时间精度影响的，是 binlog 位点或业务生成的单调版本号。
