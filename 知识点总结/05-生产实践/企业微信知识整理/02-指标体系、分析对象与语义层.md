# 指标体系、分析对象与语义层

返回：[[README|企业微信知识地图]]

## 1. 指标定义必须先于 SQL 实现

“看一下 KA 客户最近的转化效果”不是可直接开发的指标需求，因为至少缺少：

1. 转化起点和终点：注册到付费，还是创建方案到完成渲染？
2. 统计主体：企业、用户、方案还是订单？
3. 时间锚点：按起点时间入组，还是要求起点终点都在统计期？
4. 观察窗口：注册后 7 天、30 天还是不限期？
5. 存量范围：只看新进入的 KA，还是统计期内所有 KA？

只有这些条件明确，SQL 中的分母、分子和时间过滤才有唯一含义。

## 2. 为什么统计对象会改变结论

假设一个用户创建了 100 个方案，其中只有 1 个方案完成渲染：

- 按用户统计，只要用户至少有一个方案渲染，就会得到 1/1=100%。
- 按方案统计，转化率是 1/100=1%。

两者都可能计算正确，但回答的是不同问题。用户是行为发起者，方案是价值承载体。看到漏斗需求时，应先问行为发生在哪个对象上，以及用户与对象是否一对多。若一对多，就必须评估对象级漏斗。

## 3. 原子度量、原子指标、派生指标和衍生指标

这些术语在不同公司并不完全一致，关键是内部定义稳定：

- 原子度量是事实行上的可计算值，例如一次支付的 `pay_amount`。
- 原子指标是固定粒度和限定条件下最小可复用统计，例如“支付成功金额”“发起渲染任务数”。
- 派生指标由原子指标按稳定业务规则组合，例如支付转化率 = 支付用户数 / 注册用户数。
- 衍生指标是在已有指标上增加时间窗口、分群或比较方式，例如近 30 天支付金额环比。

比例和均值通常不可直接再次平均。若门店 A 转化率为 1/2，门店 B 为 90/100，直接平均得到 70%，实际总体是 91/102≈89.2%。因此 DWS 应保留分子和分母，查询时重算，而不是只保存比例。

## 4. 指标条件应结构化

一个指标至少要记录：

- 指标名称和唯一编码。
- 统计主体与粒度。
- 度量表达式。
- 过滤条件。
- 时间字段和统计周期。
- 去重键。
- 维度适用范围。
- 数据来源与血缘。
- 负责人、版本、生效时间和质量规则。

例如“渲染成功率”必须说明分母是按钮点击、任务发起数还是去重后的方案数；失败是否包含超时；同一任务重试是否只计一次。

## 5. DWD、DWS、ADS 中的口径

- DWD 固化行为与状态语义，例如 `is_render_action` 的判断不能由每个下游用 `LIKE '%render%'` 自行猜测。
- DWS 固化公共统计规则和原子指标，例如某粒度下的渲染任务数、成功任务数。
- ADS 组合最终业务口径，例如某客户采用成功图数大于 10 作为有效方案阈值。

这样分层的原因是变化频率不同：源字段解释应稳定，公共指标需要治理，最终场景阈值可能经常调整。

## 6. 宽表与自助分析

宽表的目标是减少分析者重复 join 的成本。它可以包含常用维度、多个基础指标和统一时间字段，但一张宽表最好服务一个稳定统计主体。例如用户宽表不应同时混入订单行粒度和方案粒度明细，否则维度下钻时会重复计数。

分析场景可分为：

1. 方法固定，直接交付报表。
2. 方法灵活但在现有数据框架内，提供宽表或语义层自助分析。
3. 方法和数据范围都不稳定，先通过探索分析验证，成熟后再产品化。

不是所有临时需求都要立刻建设成指标平台。只有重复出现、口径可稳定、用户能理解配置含义的分析模式，才适合产品化。

## 7. Model、Metric、Question、Dashboard

语义层可将 SQL 拆成可治理部件：

- Model 定义数据骨架：主表、维表、join 条件和可用字段。
- Metric 定义聚合表达式、过滤条件和适用粒度。
- Question 选择 Model、维度、Metric 和额外过滤，生成一次查询。
- Dashboard 组合多个 Question，本身不直接定义底层 join。

语义层的价值不是让 AI 猜 SQL，而是把业务知识转成确定配置。如果模型把用户表和订单表的关系定义错了，任何上层问题都会系统性出错，因此整个体系的核心是高质量 Model 与 Metric。

## 8. NL → DSL → SQL 为什么比直接 Text2SQL 稳定

直接 Text2SQL 让模型同时理解业务、选择表、决定 join、生成方言 SQL 和保证安全，错误面很大。混合架构让模型先生成受约束 DSL：

```json
{
  "model": "order_analysis",
  "metrics": ["paid_amount"],
  "dimensions": ["country"],
  "filters": [{"field": "paid_date", "op": "between", "value": ["2026-07-01", "2026-07-31"]}]
}
```

确定性程序再验证字段权限、口径和过滤范围，并生成 SQL。这样可以拒绝越权字段、限制全表扫描，也便于审计。复杂的探索性 SQL 仍可能需要 Text2SQL 或工程师编写，语义层主要覆盖常规指标查询。

## 9. 高价值客户与活跃度的拆解示例

“看高价值客户活跃度变化”应拆成：

- 高价值客户如何识别：人工标签、历史累计付费，还是近 30 天付费？
- 标签是静态还是随时间变化？分析历史时使用当时标签还是今天标签？
- 主体是企业还是用户？
- 活跃度是登录天数、行为次数、使用时长还是项目创建数？
- 变化是日环比、月同比还是前后 30 天对比？

一个可实现定义示例：以企业为主体，将每个月末过去 90 天付费金额超过 10 万的企业定义为高价值企业，统计其当月有渲染行为的天数，并与上月比较。该定义明确了主体、标签窗口、行为、时间锚点和比较方式。

## 10. 指标治理的两种落地方式

一种是“指标文档”：平台保存定义、责任人和血缘，工程师据此开发任务。另一种是“定义即生产”：配置指标后平台自动生成 SQL 和调度。后者自动化程度高，但只有在模型、语法、调度、补数、权限和质量规则都标准化后才可靠。

如果平台无法生成复杂离线任务，不应假装已实现定义即生产。可以先把指标 ID、口径和血缘治理起来，再逐步扩大自动生产覆盖面。
