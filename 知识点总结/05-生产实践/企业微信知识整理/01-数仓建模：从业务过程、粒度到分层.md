# 数仓建模：从业务过程、粒度到分层

返回：[[README|企业微信知识地图]]

## 1. 建模的起点不是表，而是业务过程

业务过程是为了完成一个业务目标而发生的一组可识别活动，例如注册、下单、支付、退款、创建方案、发起渲染和完成审核。建模前先识别业务过程，是因为源系统里的表通常是按照应用开发和事务处理设计的，并不天然等于分析模型。

例如前端埋点表中可能同时出现 `click_render`、`submit_render` 和 `render_success`。不能因为 action 名不同就立即拆成三张事实表，也不能因为它们都在一张日志表里就永远放在一起。应判断：

- “点击渲染按钮”是一次瞬时行为，没有独立生命周期，适合留在用户行为事实中。
- “渲染任务”如果有 `render_id`、创建时间、执行状态、失败原因和完成时间，它已经是一个独立业务实体，应从后端渲染任务表建设业务事实。
- 埋点可以用于路径和漏斗分析，但可能丢失、乱序或被拦截；涉及收入、库存、审核状态等正式口径时，应以后端业务表为事实来源。

因此，决定是否拆事实表的依据是“是否形成独立业务过程”，而不是 action 是否不同。

## 2. 粒度：一行数据究竟代表什么

粒度必须在选字段之前声明。一个合格的粒度描述应包含统计主体、业务动作和必要的时间层级，例如：

- 一行代表“一次权限权益消耗流水记录”。
- 一行代表“一个方案在一天内、某种渲染类型和分辨率下的渲染统计”。
- 一行代表“一个账户在某天结束时的会员状态快照”。

为什么粒度如此重要？因为聚合错误通常不是 SUM 写错，而是同一张表混入了不同粒度。例如订单表一行是订单，订单商品表一行是订单项。如果直接按 `order_id` 连接后求订单金额，订单金额会被商品项数量重复放大。正确做法是先明确最终粒度，再决定是否预聚合订单项或使用不会重复的度量。

判断字段角色时，不要只看字段名，要看它在当前粒度下的作用：

- 能在当前粒度上被计数或求和的值是度量，例如订单项粒度的 `item_amount`。
- 用来描述上下文或分组的字段是维度属性，例如渠道、地区、产品类型。
- 同一个概念换到另一模型可以扮演不同角色，但在同一模型内角色应稳定。比如“账户数”在账户明细中不是字段度量，在日汇总表中可以是 `account_cnt`。

一句话记忆：**业务语义可以随场景变化，字段在当前模型中的角色不能混乱。**

## 3. 事实表的常见类型

### 3.1 事务事实表

一行记录一次最低粒度业务事件，例如一次支付、一次登录、一次权益消耗。它通常只追加，不覆盖历史，适合计算次数、金额和路径。

### 3.2 周期快照事实表

按固定周期记录实体当时状态，例如每日库存、每日账户余额、每日会员状态。余额和库存通常是半可加指标：可以跨商品或账户求和，但不能把每天的余额跨时间直接求和，否则会重复计算存量。

### 3.3 累积快照事实表

一行表示一个流程，并随着里程碑发生而更新，例如订单创建、支付、发货、签收分别填入不同日期列。它适合分析流程耗时，但更新方式和普通追加事实不同。

### 3.4 无度量事实表与关系事实表

有些事实表没有金额等数值，一行本身就代表事件或覆盖关系。例如“用户参加活动”“员工属于组织”。统计时使用 `COUNT(*)`。聊天记录中提到的“关系型事实”可归入这一类，但仍要声明关系生效时间，否则组织变更后无法还原历史。

### 3.5 状态变更日志

记录 `old_status`、`new_status`、`change_time`，适合分析状态流转和首次到达某状态的时间。只有当前最新状态的接口无法还原历史首次提审时间，这正说明：如果分析需要历史过程，源系统必须提供变更日志、CDC 或审计表，不能等数据丢失后依赖当前快照推导。

## 4. 业务实体、行为与日志事实

业务实体通常具备唯一 ID、生命周期、状态变化和被多次引用的能力，例如订单、方案、渲染任务和用户账号。行为则是点击、浏览、提交等瞬时动作。

DWD 对两类数据的处理重点不同：

- 行为日志需要做行为语义抽象。比如保留原始 `core_action`，同时生成稳定的 `action_type`、`action_sub_type` 和 `event_result`。
- 业务事实需要做生命周期状态抽象。比如将源系统的“失败、超时、系统取消”映射为统一的 `is_failed` 或标准状态组。

这样做的原因是，如果 DWD 不统一语义，每张 DWS 或 ADS 都会各写一套 CASE WHEN。规则变更时需要修改十几处，最终出现同名指标不同口径。DWD 应保留原字段以便追溯，同时提供标准化字段供下游优先使用。

当规则越来越复杂、需要版本管理或按时间生效时，不应继续堆叠 CASE WHEN，应建设映射维表，例如：

```text
source_action | standard_action | effective_from | effective_to | rule_version
```

事实按事件时间关联当时有效的规则版本，从而避免用今天的分类方式重写历史。

## 5. DWD 与 DWS 的真正边界

用“是否 GROUP BY”区分 DWD 和 DWS并不准确：

- DWD 面向业务事实，强调原子粒度、真实发生和可追溯。
- DWS 面向分析对象或分析主题，开始为了复用和分析效率组织结构。

DWS 可以是轻度聚合表，也可以是不聚合的宽明细表。例如将用户、组织、行业和会员信息冗余到“用户日行为宽表”，虽然仍是明细，但它已经围绕分析场景组织，因此更接近服务层。

判断问题可以写成：

> 这张表主要为了描述业务发生，还是为了让分析者更容易统计？

如果是前者，倾向 DWD；如果已经围绕分析对象打宽、预计算或统一跨过程指标，倾向 DWS。

## 6. ODS、DWD、DWS、ADS 的职责

### ODS：保真与可重放

ODS 以源系统为主，尽量保留原字段、原值和同步元数据。它的价值是审计和重放，而不是直接承载稳定指标。若源数据已经足够清晰、需求一次性且风险低，可以直接从 ODS 交付，但必须承认这是成本权衡，而不是完整建模。

### DWD：清洗后的原子事实

DWD 完成去重、类型统一、时间标准化、枚举映射、主键确认和业务语义固化，同时保留足够原始信息用于追溯。不应把具体报表的阈值写死在 DWD。

### DWS：公共分析能力

DWS 围绕主题和分析对象沉淀公共汇总、宽表和原子指标。它可以包含维度冗余、分组字段和派生字段，但应保持固定粒度和可复用性。

例如客户 A 认为“有效方案”是渲染数大于 10，客户 B 认为大于 20。DWS 不应直接生成唯一的 `valid_design_cnt`，而应提供：

```text
user_id, design_id, render_type, resolution, render_cnt
```

ADS 再按客户口径筛选和计数。这样改变阈值时不必重建底层。

### ADS：面向最终消费

ADS 服务具体看板、接口、页面、名单或导出任务，可以贴近展示字段和最终筛选逻辑。ADS 复用性较弱，因此公共口径不能只存在于某个 ADS 的 SQL 中。

## 7. 数据域、主题域与分层不是同一个维度

数据域是生产与治理边界，例如用户域、交易域、方案域和财务域。主题域是在数据域内围绕一组相近业务过程或分析问题继续组织，例如用户域下的注册登录、用户状态和用户画像。

可使用以下工程映射，但不要当成绝对理论：

```text
数据域 1 → N 主题域
主题域 1 → N 业务过程
业务过程 1 → N 物理模型或任务
```

ODS/DWD/DWS/ADS 是加工阶段；数据域/主题域是资产归属。它们可以交叉，不能简单说“DWD 就是数据域、ADS 就是主题域”。

## 8. 维度模型的关键补充

维表描述业务上下文，事实表保存事件或度量。成熟模型通常保留业务自然键，并使用代理键关联事实：

- Type 1 缓慢变化维直接覆盖旧值，不保留历史，适合纠错类属性。
- Type 2 每次变化新增一条版本，包含生效开始、结束和当前标记；事实按事件时间关联当时版本。
- Type 3 仅保留有限的前值，适合少量需要新旧对比的属性。

并非所有字段都要做 SCD2，因为版本越多，存储、关联和治理成本越高。只有历史分析确实需要“当时属性”的字段才值得保留版本。

未知维度成员也不应简单丢弃。事实到达时维度尚未到达，可以使用统一的 unknown 代理键，后续再修正，否则 inner join 会让事实无声丢失。

## 9. 建模检查清单

- 是否先写出完整粒度，而不是只列主键？
- 数据来自行为埋点还是后端业务实体？哪个才是系统事实来源？
- 是否混入不同粒度，导致 join 后金额或次数被放大？
- 度量是可加、半可加还是不可加？比例是否保留了分子和分母？
- DWD 是否保留原字段并提供统一语义字段？
- DWS 是否保持分析对象和粒度稳定，而不是为每个报表无限加字段？
- ADS 是否只做场景组装，没有私自重写公共指标？
- 组织、客户等级等变化属性是否需要按历史时点还原？
- 表的更新方式是追加、覆盖、快照还是拉链？
