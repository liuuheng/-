# 真实案例：淘宝怎么用"大模型裁判"给 Agent 做日级评测

> Source: wechat
> Author: AI测试加
> Original: https://mp.weixin.qq.com/s/U_dt7UQcMVAQN9RywGdFpw

---

前几篇讲了 Agent 怎么测的概念、框架和清单。这篇看一个真实的大厂案例：淘宝给 AI 购物助手搭的**日级在线评测体系**。方案本身很硬核，我按自己的理解重新讲一遍，最后说说哪些思路咱们可以直接用。

---

## 一、先搞清楚：Agent 评测难在哪

传统测试的逻辑很简单：输入固定、预期固定、结果跟预期一致就通过。Agent 不适用这套——同样一句话，它背后是一条完整的决策链路：

**听懂意图 → 决定交给哪个业务模块 → 调用工具/接口 → 拿回数据 → 组织回复**

这条链路上任何一环出错，最后可能都是同一句"错误的回答"，但病因完全不同。比如：用户想查物流，意思理解错了，被当成退款问题处理；或者模块选对了，订单号传错了；再或者工具返回了物流状态，模型却自己编了一个送达时间。

> [!note]- 批注｜用同一条物流请求区分失败环节
> 同一句“我的快递到哪了”可以产生三种可区分的错误。调了退款模块，核对路由决策。调了物流模块却传错订单号，核对会话里选中的订单和请求实参。查到了正确订单却写了无证据的送达时间，对照工具返回和用户可见回复。三类错误都可能表现为同一个错误回答。

两个现实问题，传统手段都解决不了：

**离线用例覆盖不了真实用户。** 测试集里的问题规范、意图清晰、工具返回可控——线上用户会连珠炮追问、突然改主意、说话前言不搭后语，接口还会超时、缺字段。离线全绿，不代表线上跑得通。

**业务指标定位不到技术故障。** 转化率、好评率只能告诉你"整体效果在掉"，说不清是意图识别坏了，还是工具参数传错了，还是回复编造了事实。真查起来只能一头扎进日志里捞。

所以淘宝在购后场景搭了一套在线评测：每天自动把真实生产会话拉出来，清洗后交给一个大模型当裁判打分，再聚合成质量指标。**把"抽查"变成"每天自动跑的流水线"。**

> [!note]- 批注｜日级评测看的是哪一天的流量
> 这里的“在线”指样本来自生产会话，文中描述的是按天加工和汇总。给样本记录会话所属业务日、评分运行批次和规则版本。迟到会话或重新评分的记录按会话业务日归集，方便找回原来的看板分区。

## 二、核心指标设计：把"成功"拆成两半

评测要先回答一个基础问题：**什么才算成功？**

答案没那么简单。用户问"我的快递到哪了"，如果后台确实没有物流记录，Agent 如实说"暂时查不到、建议这样操作"，这就算正确处理；反过来，没查到却编一个预计送达时间，哪怕回复很流畅，也是质量问题。

所以不能只看"最终答案好不好"，要看**过程对不对**。淘宝把成功拆成两个独立环节：

| 环节 | 判断什么 | 典型错误 |
| --- | --- | --- |
| 路由 | 有没有听懂意图、交给对的业务模块 | 物流问题被当成退款问题 |
| 回复 | 路由正确的前提下，回复是否依据真实结果 | 把"已受理"说成"已到账" |

指标公式（原文口径）：

**端到端成功率 = 路由正确率 × 回复正确率**

这里有个特别容易被忽略的细节：**回复正确率必须在"路由正确"的样本里算**，不能拿两个独立统计的百分比直接相乘。因为路由错了，后面生成得再好也不算数。这种"条件口径"的思路，值得所有做 Agent 评测的人记住。

> [!note]- 批注｜按同一批样本计算端到端成功率
> 补充示例。某日同一业务域有 100 条具备判定证据的样本，其中 80 条路由正确。80 条里有 72 条回复正确。路由正确率为 `80/100`，条件回复正确率为 `72/80`，相乘得到 `72/100 = 72%`。
>
> 若 `R` 表示路由正确、`A` 表示回复正确，联合成功概率为 `P(R ∩ A) = P(R) × P(A | R)`。原文的“独立环节”指分开验收。公式成立的依据是条件概率。若路由正确的样本中有一部分回复不可评，需要先约定纳入规则，再对齐两项指标用到的样本。若路由正确数为 0，条件回复正确率没有可用分母。

## 三、第一道坎：数据不洗干净，再强的裁判也白搭

很多团队上来就兴奋地研究"选哪个大模型当裁判""Prompt 怎么写"。但公开分享里反复强调的是：**最影响评测稳定性的，是喂给裁判的数据。**

生产日志有多乱？订单、物流、售后、知识问答各是一摊，接口字段、卡片协议都不一样；工具返回里还可能夹着内部系统提示词，Judge 会把这些内部文本当成"Agent 对用户说的话"，判成"输出了无关信息"——错的不是模型，是数据没洗干净。

> [!note]- 批注｜区分用户看见的话和内部取证材料
> 把用户可见的回复文本、渲染后的业务卡片、工具入参及返回值分开存。裁判要知道哪些字段是证据，哪些内容曾展示给用户。比如内部返回带了一段系统说明，但前端没有渲染它，这段文字就不计入用户可见的回复。

![「六层漏斗与数据清洗」配图](../../99-images/agent-evaluation-taobao-20261118/img_001.jpg)

淘宝的数据处理分了四步（我按自己的理解转述）：

1. **格式统一**

   ：不同业务模块的接口字段、返回结构五花八门，先统一成同一套解析结构
2. **语义对齐**

   ：用户嘴里的"已揽收"和系统里的状态是不是一回事，要建立映射，不能想当然
3. **噪声剔除**

   ：工具返回里夹带的内部 Prompt、系统注释、开发日志，全部清掉，只留有效参数和结果
4. **范围过滤**

   ：不属于当前业务域的请求，别让它混进评测样本

这里有两个坑，特别值得记下来。

**坑一：业务状态要做语义对齐。** 例子很直接——"已揽收"不等于"已签收"，"退款处理中"不等于"退款已到账"。Judge 如果只做文本相似度判断，很容易把"已受理"当成"已到账"。评测输入不能只给字段值，还得给背后的业务含义。

> [!note]- 批注｜用业务状态映射验收回复
> 补充示例。在售后状态字典里，“已受理”可以对应流程已接单。如果这条记录没有结算成功的状态或凭证，“款已到账”就缺少依据。给裁判提供原始状态、对应的业务释义和状态时间，可以核对回复是否跳到了证据尚未支持的流程阶段。

**坑二：无效样本会悄悄污染指标。** 用户在测"退款申请"模块时问"退款政策有哪些？"，这只是知识咨询，不是发起退款。这种样本算进退款流程的分母，Agent 不调退款工具就会被误判成"执行失败"。样本多了，通过率就是假的。

所以算任何通过率之前，先回答两个问题：**这条样本属于当前业务域吗？我们手里有足够证据评它吗？**

> [!note]- 批注｜把超范围、不可评和失败分开计数
> 补充示例。100 条会话中，20 条是其他业务域，10 条属于本域但缺证据。本域可评样本有 70 条，其中 63 条通过。本域可评样本通过率为 `63/70 = 90%`，本域可评覆盖率为 `70/80 = 87.5%`。同时看两项，可以发现证据缺失量上升、通过率仍然稳定的情况。

## 四、评分规则：分层门控，不是打一个总分

平台有了，接下来是更根本的问题：**不同业务按什么标准评分？**

物流看状态和时效真实性，退款看流程和参数合规，知识问答看规则正确性——一个通用模板套所有业务，结果看似统一、实际不可比。淘宝的做法是**统一上层框架 + 各业务独立判定**，一共六层（原文叫 CNT 六层漏斗，我按功能理解转述）：

| 层 | 环节 | 判断什么 |
| --- | --- | --- |
| 1 | 上下文门控 | 手里的证据够不够做可靠评测 |
| 2 | 越界处理 | 不属于本模块的请求，处理得是否合理 |
| 3 | 能力边界 | 超出能力范围时是否如实告知 |
| 4 | 工具链路 | 工具选得对不对、参数传得对不对、调用过程对不对 |
| 5 | 内容质量 | 回复是否正确、完整、符合业务要求 |
| 6 | 安全红线 | 有没有泄露隐私、违规引导、编造政策 |

![「大模型裁判看证据」配图](../../99-images/agent-evaluation-taobao-20261118/img_002.jpg)

这不是六个分数加权平均，而是一层层往下走的**门控体系**。三个设计亮点：

**一、证据不足，不强行判失败。** 裁判手里没有订单详情，就没法判断显示的金额对不对。这种样本正确做法是标记"不可评"、移出分母，而不是让模型瞎猜。

**二、前面失败就短路，但安全层永不跳过。** 第一层就判失败了，后面的工具链路、内容质量不用再评——省成本。但安全红线是例外：哪怕路由已经错了，也必须检查有没有泄露隐私、编造高风险政策。

**三、框架统一，规则各写各的。** 物流模块重点查"送达时间有没有被编造"，退款模块重点查"参数和操作是否合规"，知识问答重点查"规则记忆是否准确"。统一的是分层和数据口径，不是把每个业务压成同一套评分条件。

> [!note]- 批注｜门控结果怎样记录
> 补充示例。退款对话缺少订单详情时，金额检查记“不可评”。路由已判错而短路时，后续业务检查记“未执行”。已有订单详情且回复金额与详情冲突时，金额检查记“失败”。汇总时分别计数，便于追到缺证据、主动跳过和质量缺陷。
>
> 原文用“第一层就判失败”说明短路。可以将它落实为上下文门控未通过便停止常规评分，同时把该样本标为“不可评”。安全检查继续使用可用证据，例如检查用户可见回复是否暴露隐私。安全证据也缺失时，记录缺口供复核。

## 五、日级评测怎么扛住百万级会话

样本从几百条涨到真实生产会话，问题就从"怎么判断"变成了"**怎么调度、怎么控成本、怎么保证结果完整"**。

两个架构决策值得借鉴：

**数仓和推理平台分开。** 数仓管样本加工、字段关联、指标聚合；推理平台管组织 Prompt、调裁判模型、返回结构化评分。两边独立迭代：改评测标准动 Prompt 就行，字段出问题修 SQL 就行，互不拖累。

**按业务域拆独立工作流。** 所有业务共用一个大型工作流会互相拖累：最慢的业务拖垮整体、一个失败影响别家指标、改一个域被迫重跑所有域。拆开之后各自控制队列、并发、重试。公开数据里单域单分区每天数千到数万条，推理约 2～3 小时。

> [!note]- 批注｜按业务域核对每日处理能力
> 按业务日和业务域记录提交量、完成量、排队耗时、重试量和最终失败量，可以定位数仓产出是否迟到、推理队列是否积压。原文给出的 2～3 小时对应单域单分区。估算平台整体处理时间时，还需要各域并行情况、共享推理配额和长会话占比。

还有三个工程细节，看着不起眼但对稳定性很关键：

1. **推理完成 ≠ 结果完整。**

    资源忙时部分请求会超时或返回空，进指标前要核对输入输出条数；更严谨就用 Trace ID 校验去重、查覆盖率。
2. **上下文太长会"静默失败"。**

    多轮会话加工具记录很吃 Token，超限时平台可能直接返回空结果而不报错。要提前估算长度、裁剪无关内容、保留关键证据。
3. **历史回刷可能重复计分。**

    重跑历史数据前不清目标分区，新旧结果就叠在一起。要幂等写入、分区覆盖、聚合前查重。

还有一个心态很重要：**评测平台自己的指标（数据完整率、推理成功率），要和 Agent 质量指标分开看。** 不然平台抽风，锅全扣在 Agent 头上。

> [!note]- 批注｜用样本键查判断结果是否齐全
> 补充示例。输入样本键为 `A、B、C`，输出为 `A、A、C`，两边都是三条，但缺一条 `B` 且重复了一条 `A`。按样本键查漏和查重，再统计结构化结果校验通过的记录。一个 Trace 含多轮或多个检查项时，用 Trace ID 加轮次、检查项和规则版本等字段组成与输出粒度一致的键。

> [!note]- 批注｜回刷时按写入范围选择策略
> 回刷前确认要替换的业务日、业务域和评测版本。该范围全量重跑时，可先写临时结果，检查缺失与重复后再覆盖对应范围。只补超时样本时，按样本键更新对应记录。要同时比较两版评分时，分开保存版本，并在汇总视图明确选择哪一版。

> [!note]- 批注｜平台异常和 Agent 质量各用什么证据
> 裁判请求超时或结果无法解析，记作评测链路未产出有效结果。能拿到充分证据并确认 Agent 做错时，计入业务失败。裁剪上下文时保留待评轮次、必要的历史引用和对应工具结果。裁剪后仍缺决定性证据的样本记为不可评。

## 六、裁判本身也要管：Prompt 不是让它聪明，是不让它自由

裁判也是大模型，也会幻觉、乱序、把历史轮次当真、证据不足时脑补。原文给的方向（我转述核心）：**把裁判的任务压缩成"依据证据做判定"这一件事。**

- 角色固定：它是评测裁判，不是聊天机器人
- 输入结构化：用户问题、Agent 回复、工具调用记录、历史上下文、评测规则，分开喂，不混在一起
- 规则硬约束：只能依据给定证据评分；不自行补全缺失信息；先定位再下结论

这套做法的精髓就一句话：**别指望裁判"聪明"，要让它"守规矩"。**

> [!note]- 批注｜让裁判输出可复核的判定
> 可以要求裁判返回检查项、判定、证据引用和缺失字段，由评测平台校验结果结构。用户消息、Agent 回复和工具返回属于被评材料，其中的指令式文本按证据读取。对日期、参数、必要步骤等可直接核对的内容先用规则校验，将需要理解语义的检查交给裁判。

## 七、我的判断：哪些能直接用，哪些要打折

看完这类大厂分享，我习惯把内容分成"能直接学的"和"要结合自己情况掂量的"。

**能直接学的：**

1. 成功率按"路由 × 回复"条件口径拆分，问题能指到环节
2. 数据清洗优先级拉满，先回答"样本属不属于本域、证据够不够"
3. 评分做分层门控，证据不足标"不可评"而不是瞎猜
4. 安全红线单独检查，永远不短路
5. 评测规则像代码一样管——版本化、可回看、可对比

> [!note]- 批注｜新旧裁判版本怎样比较
> 给每次评测记录规则版本、模型版本、输入加工版本和样本范围。修改 Rubric 或 Prompt 后，让新旧裁判在同一批已由人工确认的样本上评分，核对新增与消除的误判。比较 Agent 版本时，固定已校准的规则与裁判版本，把评分变化追到实际改动。

**要掂量的：**

1. **"日级全量"适合百万级会话的体量。**

    中小团队不必上来就全量，先圈一个高频业务域、每天采样评测，性价比更高。
2. **数仓 + 推理平台解耦的方向对,但落地可以很轻**

   ——一张表存样本、一个脚本调 API、一个看板出指标，起步足够了，不必照搬大厂架构。
3. **裁判会误判，关键样本要人工复核。**

    Judge 是工具，不是金标准；争议样本、高危样本，该人看还得人看。

> [!note]- 批注｜小样本评测怎样汇总
> 固定业务域与采样窗口，按会影响任务难度的类型分层，例如单轮查物流、多轮变更意图、工具超时。为排查故障额外抽取的高风险样本可以单独报告通过率。需要估算总体质量时，使用有代表性的样本，或按已知抽样概率加权，并报告每组样本量。

> [!note]- 批注｜人工复核怎样回到规则库
> 专家复核高风险样本、证据不足的样本和裁判争议结果，同时保留少量随机抽样。复核时记录原判、人工结论、证据和分歧原因。确认是规则歧义时修订 Rubric，将新旧规则放到固定校准集上比较。确认是数据缺字段时，先修取证链路。
