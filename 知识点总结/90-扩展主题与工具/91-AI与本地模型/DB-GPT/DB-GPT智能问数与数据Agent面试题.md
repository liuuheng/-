##### DB-GPT 智能问数与数据 Agent 面试题

来源：[大数据Agent 项目该背就背，不要太老实](https://mp.weixin.qq.com/s/EMQRh0xEHUQZLg2TyHLMIQ)

适用场景：数据开发、数仓开发、数据平台岗位中涉及 ChatBI、Text2SQL、数据 Agent 或 DB-GPT 项目经验的面试。

使用边界：本文保留原文 30 道面试题的技术主线，但示例中的准确率、延迟、成本、人力节省和表数量都不是通用结论。回答时必须换成自己能够提供评测集、日志、代码或运行记录的数据。个人 Demo、公司预研和生产系统要明确区分。

##### 一分钟项目介绍

Q：请用一分钟介绍这个智能问数项目。
A：这个项目解决的是临时取数依赖数据开发的问题。用户输入自然语言问题，系统先从元数据和指标知识库中召回相关表、字段、口径与示例，再让模型生成目标引擎的 SQL。SQL 不会直接执行，而要经过语法、表字段、权限、分区条件和资源风险校验；校验通过后由数据源连接器执行，最后返回结果、SQL、来源表和口径说明。我主要负责的部分应按真实情况回答，例如元数据接入、指标口径知识库、SQL 校验或权限链路。项目效果只报告自己有证据的评测结果。

##### 知识点补充

回答顺序固定为“业务问题—输入输出—完整链路—个人职责—验证结果”。不要一开始罗列 SMMF、AWEL、RAG 等名词；面试官首先要判断项目解决什么问题，以及你具体做了什么。

##### 一、项目定位与技术选型

##### 1. 为什么做智能问数项目？

Q：这个项目的业务背景是什么，为什么要做？
A：先说明原流程的可观察问题，例如临时取数工单量、平均等待时间、数据开发投入和重复问题比例。智能问数的目标不是让模型替代全部分析，而是让权限范围内、口径明确、复杂度可控的问题能够自助查询。是否值得建设，要比较上线后的工单下降、问题正确率、人工复核成本和业务实际使用率。没有历史工单或基线数据时，只能称为技术预研，不能说已经节省了多少人力。

##### 知识点补充

业务价值要落到“谁在什么场景下缩短了哪段流程”。“用了大模型”“支持自然语言”是能力描述，不是业务结果。

##### 2. 为什么选择 DB-GPT，而不是自研或 Dify？

Q：为什么选择 DB-GPT？为什么不自研，也不用 Dify？
A：选型依据应和项目目标对应。DB-GPT 面向数据场景，已有数据源连接、Text2SQL、知识库、模型接入和结果展示能力，适合快速验证智能问数；通用工作流平台也能实现，但数据连接、SQL 校验和图表链路通常需要额外建设；完全自研的控制力最高，代价是要自行维护模型网关、会话、编排、连接器、权限和前端。最终选择还要比较许可证、版本稳定性、现有技术栈、私有化要求和团队维护能力，不能只说“社区活跃”。

##### 知识点补充

“为什么不用某方案”比“为什么用当前方案”更能体现选型能力。应准备一张针对当前需求的对比记录，而不是泛泛比较产品优劣。

##### 3. DB-GPT 的整体架构是什么？

Q：请介绍 DB-GPT 的整体架构。
A：可以按四层回答。数据层通过连接器访问 MySQL、Hive、Doris、StarRocks、ClickHouse、Spark 等数据源；模型层通过 SMMF 管理 API 模型和本地模型；编排层由 AWEL、Agent 与 RAG 组成；应用层提供自然语言问数、数据库交互、知识库和报表等场景。讲完分层后，要走一遍真实请求：用户问题进入路由，检索 schema、口径和示例，模型生成 SQL，校验通过后执行，再渲染结果并保留复核信息。

##### 知识点补充

架构回答的重点是组件之间传递什么数据，以及每层失败时如何处理。只记住分层名称，无法证明理解了系统。

##### 4. SMMF 解决什么问题？

Q：SMMF 是什么，解决了什么问题？
A：SMMF 是模型服务管理层，用统一接口管理不同模型服务，使上层应用不直接绑定某个 API 或本地推理框架。预研阶段可以接外部 API，生产阶段若要私有化，可切换到本地模型服务，但前提是接口、能力和上下文约束兼容。面试时应说明自己实际配置过哪些模型、如何切换、切换后哪些参数仍需调整。

##### 知识点补充

“应用代码零修改”只能在抽象接口完全覆盖模型差异时成立。工具调用、结构化输出、上下文长度和 Prompt 模板仍可能需要适配。

##### 5. AWEL 与普通 Chain 有什么区别？

Q：AWEL 是什么，它和 LangChain 的 Chain 有什么区别？
A：AWEL 用有向无环图组织工作流，使节点、依赖、重试和观测位置更明确。问数主链路包含检索、生成、校验、执行等确定步骤，适合显式工作流；澄清问题、失败反思等环节才需要有限的 Agent 自主性。回答时不要把“声明式”和“命令式”说成绝对优劣，应结合可观测性、重试、状态管理和团队维护成本说明取舍。

##### 知识点补充

生产链路越依赖自由规划，结果和资源消耗越难预测。能够固定的流程应固定，只在确实无法预先枚举的局部引入 Agent。

##### 二、个人贡献与对话设计

##### 6. 二次开发具体改了什么？

Q：你说做了二次开发，具体改了什么？
A：回答必须落到代码或配置位置。可以从三个方向中选择自己真正完成的内容：元数据增强，把表字段注释、分层和关联关系加入召回；指标口径知识库，让系统能检索口径并在歧义时反问；SQL 校验与权限钩子，在执行前解析表字段、检查权限、分区和资源风险。每个改动都要说明修改前的失败案例、实现位置、异常路径和修改后的回归结果。

##### 知识点补充

“接了一个模型”“改了 Prompt”通常不足以称为二次开发。最低证据包括代码差异、配置、运行日志、失败样例和测试结果。

##### 7. 多轮对话上下文如何管理？

Q：用户连续追问时，系统如何管理上下文？
A：保留完成当前任务所需的最近对话，并保存上一轮经过校验的 SQL、结果摘要和已确认口径。用户说“再按渠道拆一下”时，以上一轮 SQL 为基准做受控增量修改，比把全部自然语言历史重新交给模型更稳定。还要限制上下文长度，避免明细结果和敏感数据被无边界带入后续模型请求。

##### 知识点补充

对话历史、业务状态和执行状态是三类数据。历史消息只表示用户说过什么；已经确认的口径和上一轮 SQL 才是可复用的任务状态。

##### 三、Text2SQL 准确性

##### 8. 准确率如何从低水平提升？

Q：Text2SQL 准确率是怎么提升的？
A：按三个阶段回答。先提高 schema 召回质量，确保模型拿到正确表和字段；再建立业务问题与标准 SQL 的 few-shot 示例库，按问题语义动态召回少量相似案例；最后增加解析、元数据校验、执行报错回传和有限重试。每层贡献多少要做消融实验：固定同一评测集，分别开关某层，比较执行结果准确率，不能直接引用文章中的提升百分比。

##### 知识点补充

准确率提升必须能区分召回错误、语义错误、SQL 生成错误和执行错误。只给总准确率，无法判断下一步应优化哪一层。

##### 9. 数仓几百张表，Schema 放不进 Prompt 怎么办？

Q：表和字段太多，无法全部放进上下文，怎么处理？
A：把表名、字段名、中文注释、分层和主题域建立检索索引，先按问题召回少量候选表，再对宽表选择相关字段。排序时可加入数仓分层、查询热度、表质量和用户权限等信号，引导模型优先使用稳定的汇总层，而不是扫描明细表。召回结果仍要记录，便于判断 SQL 错误是否由选表错误引起。

##### 知识点补充

Top K 不是越大越好。候选表过少会漏召回，过多会增加歧义和 Token；K 值需要在固定评测集上调试。

##### 10. 如何处理模型编造的表和字段？

Q：模型生成了不存在的表名或字段名，怎么治理？
A：先通过检索缩小可用 schema，再在生成后用 SQL 解析器提取全部表和字段，与当前 catalog 的元数据及用户白名单比对；不匹配就拒绝执行，并把受控错误回送模型重新生成，重试次数必须有限。这个流程能处理标识符幻觉，但不能证明 Join 条件或指标口径正确。

##### 知识点补充

字段存在性、SQL 可执行性和业务正确性是三个不同层级。字段都存在的 SQL 仍可能算错结果。

##### 11. 多表 Join 准确率低怎么办？

Q：模型不会选 Join 键，或者多表 Join 经常出错，怎么处理？
A：在元数据中维护主外键、常用 Join 路径、基数和时间有效性，并把相关关系与表结构一起召回。高频分析路径可以沉淀为 DWS 宽表、语义模型或指标服务，减少模型临时拼接多张明细表。评测时单独统计 Join 问题，记录错表、错键、重复放大和时间条件缺失等错误类别。

##### 知识点补充

Join 准确率的上限受数仓建模和元数据质量约束。缺少关联关系时，换更大的模型也只是让猜测更像真的。

##### 12. 同一指标有多种口径怎么办？

Q：“销售额”同时有 GMV、实付和收入等口径，模型怎么选择？
A：指标知识库需要保存名称、定义、公式、粒度、时间口径、适用组织、来源表和负责人。问题同时命中多个合法口径时，系统必须展示候选定义并要求用户澄清，不能让模型自行选择。生成结果中还应展示本次采用的口径和来源表，方便业务复核。

##### 知识点补充

知识库解决“系统知道有哪些口径”，澄清流程解决“本次用户要哪个口径”。两者缺一不可。

##### 13. 用户问题很模糊怎么办？

Q：用户只说“看看最近销售怎么样”，系统如何处理？
A：先识别意图并检查必填槽位，例如指标、时间范围、组织范围、维度和对比基准。缺少会改变结果的条件时先反问；可以安全使用默认值时，也要明确展示默认条件。宁可多问一个决定结果的问题，不要用隐藏假设生成看似完整的答案。

##### 知识点补充

不是所有信息缺失都要追问。只有缺失值会改变计算口径、权限或查询范围时，追问才有必要。

##### 14. 什么时候应该微调模型？

Q：项目考虑过 Text2SQL 微调吗，什么时候值得做？
A：先用检索、Prompt、few-shot 和校验建立稳定基线，并积累按难度分层的领域评测集。如果主要错误仍来自缺元数据或口径，微调不能解决；只有通用模型在获得正确上下文后仍持续出现模式化生成错误，同时已有足量、高质量且许可清晰的“问题—SQL”样本，才值得评估微调。比较时要包含训练、标注、部署和版本维护成本。

##### 知识点补充

公开数据集上的准确率不能直接代表公司数仓效果。业务表名、方言、口径和 Join 关系变化后，数据分布已经不同。

##### 15. 不同 SQL 方言怎么适配？

Q：模型生成 MySQL SQL，但执行引擎是 Hive、Spark 或 StarRocks，怎么办？
A：Prompt 中明确目标引擎和版本，生成后使用 SQL 解析器做语法校验和可支持范围内的方言转换，再通过目标引擎的测试库或 `EXPLAIN` 验证。日期函数、复杂类型、窗口语义、Hint 和引擎扩展语法可能无法无损转换，必须维护方言规则和回归用例，不能只调用一次自动转译。

##### 知识点补充

“解析成功”不代表目标引擎能执行，“执行成功”也不代表语义等价。方言适配要同时检查语法和结果。

##### 四、安全、权限与资源治理

##### 16. 权限怎么做？

Q：如何防止用户通过自然语言查到无权访问的数据？
A：模型不参与最终授权判断。系统根据登录用户获取可访问的表、列和行级范围，生成后的 SQL 经过权限校验或受控改写；无法证明安全时直接拒绝。数据库或计算引擎再使用最小权限账号兜底，并记录用户问题、生成 SQL、改写结果和执行行为。Prompt 中写“不要访问敏感表”只能改善体验，不能作为权限控制。

##### 知识点补充

行级权限改写要正确处理子查询、CTE、集合操作和外连接。简单拼接 `WHERE` 可能改变结果语义或被绕过。

##### 17. 如何防止全表扫描拖垮集群？

Q：模型生成高成本 SQL，把查询集群打满怎么办？
A：执行前根据目标表规则检查分区裁剪条件，必要时执行 `EXPLAIN` 或获取扫描量估算；超过阈值的查询要求缩小范围或转人工。执行侧设置超时、并发、扫描量和结果行数限制，并使用独立资源组或队列隔离问数负载。监控拒绝率、超时率、扫描字节和对其他业务查询的影响。

##### 知识点补充

有 `WHERE` 不等于能裁剪分区，`EXPLAIN` 的代价估算也不一定准确。治理规则必须结合具体引擎和表设计验证。

##### 18. 数据会泄露给模型服务商吗？

Q：调用外部模型 API 时，如何保证数据安全？
A：预研阶段只传完成生成所需的 schema、口径和经过审查的少量样例，不传查询明细和敏感值；字段名本身敏感时也要做映射。生产是否采用外部 API，要经过数据分类、合同和安全评审。私有化部署也不能直接等同于数据不出域，还要检查日志、遥测、依赖下载、向量库、备份和运维访问路径。

##### 知识点补充

模型输入、检索上下文、工具执行结果和日志都可能含敏感信息，安全审查不能只盯 Prompt。

##### 五、性能、成本与部署

##### 19. 响应延迟是多少，怎么优化？

Q：端到端延迟如何分析和优化？
A：把延迟拆为意图识别、检索、Prompt 组装、模型生成、SQL 校验、查询执行和结果渲染，记录各阶段 P50、P95 和超时率。检索与部分规则判断可并行，高频确定性问题可以缓存，模型输出可以流式展示进度；如果主要耗时在数据库查询，换更快模型不会解决。回答中的延迟数字必须来自相同数据量和并发下的监控。

##### 知识点补充

业务能否接受延迟取决于替代对象。替代半天工单时十秒可能可接受，替代交互式 BI 时同样延迟可能过高。

##### 20. 成本怎么控制？

Q：如何控制模型和查询成本？
A：模型侧通过召回压缩上下文、缓存高频问题、按复杂度路由模型和限制重试次数控制 Token；数据侧限制扫描量、并发和结果规模，优先使用汇总表。成本统计应包含模型调用、向量库、计算引擎、GPU 或 API、存储和运维，不只统计单次 Token 费用。

##### 知识点补充

降低上下文可能同时降低成本和噪声，但过度裁剪会漏掉必要 schema。成本优化必须与准确率一起评估。

##### 21. 系统如何部署？

Q：Demo 和生产环境分别怎么部署？
A：Demo 可以在单机环境运行 Web 服务、模型接入、向量库和测试数据库，用于走通链路。生产需要把应用服务、模型服务、向量检索和数据查询按负载与故障域拆分，增加高可用、配置管理、密钥管理、监控、审计和发布回滚。具体安装命令、端口和默认组件随版本变化，回答时应以自己运行版本为准。

##### 知识点补充

“Docker Compose 能启动”证明原型可运行，不证明满足生产可用性。还要回答状态存在哪里、组件故障如何恢复、容量如何扩展。

##### 22. 如何与现有 BI 系统集成？

Q：智能问数如何接入公司已有 BI？
A：可以把问数页面嵌入 BI 门户，也可以通过企业通信机器人提供入口。生成结果应跳转或沉淀到受权限控制的 BI 查询页，并展示 SQL、来源表、口径和数据截止时间。已有 BI 的语义层、权限、缓存、审计和图表能力应优先复用，避免再造一套不一致的指标系统。

##### 知识点补充

接入方式要考虑用户身份透传。机器人或共享链接如果无法映射到真实用户，就无法可靠执行个人数据权限。

##### 六、评测、Badcase 与业务验收

##### 23. 准确率怎么定义？

Q：Text2SQL 准确率的判定标准是什么，评测集从哪里来？
A：优先使用执行结果一致性，而不是 SQL 文本完全一致，因为同一问题可能有多种等价写法。评测集可以从历史取数工单抽样，经人工确认口径和标准结果，并按单表过滤、聚合、多表 Join、时间计算和口径歧义分层。还要定义空结果、排序、浮点误差、执行失败和超时如何计分，训练或 few-shot 样本不能泄漏进测试集。

##### 知识点补充

整体准确率会被简单问题比例影响。至少同时报告总样本量、各难度样本量和分层结果。

##### 24. Badcase 如何闭环？

Q：错误案例从哪里收集，如何修复并防止复发？
A：从用户点踩、空结果、执行报错、权限拒绝和人工抽检中收集案例，标记为召回错表、业务语义错误、口径缺失、SQL 生成错误、权限错误或执行故障。修复后加入固定回归集；可靠且具有代表性的案例才能进入 few-shot 库。每次 Prompt、模型、元数据或规则变化都运行回归，比较新增修复与历史退化。

##### 知识点补充

修复一条 Prompt 不一定能修复一类问题。优先把稳定知识写入元数据或口径资产，把确定性限制写成规则。

##### 25. 上线后如何判断业务是否买账？

Q：如何验证系统真正产生了业务价值？
A：同时观察使用、正确性和效率：周活用户、有效提问量、重复使用率；分层准确率、高风险错误率和人工复核率；取数工单量、平均等待时间和数据开发投入。还要区分“用户尝试过”和“用户拿结果做了决策”。每个答案展示 SQL、来源表和口径可以提高可复核性，但不能替代正确性评测。

##### 知识点补充

工单下降可能来自业务淡季或流程变化。要尽量使用试点组、对照期或相同业务周期比较，避免把相关性直接写成项目收益。

##### 26. 模型一本正经地给错答案怎么办？

Q：业务方相信了错误答案，系统如何兜底？
A：强制展示 SQL、来源表、口径和数据截止时间；校验失败、口径不明确或超出能力范围时拒答或转人工；关键报表只开放经过验证的模板或指标接口，不允许自由生成。建立用户反馈、审计和事故复盘机制，明确哪些结果只供探索，哪些可以进入正式决策。

##### 知识点补充

可解释性让错误更容易被发现，但不会自动让结果正确。高风险场景需要确定性数据产品，而不是仅给自由问数加免责声明。

##### 27. DB-GPT 有什么缺点，踩过什么坑？

Q：请说几个你实际遇到的 DB-GPT 问题。
A：只能回答自己验证过的问题。可检查的方向包括版本升级导致配置或接口变化、文档与代码不同步、默认 Prompt 不适合中文指标口径、内置组件的高可用或容量有限、模型和数据源适配差异。每个问题都要说明使用版本、报错或现象、定位证据、临时处理和后续风险，不能照搬别人的“踩坑清单”。

##### 知识点补充

能够指出缺点不等于用过项目；包含版本、复现条件和修复记录才构成经验。

##### 28. 如果重做一次，会改什么？

Q：项目复盘后，最想提前做哪两件事？
A：第一天就建立评测集和错误分类，否则每次优化只能凭感觉；接入模型前先治理表字段注释、关联关系和指标口径，否则模型拿不到完整业务语义。还可以补充自己实际遇到的工程问题，例如权限设计介入太晚、查询资源没有隔离或缺少链路追踪。

##### 知识点补充

复盘回答应说明原决策为何合理、后来出现了什么新证据、下次如何改变流程。只说“加强沟通、提高测试”没有可执行性。

##### 七、演进方向与行业判断

##### 29. 如何从 ChatBI 演进到数据 Agent？

Q：智能问数之后，系统还能如何演进？
A：从单次生成 SQL，逐步扩展到受控的多步任务：指标异常后自动选择下钻维度、按固定工作流生成周报、调用沙箱执行 Python 分析。每增加一种工具或自主步骤，都要补权限、预算、超时、幂等、审计和人工确认。不能因为名称从 ChatBI 变成 Agent，就放宽生产安全边界。

##### 知识点补充

数据 Agent 的基础仍是机器可读的元数据、指标口径、血缘和权限。底层数据资产不完整时，多 Agent 只会放大错误链路。

##### 30. 如何看待 MCP 与数据 Agent？

Q：MCP 会怎样影响数据平台和数据开发岗位？
A：MCP 可以把查元数据、取指标口径、看血缘和执行查询封装成标准化工具接口，使不同 Agent 复用数据平台能力。实际价值取决于工具的输入输出是否稳定、身份权限是否透传、调用是否可审计、错误是否可恢复。对数据开发而言，需要把数据资产建设成机器可读、权限明确、可验证的服务，而不只是部署一个 MCP Server。

##### 知识点补充

MCP 统一的是工具接入形式，不会自动统一业务语义，也不会替代权限、质量和资源治理。

##### 八、面试前的实操与证据清单

Q：为了让这套项目经验经得住追问，最低要准备什么？
A：至少完成以下内容：

1. 记录 DB-GPT、模型、数据库和运行环境的实际版本。
2. 跑通一条“自然语言—召回—生成 SQL—校验—执行—展示”链路并保存日志。
3. 完成一个可展示的改动，例如口径澄清、字段白名单或强制分区检查。
4. 准备一组分层评测题，保留标准结果、实际结果和错误分类。
5. 准备一个失败案例，讲清现象、证据、修复和回归验证。
6. 统计自己的表数量、样本数量、准确率、P95 延迟、费用和失败分布。
7. 明确哪些是自己完成的，哪些是框架原生能力，哪些只是后续计划。

##### 知识点补充

原文中的“85% 准确率、8 秒延迟、节省 1/3 人力、每月几十元、Join 70%”都是示例。面试时可以报告不漂亮但可追溯的结果，不能把示例数字包装成个人成果。

##### 九、可直接套用的回答骨架

Q：面对没有准备过的项目追问，如何组织答案？
A：使用“结论—条件—实现—证据—边界”五段式：先直接回答选择或判断；说明它成立的业务和技术条件；讲自己实现的链路或代码位置；给出评测、日志或监控证据；最后说明未覆盖场景和下一步。没有做过的内容直接区分为“框架支持”“我验证过”和“生产尚未验证”，不要把三者混在一起。

##### 知识点补充

面试官连续追问的目的通常是确认事实边界。稳定地说明“做到了什么、凭什么确认、什么还没做”，比背出更多术语更可信。
