# Agent 评测面试问答：以美团商家广告助手为例

美团商家广告助手会查账户数据、生成巡检报告，也可以编辑投放计划。商家有一次要求巡检昨日投放，Agent 交付了完整的报告，执行记录却显示它查的是当天数据。美团案例和披露的回归数字来自技术团队的白皮书，追问参考两篇笔记的批注。[[08-Agent 评测白皮书（业务实践篇）：巡检评测与优化闭环|业务实践篇]] · [[09-真实案例：美团 Agent 评测从“测出来”到“改进去”（原文批注版）|案例解读]]

## 出题与判定

### Q1. 给一个能查数据、调工具的业务 Agent 搭评测，你怎么做？

我会用业务任务来验收 Agent。以巡检为例，先用业务流程和线上失败样本出题，给每道题配好账号、数据和判定标准。试跑时保留实际查询、工具返回和报告，逐项检查该走的分支有没有走、结论是否忠实于数据、报告能不能交付。评测器用专家标注过的样本校准。出现失败时，从失败项追到执行证据，修完再用同一套标准回归，同时看通过率、稳定性和耗时。

**追问　如果任务是编辑投放计划，验收证据怎么变？**

在隔离的测试账号下记录编辑前的计划状态。执行后按计划 ID 回读，核对目标字段的实际值以及其他受约束字段的预期值。调用返回的成功状态可以帮助排查，计划对象的实际状态才是这类任务的交付证据。

### Q2. 评测集从哪来？怎样知道覆盖到了有风险的分支？

从业务 SOP（标准作业流程）拆出状态、数据依赖、分支条件、提前停止点和能力边界，再从线上或离线的失败样本补题。比如无异常门店时，预期是跳过下钻并生成报告。用户实际想编辑计划时，预期是转交编辑 Skill，也就是负责这类任务的业务流程模块。两道题都要写清应当执行和应当跳过的动作。白皮书中的 KA 每日巡检共设计了六类、41 个场景。[[08-Agent 评测白皮书（业务实践篇）：巡检评测与优化闭环#二、商家广告助手的 Benchmark 设计|巡检场景设计]]

**追问　收到「昨日查成今天」这条 Bad Case，怎么把它加入题集？**

保留原例做回归，再把它抽成日期理解与计算问题，补上今日、昨日、指定历史日期和周末等样本。每条样本都要给出运行日、业务时区和预期查询范围。遇到「上一个工作日」，用业务日历算期望值。

### Q3. 一道题怎样变成可复跑的 Task？

Task 是带执行前提和判定标准的测试用例。它要记录用户请求、目标账号、权限、业务运行日和数据状态，并定义要验收的行为和结果。一次实际执行叫 Trial。Trace 是这次执行留下的记录，验收时要能从中查到工具名、请求参数、返回值和时序。评测运行器（Harness）负责准备环境、运行 Task、收集证据并汇总多次 Trial 的结果。

**追问　两版 Agent 都收到「巡检昨日投放」，为什么还要核对运行日？**

「昨日」是相对日期。旧版在 `D` 跑，期望查询 `D-1`。新版在 `D+1` 跑，期望查询 `D`。我会给两版注入相同的业务运行日，复用同一份测试数据，再核对账号、权限和其余运行配置是否可比。

### Q4. 怎样判一次巡检成功？Grader 怎么选？

Rubric 是逐条定义验收条件的评分细则。流程检查必要调用和条件分支，证据检查工具参数和报告结论，交付检查报告内容与必要格式。适用的成功必需项全部通过，这次 Trial 才成功。报告结构完整、查询日期却错了，判整次失败。重复调用、规划效率等质量项另记，用于定位性能和成本问题。

**追问　查询日期和报告忠实性分别怎么判？**

Grader 是执行判定的程序或模型。预期日期已确定，Trace 里的 `query_date` 也可解析，就用确定性 Grader 做精确比较。判断报告结论是否得到工具数据支持时，可以把工具结果和报告一起交给 LLM Grader，并给出明确的通过条件。已有必需项确认失败时，整次 Trial 判失败。其余必需项都通过、但有一项或多项缺少证据时，记为「无法判断」，高风险场景转人工复核。

## 指标、校准与排查

### Q5. `Pass@k` 和 `Pass^k` 各自回答什么问题？

在这套巡检 Benchmark 的口径里，同一 Task 的 `k` 次可比试跑算一组。`Pass@k` 是至少成功一次的 Task 占比，回答多试几次能否做成。`Pass^k` 是 `k` 次全部成功的 Task 占比，衡量重复执行是否稳定。[[09-真实案例：美团 Agent 评测从“测出来”到“改进去”（原文批注版）#六、最有意思的一个细节：Pass@k 与 Pass^k|重复执行指标]]

假设 3 道 Task 各跑 3 次，分别成功 3 次、2 次和 0 次。有两道至少成功一次，`Pass@3 = 2/3`。只有一道三次全过，`Pass^3 = 1/3`。按 Trial 统计则是 9 次试跑成功 5 次，单次执行的成功比例为 `5/9`。

**追问　两个指标差得多，下一步查什么？**

如果每次试跑都明确判为成功或失败，且两项指标用的是同一批试跑和同一个任务分母，差值就是同时出现成功与失败的 Task 占比。先找出这些 Task，再比较它们通过和失败时的 Trace，确认波动来自执行还是判定。比较不同 Agent 版本时，要统一 `k`、成功标准和试跑条件。

### Q6. 评测器也会误判，怎么校准？

用业务专家审核过的通过、失败和边界样本建立校准集。逐层核对 Trace 有没有读对工具参数和返回值、确定性规则有没有表达业务约束、LLM Grader 和专家在哪些语义题上有分歧。规则改完，回放原误判样本和相邻反例。日常用固定校准集做自动回归，抽检争议或高风险结果，指标突变时增加复核。

**追问　为什么美团把固定调用顺序改成 DAG？**

读到计划列表后，预算查询和花费查询可以换序或并行，判断是否触达预算前要拿齐两项结果。旧规则要求固定的先后顺序，会把合法换序判成失败。DAG（有向无环图）用边表达真正的先后依赖。校准时要验证合法换序能够通过，同时漏查一路或提前给出结论仍会被拦下。[[08-Agent 评测白皮书（业务实践篇）：巡检评测与优化闭环#三、评测优化与Agent 迭代（Error Analysis）|评测器校准与归因]]

### Q7. 看到「日期不一致」失败项，怎样查根因？

从失败项对应的局部 Trace 查起。先按运行日算出预期查询日期，再核对原始工具请求和返回数据。如果入参已经是 `D`，往前查日期解释、参数生成和工具适配。如果入参是 `D-1` 但返回数据属于 `D`，查工具执行、默认值和数据。若原始请求与返回都正确，就核对 Trace 解析和 Grader 的期望值。这样可以把「昨日查成今天」定位到实际出错的环节。

**追问　同一道题偶尔出错，怎样补证据？**

固定 Task、运行日和数据状态多跑几次，找出成功与失败试跑中最早分歧的调用或判断。局部证据解释不了差异时，再查看完整 Trace，或只替换一个可疑组件做对照。

## 优化、回归与发布

### Q8. 找到根因后，哪些职责适合从模型下沉？

把有明确输入和固定判断规则的工作交给配置或代码。美团用公共配置管理平台、账号和参数约束，并明确登录前置条件、账号路由、唯一命令模板和重试规则。Skill 写明什么条件触发下钻、什么条件终止以及转交到哪里。数值计算、字段映射和筛选交给代码。模型负责编排调用、理解业务条件和根据证据生成报告。[[08-Agent 评测白皮书（业务实践篇）：巡检评测与优化闭环#三、评测优化与Agent 迭代（Error Analysis）|巡检任务优化]]

**追问　日期计算写进代码后，「昨日」由谁处理？**

可以先从请求和上下文解析出「前一自然日」这类日期意图，再由日期函数基于运行日、时区与业务日历生成查询范围。日期意图有歧义且会影响任务结果时先追问。实际查询仍由日期检查项验收。

### Q9. Grader 和 Agent 同时改了，怎样解释通过率上涨？

用同一批带专家结论的历史 Trace 对照新旧 Grader，核对哪些误判被修正、哪些样本产生了新分歧。新版需要旧 Trace 未记录的证据时，补跑采集。评估 Agent 改动时，让新旧 Agent 在可比的 Task、环境和数据状态下各自运行，再统一用同一版已校准 Grader 判定。

**追问　明确停止条件后，你会回归哪些场景？**

至少覆盖三种分支。无异常时应跳过下钻，有异常且尚未定位原因时应做必要下钻，命中直接原因时应停止后续弱证据检查。对照目标检查项，再看整体完成率和耗时，防止缩短流程时漏掉必要诊断。

白皮书披露的脱敏变化量为任务完成率增加 17 个百分点，`Pass@k` 增加 22 个百分点，`Pass^k` 增加 12 个百分点，平均 Token 与平均耗时分别相对下降 52% 和 53%。这些数对应同一巡检 Benchmark 的版本回归。[[08-Agent 评测白皮书（业务实践篇）：巡检评测与优化闭环#三、评测优化与Agent 迭代（Error Analysis）|离线回归结果]]

### Q10. 怎样把一次评测变成每轮迭代都能跑的回归？

把 Task 集、环境配置和 Grader 留成可复用的评测资产，并记录各自版本。用同一条评测流水线批量执行、收集 Trace、逐项判定和汇总。报告要能从失败的 Task 下钻到具体检查项、工具参数和返回值。人工复核集中在抽样校准、争议和高风险结果上。[[08-Agent 评测白皮书（业务实践篇）：巡检评测与优化闭环#四、评测体系的工程化落地|评测工程化]]

**追问　怎样控制日常回归的成本？**

提交改动时可以重点跑受影响分支和一组核心任务。发布前再跑固定的完整回归集，对稳定性敏感的任务安排重复试跑。保留每轮的任务范围和试跑次数，比较版本时使用相同的评测范围。

### Q11. 离线评测通过后，怎样判断上线效果？

上线前用离线回归核对任务成功率、执行稳定性和资源成本，按任务风险设置发布门槛。上线后观察线上任务失败率、耗时和实际计划变更，再结合用户采纳、问题解决等业务指标评估效果。编辑计划这种会改变账户状态的任务，可以先在少量已授权的账号上验证实际变更，再逐步扩大范围。

**追问　试用商家的业务指标上升了，怎么判断有多少来自 Agent？**

原文线上结果来自少量试用商家的观测，能用作后续实验的线索。若要估计 Agent 的因果收益，需要足够的样本和同期对照，例如让相近门店随机进入使用 Agent 和保持原流程的两组，并同时观察促销、季节与门店经营状态。[[08-Agent 评测白皮书（业务实践篇）：巡检评测与优化闭环#三、评测优化与Agent 迭代（Error Analysis）|离线到线上]]

## 情境题

### Q12. 评测时，什么时候回放工具响应，什么时候接真实工具？

要对照日期理解、工具选择和分支决策，可以固定业务运行日与数据，用回放减少工具和数据波动。回放按工具名与账号、`query_date` 等实参匹配响应，保留实际请求供 Grader 核对。遇到合法请求但缺少对应响应时，补齐回放数据再复跑。要验收鉴权、真实接口行为或写入是否生效，就用隔离的测试账号接真实工具，核对接口返回和实际状态。

**追问　连续三次试跑「调整预算」，怎样让结果可比？**

每轮都要从同样的初始预算和业务状态开始。可以在每轮前恢复测试数据，或给每次 Trial 一份独立但等价的测试计划，再按计划 ID 回读。计划起始值已经等于目标值时，验收的是「目标已满足」这个分支，可以单独出题。

### Q13. 修好一批旧题后，怎样验证 Agent 能处理同类新任务？

日常回归保留旧题和已经修复的失败样本，用来检查错误是否重现。再留一批独立任务用于版本验收，覆盖同样的业务规则和风险，使用新数据或新条件组合。调 Prompt 和 Skill 时用回归题验证改动。某道验收题拿来调试后，就把它纳入回归集，并补充新的独立验收题。

**追问　把「巡检昨天」改成「看看昨儿的投放」，算一道新验收题吗？**

这条变体可以测触发词和措辞理解。切分回归题和验收题时，我会把同一原例及其改写放在同一侧。要测日期计算能否覆盖新边界，可以留出「月初查昨日」，验收查询是否正确落到上月最后一天。

### Q14. LLM Grader 与专家有 95% 的一致率，可以自动放行吗？

能否自动放行取决于高风险检查项的误判和证据是否充足。我会在专家判失败的高风险样本中，统计有多少条被 Grader 放行。白皮书里有一次误放，工具只报告「投放消耗下降」，评测器却接受了「投放效果变差」。校准时应把报告结论和原始工具返回同时提供给 Grader，并写明结论需要哪类数据支撑。[[08-Agent 评测白皮书（业务实践篇）：巡检评测与优化闭环#四、评测体系的工程化落地|语义判定与人工质检]]

**追问　100 次试跑里有 10 次缺少验收证据，通过率怎么报？**

假设有 76 次确认通过、14 次确认失败、10 次待复核，报告已确认通过 `76/100`、待复核 `10/100`。如果另外报可判定样本的通过比例，就明确写成 `76/90`。用于发布判断时，成功必需项要有足够的证据才能放行。

### Q15. 新版任务完成率更高，编辑计划的权限检查却退化了，你怎么决定是否发布？

我会对改状态的任务单设权限和写入结果的发布条件。比如验收要求权限不足时停止，而新版仍然发起了被禁止的编辑调用，即使工具拦住了写入，权限检查也判失败。这个分支要先修复和复测，再作发布决定。回归要同时覆盖有权限与无权限两种用例，分别确认该写的确实写了、该停止的及时停止。

**追问　两版都达到成功率和稳定性要求，怎样比较成本？**

用同一批任务和试跑协议比较端到端时延，再用总运行成本除以成功次数，得到每成功交付一次的平均成本。总成本包含失败及重试的消耗。复杂分支单独核对时延是否满足业务要求。

### Q16. 把巡检评测迁到数仓取数 Agent，你会怎么设计一道题？

可以用「统计昨日发生成功支付的订单数，按订单去重」做一题。Task 固定运行日、业务时区和测试数据版本，约定按支付时间判定「昨日」。用人工核对过的基准结果验收订单数，同时检查实际查询的时间范围、支付状态、去重键 `order_id` 和读表权限。

**追问　SQL 能运行，结果数字也对，还要验收什么？**

用能区分业务口径的数据再测一次。同一订单有两条昨日支付事件时，应只算一单。昨日创建、今日支付的订单，应归到今日。必要时从实际查询或执行记录确认取数范围和去重口径，并允许满足同一业务定义的不同 SQL 写法。
