##### 架构与数据湖

##### 流批一体

Q：如何理解实时离线一体或流批一体架构？
A：我理解的流批一体不是让实时和离线共用一个集群，而是让同一份表、Catalog 和计算口径同时支持增量处理与历史重算。实际落地可以是 MySQL CDC、日志进入 Kafka，Flink 实时写入 Paimon/Iceberg/Hudi 主键表；实时看板消费增量，离线 Spark/Flink Batch 读取同一快照做 T+1 对账。指标逻辑尽量复用同一 SQL 模板，补数时指定历史快照或分区重跑，结果通过表格式的原子 commit 切换。资源仍用独立队列隔离，Compaction、小文件、Schema 演进和迟到更新由专门任务治理。验证是否真正一体化，要看同一订单在实时、批量查询是否口径一致、失败后能否回放，以及补数是否无需维护第二套明细表。

##### 知识点补充

常见底座是 Kafka + Flink + Iceberg/Hudi/Paimon 等湖表，配合统一 Catalog。真正难点包括 CDC 更新语义、小文件、Compaction、Schema 演进、流批资源冲突和一致性提交。

##### 实时与离线资源隔离

Q：实时和离线任务发生资源冲突时怎么处理？
A：实时任务有持续低延迟和稳定 checkpoint 的要求，离线任务更偏吞吐，所以我会先做资源池和优先级隔离，而不是发生冲突后临时抢资源。在 YARN 可使用独立队列、容量和抢占策略，在 Kubernetes 可使用 namespace、quota、priority class 和独立节点池；核心实时任务预留 CPU、内存、磁盘和网络，离线任务按时间窗弹性调度。发生冲突时再根据 CPU、内存、磁盘 IO、网络和存储服务定位共享瓶颈，限制离线并发或迁移任务。

##### 知识点补充

计算集群隔离不代表完全隔离，Kafka、HDFS、Hive Metastore、对象存储和网络仍可能是共享瓶颈。需要联合监控并定义实时任务的资源保障、离线任务截止时间和降级策略。

##### 数据湖选型

Q：常见数据湖方案有什么优缺点，怎么选？
A：我不会只做 Iceberg、Hudi、Paimon 功能表，而会拿真实 CDC 数据做 POC。若场景是 Flink 每秒数万条订单更新、分钟级查询最新主键状态，我重点测试 Paimon/Hudi 的 upsert、changelog、compaction 和恢复；若多个 Spark、Trino、Flink 引擎共享超大离线表，则重点看 Iceberg 的快照、分区演进和生态兼容。POC 固定 1 TB 数据与更新比例，测持续写吞吐、查询 P95、小文件数、compaction 对前台的影响、并发 commit 冲突、Schema 演进和 checkpoint 恢复时间。还要验证对象存储、Catalog 高可用和版本升级。最终由核心 SLA 和团队运维能力决定，不宣称某个湖表全面最好。

##### 知识点补充

三者都通过表格式在对象存储或 HDFS 上提供事务快照、Schema/Partition 演进等能力，但实现和生态侧重点不同。COW 读快写放大较大；MOR 写入快，但查询可能承担合并成本。

##### 行式存储与列式存储

Q：行存和列存有什么区别，为什么分析系统通常选择列式存储？
A：行存把一行的各列连续组织，适合按主键读取或修改整行的 OLTP；列存把同一列的数据放在一起，分析查询只扫描需要的少数列，并且同类型值更容易做字典、RLE 等压缩和向量化执行。比如百列宽表只算地区和销售额，列存不必读取其余 98 列，I/O 会明显下降。但列存不擅长高频单行更新，写入通常需要批量和后台合并。实际架构中 MySQL 承担交易写入，Parquet/ORC 或 ClickHouse 承担分析，不会因为列存查询快就替换所有行存业务库。

##### 知识点补充

存储布局与执行引擎需要配合：列裁剪、谓词下推和向量化才能真正减少读取与 CPU。Parquet/ORC 是文件格式，ClickHouse MergeTree 是存储引擎，层次不同。

##### Hudi 增量入湖与流批衔接

Q：为什么使用 Hudi，实时写入和离线查询怎样衔接？
A：传统 Hive 分区适合追加，但订单状态更新、CDC 去重和近实时增量消费需要自己维护大量覆盖逻辑。Hudi 提供基于 record key、preCombine 字段和时间线的 upsert、事务提交、增量查询与回滚。实时链路可由 Flink 消费 Kafka/CDC 写 Hudi，离线 Spark/Hive 读取快照或增量视图；下游保存上次成功 commit，只消费后续变更。选 Copy-on-Write 时读简单但写放大较大，选 Merge-on-Read 时写入更快、读取需合并并依赖 compaction。落地还要设计分区、索引、并发写控制、小文件治理和 schema 演进，并做故障恢复验证。

##### 知识点补充

Hudi 不会自动解决所有流批一致性问题；源端重复、主键变化、迟到事件和下游提交仍需定义。选型要与 Iceberg/Delta 结合更新频率和引擎生态比较。

##### HDFS、Spark Streaming 与 Flink Checkpoint 对比

Q：HDFS 的可靠存储、Spark Streaming Checkpoint 和 Flink Checkpoint 有什么区别？
A：HDFS 通过 block 副本和 NameNode 元数据管理保证文件持久化，它是存储基础，不是计算状态快照机制。Spark Streaming checkpoint 把流查询元数据、进度或状态写到可靠文件系统，用于 Driver/状态恢复；Flink checkpoint 由 barrier 协调多个算子形成一致性快照，记录状态和 source 位点，并与事务或幂等 sink 组合实现端到端一致性。三者可以叠加：Spark/Flink 的 checkpoint 文件常存放在 HDFS，但恢复语义由计算引擎定义。生产设计会分别确定存储副本、快照间隔、保留、兼容升级和恢复时间，不能把“文件有三副本”等同于作业状态一定正确。

##### 知识点补充

Checkpoint 解决故障后的状态恢复，业务补数还需要原始数据保留和可重放链路。Savepoint、checkpoint 和普通 HDFS 备份的用途也不相同。

##### OLTP、OLAP 与可视化链路

Q：OLTP 和 OLAP 有什么区别，数据报表和可视化链路怎么设计？
A：OLTP 面向订单、账户等短事务，典型是高并发点查和小范围更新，要求主键索引、约束和强一致；OLAP 面向历史扫描、分组聚合和多维分析，偏列存、MPP、预聚合与批量写。可视化链路中，原始数据先经数仓统一口径，热点指标写 ClickHouse/Doris/Kylin 等服务层，BI 工具通过受控数据集和语义层查询，不直连业务 MySQL。看板按用户角色控制行列权限，设置刷新频率、查询超时和缓存，并显示数据截止时间。临时探索与固定大屏使用不同资源队列，避免一个全表查询拖垮所有报表。

##### 知识点补充

HBase 可支撑主键型报表明细查询，但不擅长任意多维聚合。BI 工具只是展示入口，性能主要由模型、存储和查询治理决定。

##### Kylin Cube 构建原理

Q：Kylin 如何直接构建 Cube，什么时候值得使用预计算？
A：先定义数据模型中的事实表、维度表和 Join，再选择维度、度量、分区列及聚合组。构建任务从 Hive/湖仓读取目标分区，生成不同维度组合的 cuboid，做字典编码、聚合并写入存储，完成后发布 segment，查询时把 SQL 映射到已预计算 cuboid。直接全量构建所有维度组合会产生维度爆炸，我会用 mandatory、hierarchy、joint dimension 等聚合组约束组合，并对高基数维度谨慎建 Cube。适合固定、高并发、低延迟多维报表；临时探索和维度频繁变化更适合现代 MPP OLAP。上线监控构建时长、膨胀率、segment 合并和查询命中。

##### 知识点补充

Cube 用空间和构建时间换查询速度。不同 Kylin 版本的存储和构建引擎差异较大，回答要说明实际版本。

##### Lambda 与 Kappa 架构

Q：Lambda 和 Kappa 架构有什么优缺点，实际怎样选择？
A：Lambda 保留批、流两条计算链，实时层先给低延迟结果，批层重算权威历史并校正，回溯清晰，但两套代码、口径和运维容易不一致。Kappa 以可重放日志为核心，只维护流计算，通过旧 offset 重放历史，链路更简单，但要求日志保留、回放隔离和下游版本化足够完善。我会根据延迟、历史规模、修订频率、团队能力和成本选择；现实常是混合架构，不能因为用了 Flink 就宣称完全 Kappa。

##### 知识点补充

流批一体不自动消除实时、离线资源和 SLA 差异。回放应写影子结果，避免污染在线输出。

##### 应用程序开发流程

Q：一个数据应用从需求到上线的完整开发流程是什么？
A：先澄清目标、用户、输入输出、SLA 和验收样例，再做数据探查与方案评审，明确接口、Schema、状态、容量、安全和回滚。开发使用版本控制、代码评审、单元及集成测试，在测试环境回放边界数据；上线前完成配置、权限、监控、操作手册和审批。发布采用灰度或影子双跑，对账功能、性能和资源后切流，异常按预案回滚。上线后观察完整业务周期并复盘，不能把“部署成功”当作交付完成。

##### 知识点补充

数据应用还要验证重跑幂等、历史补数和 Schema 演进。需求、代码、配置、SQL 与口径应关联到同一发布版本。

##### Hudi 与 Kudu 的区别

Q：Hudi 和 Kudu 都支持更新，它们的定位有什么不同？
A：Hudi 是构建在 HDFS/对象存储文件之上的湖表格式，通过提交时间线、索引和 Copy-on-Write/Merge-on-Read 提供增量写、upsert、回溯及多引擎读取，适合数据湖和批流摄取。Kudu 是独立分布式列式存储服务，由 Master/Tablet Server 管理，擅长低延迟随机更新和分析扫描，常与 Impala 配合，但需要运维专门集群。选择时我比较更新延迟、查询引擎、对象存储、运维和一致性需求；湖上多引擎历史数据偏 Hudi，频繁点更新且接受专有服务偏 Kudu。

##### 知识点补充

两者都不是传统 OLTP 数据库。Hudi 性能受小文件、compaction 和 clustering 影响，Kudu 受 tablet、主键和内存/磁盘布局影响。
