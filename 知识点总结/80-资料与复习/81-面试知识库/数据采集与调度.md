##### 数据采集与调度

##### Flume 负载均衡与 Kafka 组合

Q：Flume 如何做负载均衡？Flume+Kafka 和 Kafka+Flume 应该怎么选择？
A：Flume 一个 Source 可通过 Channel Selector 把事件复制或多路分发，多个 Sink 组成 Sink Processor 后可选 load balancing 或 failover；负载均衡按轮询/随机把批次发往下游，失败退避，failover 则按优先级切换。采集日志时常见 Agent→Kafka，让 Kafka 承担持久缓冲、多消费者和回放；若已有 Kafka 数据还需写 HDFS，可使用成熟 Kafka Connect/Flink，确需 Flume 时再用 Kafka Source→Channel→HDFS Sink。架构选择看是否需要可靠 channel、回放、转换和运维成本，不能为了组件齐全把 Flume 放在 Kafka 前后各一层。配置后用断网、下游慢和重启演练验证不丢不重边界。

##### 知识点补充

Flume Channel 是 Source 与 Sink 的可靠缓冲边界，Memory Channel 快但进程故障可能丢，File Channel 更可靠但 I/O 成本更高。

##### Maxwell CDC 原理

Q：Maxwell 如何采集 MySQL 变更，使用时有哪些限制？
A：Maxwell 以 MySQL replication client 身份读取 binlog，解析 row event，并结合表元数据把 insert/update/delete 转成 JSON 后写 Kafka 等下游。上线前 MySQL 开启 row 格式 binlog，给账号最小复制权限，并保证 server id、binlog 保留期和位点持久化。DDL 变化时要确认 Maxwell 元数据同步，新增字段下游使用兼容 Schema；大事务会形成突发消息，需监控延迟和 Kafka 写入。它提供的是变更捕获，不自动保证下游 exactly-once，消费端仍按数据库、表、主键和 binlog 位点做幂等与审计，断点恢复后进行行数和关键金额校验。

##### 知识点补充

CDC 事件顺序通常在单个 binlog 流内有意义，分发到多 Kafka 分区后要用业务主键保持同 key 顺序。全量初始化与增量衔接需单独设计。

##### DolphinScheduler 工作流实践

Q：DolphinScheduler 在离线数仓中怎么使用，怎样保证调度可靠？
A：我按数据依赖而不是固定时间堆任务：ODS 完成并通过质量检查后触发 DWD，随后是 DWS、ADS 和报表刷新。工作流参数化业务日期，任务保持幂等，重跑只覆盖目标分区；为每个节点配置超时、重试、失败告警、资源队列和负责人，跨日依赖明确使用数据日期。补数时创建独立 backfill 实例并限并发，避免抢占日常 SLA。Master/Worker、注册中心和元数据库做高可用，监控工作流成功率、等待时间和最长路径。外部系统调用保留返回码和日志，不把“Shell 执行成功”当成数据正确。

##### 知识点补充

调度成功只表示进程退出码正常，仍需分区到达、行数、唯一性和金额等数据质量门禁。工作流版本和上线变更要可审计、可回滚。

##### Schema 变更与不停机接入

Q：新增数据源或字段格式变化时，怎样做到链路尽量不停机？
A：先把 Schema 当成契约管理。新增可空字段通常采用向后兼容：生产者先发布新 Schema，消费者按未知字段忽略并给默认值，所有消费者升级后再开始依赖该字段；字段改类型或删除采用“新增字段—双写—回填—切读—停止旧字段”的多阶段迁移，不能原地破坏。Kafka 使用 Schema Registry 或自建版本中心，Flink 反序列化对坏数据侧路并告警，湖仓表验证 schema evolution，OLAP 下游先加列。灰度期间比较新旧链路行数和关键指标，保留回滚开关；无法兼容的变更使用新 Topic/表版本并安排历史回放。

##### 知识点补充

不停机不等于无风险。兼容性要同时覆盖序列化格式、状态 Schema、Savepoint、表 DDL 和下游查询，任何一层不兼容都可能阻断恢复。

##### DataX、Sqoop 与数据迁移选择

Q：数据导入导出和迁移用过哪些工具，如何保证迁移结果可靠？
A：关系库与 HDFS/Hive 的离线批量迁移，老项目可用 Sqoop 按主键或时间字段切分并行导入；异构数据库、文件和数仓间同步常用 DataX，通过 reader/channel/writer 控制并发、批次和限速；持续增量则优先 binlog CDC、Kafka Connect 或 Flink CDC，而不是频繁全表扫。迁移前做字段类型、主键、NULL、时区和编码映射，先小批压测，避免并发查询拖垮源库。执行后校验源目标行数、主键去重、分区、最大更新时间和金额等业务总量，失败批次可按水位幂等重跑，并保存审计报告。

##### 知识点补充

工具只负责搬运，无法替代数据口径和删除语义设计。按主键范围切分前要检查分布，避免自增键空洞或热点导致任务倾斜。

##### Azkaban 调度、重跑与文件导出

Q：Azkaban 除了 HQL 还能调度什么？任务失败重跑如何避免重复，怎样把中间表导出到本地？
A：Azkaban 本质按依赖执行 job，可调 Shell、Java、Spark、数据同步、质量检查和通知，不只运行 HQL。我会把业务日期作为参数，每个任务先写临时分区，校验成功后原子替换目标分区；失败重跑同一日期不会 append 出重复数据。需要导出中间表时，由受控 Shell/Hive 任务写到 HDFS 临时目录，再用 `hdfs dfs -get` 拉到有权限的执行节点，文件很大则合并或压缩，并登记路径、校验和与自动清理，不直接下载到个人机器。工作流配置超时、重试次数、失败回调和负责人，重跑前判断上游数据是否完整。

##### 知识点补充

调度器只保证任务编排，幂等由任务本身实现。生产导出要遵守权限和脱敏，不把敏感中间表作为普通附件传输。

##### Flume HDFS 滚动与零点漂移

Q：Flume 从 Kafka 写 HDFS 时如何控制文件滚动，并处理跨零点文件落错分区？
A：HDFS Sink 可按时间 `rollInterval`、大小 `rollSize`、事件数 `rollCount` 任一条件滚动，通常关闭不需要的条件并让目标文件达到 128MB 左右，避免小文件；具体参数属于 Flume HDFS Sink，不是 HDFS 服务端参数。目录分区应基于事件中的业务时间，而不是 Sink 当前机器时间。采集端解析事件时间写入 header，HDFS path 使用该 header；无法信任客户端时间时使用服务端接收时间并保留原值。跨零点仍迟到的数据写回正确日期的待合并目录，后续 compaction 和分区修复处理，不用拦截器简单篡改全部时间。

##### 知识点补充

文件滚动过快产生小文件，过慢则可见延迟和故障重传窗口增大。临时文件后缀和 close/rename 流程也要纳入下游到达判断。

##### Maxwell 单进程瓶颈与高可用

Q：Maxwell 是单进程吗，数据量增大后有什么风险，怎样扩展和恢复？
A：单个 Maxwell 实例通常顺序读取一个 MySQL binlog 流并维护位点和 Schema，单进程能保持源端顺序但吞吐受解析、序列化和 Kafka 写入限制。数据量增大时会出现 binlog lag、内存压力和大事务阻塞，不能对同一 binlog 随意启动两个实例并行消费。扩展通常按 MySQL 实例/业务库拆采集任务，Kafka 端再按主键分区；优化 producer 批次、压缩和异步发送，同时确保 binlog 保留期覆盖最坏停机。HA 使用同一 client/server identity 和持久化位点的主备切换，切换后下游按主键与 binlog position 幂等。

##### 知识点补充

具体版本号只能回答实际项目使用版本，不能编造。大事务即使总 QPS 不高也会造成长时间延迟，应单独监控 transaction size。

##### Flume 从 Kafka 落 HDFS

Q：Flume 如何把 Kafka 数据可靠采集到 HDFS？
A：配置 Kafka Source 订阅明确 Topic 和 consumer group，事件先写 Channel，再由 HDFS Sink 批量写目标目录；File Channel 能承受进程重启，Memory Channel 延迟低但故障语义较弱。HDFS path 使用事件业务时间 header 分区，文件按大小/时间滚动并使用临时后缀，关闭后 rename，避免下游读到未完成文件。Kafka offset 的提交与 Channel 成功接收绑定，但端到端仍可能重试，因此下游按 event_id/源位点去重。上线压测 source batch、channel 容量、sink 并发和 HDFS 吞吐，监控 lag、channel fill、sink error、小文件数，并演练 HDFS 不可用后的恢复。

##### 知识点补充

现代架构也可用 Kafka Connect、Flink 或专用摄取服务落湖。选择 Flume 应基于现有运维能力和可靠性验证，而非惯性。

##### ODS 日志乱序与可追溯写入

Q：日志采集到 ODS 时如何处理乱序，是否要在采集阶段排序？
A：ODS 通常不做全局排序，而是原样保存 event_time、ingest_time、event_id、source partition/offset 和 Schema 版本，按业务日期或接收日期落盘。采集阶段只做格式校验和传输级去重，乱序由 DWD/Flink 按事件时间、Watermark 和版本处理；极晚跨分区数据进入补录目录并触发受影响日期重算。若直接按客户端日期落目录，要校验时钟漂移，异常时间使用接收日隔离，防止写到未来或过旧分区。质量监控比较事件时间与接收时间分布、迟到率和分区到达完整性。

##### 知识点补充

分布式采集无法低成本保证全局顺序。保留源位点和双时间，才能在下游确定顺序并重放修正。

##### Flume 可靠性、监控与自动恢复

Q：Flume 怎样防止丢数据？生产中监控和自动化怎么做？
A：我使用事务型 channel，Source 写入和 Sink 取出都通过事务提交；核心链路优先 File Channel，容量按峰值流量和下游最长故障时间估算，磁盘独立并预留空间。Sink 到 Kafka/HDFS 失败时让事务回滚重试，不能用 Memory Channel 承诺进程崩溃不丢。监控 channel fill percentage、put/take 成功失败、Sink 延迟、文件句柄、JVM 和磁盘，连续阈值触发告警。进程由 systemd 拉起，但反复崩溃要熔断并保留日志，恢复后用源文件位置或 Kafka 位点核对补采。

##### 知识点补充

Flume 的事务只覆盖自身 Source-Channel-Sink 交接，端到端仍取决于源可重放和下游幂等。拦截器失败、错误滚动配置和磁盘满也是常见丢数来源。

##### DataX 执行原理与性能调优

Q：DataX 如何同步数据？速度慢时你会调哪些地方？
A：DataX 把作业拆成 Reader、Channel、Writer，先按 splitPk 等方式切分读取任务，再由多个 channel 并发传输到写端。调优先确定瓶颈在源库、网络还是目标库，再调整 channel 数、byte/record speed、fetchSize 和 writer batchSize；并发不能超过源库连接和目标写入承载，避免把同步任务变成生产库事故。全量任务固定快照或时间边界，增量用更新时间加主键作为复合游标，目标侧按主键幂等。失败记录、脏数据和行数/金额对账必须纳入调度闭环。

##### 知识点补充

DataX 本身不提供通用 CDC 语义，增量边界和删除捕获需要额外设计。切分键应分布均匀且可索引，否则会出现单通道拖尾。

##### Maxwell 生产参数与故障恢复

Q：Maxwell 接入 MySQL binlog 时需要配置什么？如何保证断点恢复？
A：源库开启 ROW 格式 binlog，为 Maxwell 创建最小权限账号，并配置 host、port、database/table filter、producer、Kafka topic、分区键和失败策略。Maxwell 把当前 binlog file/position 或 GTID 持久化到自己的 schema，重启后从该位置继续；所以元数据库必须高可用和备份，binlog 保留期要覆盖最长停机时间。消息携带 database、table、type、data、old、ts 和业务主键，下游按源位点/event_id 幂等。上线会演练进程中断、Kafka 不可用、DDL 和大事务，验证是否重复或遗漏。

##### 知识点补充

Maxwell 主要采集增量，历史全量需独立初始化并明确切点。GTID、时区和 DDL 兼容都要以实际 MySQL/Maxwell 版本验证。

##### Flume Channel Selector

Q：Flume 的 Channel Selector 有哪些，如何在复制和负载均衡之间选择？
A：Replicating Selector 会把同一 Event 复制到所有选中的 Channel，适合一份数据同时走实时 Kafka 和离线 HDFS；Multiplexing Selector 根据 Header 值路由到指定 Channel，适合按业务类型分流。它不是轮询负载均衡器，多个同用途 Sink 的负载与容灾通常用 Sink Processor。落地时由 interceptor 先写入可靠路由 header，再配置 default channel 接住未知值；任一路径故障是否阻塞主链路要通过 optional channel、容量和失败策略明确，不能默认为“复制就互不影响”。

##### 知识点补充

Selector 位于 Source 到 Channel 之间，Sink Processor 位于多个 Sink 之间。复制会放大存储和网络，容量按每条支路峰值计算。

##### TaildirSource 断点续传

Q：Flume TaildirSource 如何记录文件偏移，轮转后会不会重复或漏采？
A：TaildirSource 按 filegroup 的路径匹配文件，通过 inode 和 offset 在 positionFile 的 JSON 中记录读取位置，重启后继续；positionFile 必须放在持久、可写且被监控的磁盘。日志轮转时只改名通常 inode 不变，可以继续读完；copy-truncate 或文件被快速删除可能造成重复/遗漏，所以我会选兼容轮转策略、延迟清理旧文件，并用 event_id 或源文件+偏移做下游去重。上线监控 positionFile 更新时间、源文件积压、读取速率和异常 inode，变更匹配规则前先备份位点。

##### 知识点补充

TaildirSource 适合持续追加文本，不等于任意文件采集器。容器环境 inode 与临时盘行为复杂，需验证挂载和重建后的位点连续性。

##### 采集异常补数闭环

Q：采集链路中断后怎样补数，如何避免补数与实时流重复？
A：先确定缺口的源系统、业务时间、源位点和受影响下游，冻结错误结果或打版本标记。若源文件可重放，就从保存的文件偏移重采；数据库用全量快照加 CDC 切点；Kafka 用独立消费组从指定 offset/time 回放。补数写影子分区或携带 repair_version，按业务主键/event_id 去重，对账记录数、金额、首末时间和空值后再覆盖受影响分区或发布修订。实时链路继续运行时划定互斥时间区间，不能让实时和补数同时无版本写正式表。

##### 知识点补充

补数能力依赖源保留期、位点和幂等设计，应在故障前演练。完成后更新血缘影响、告警关闭原因和复盘行动项。
