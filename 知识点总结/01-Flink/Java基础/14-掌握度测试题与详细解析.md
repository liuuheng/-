# 14 掌握度测试题与详细解析

## 1. 如何使用这套题

这不是背诵题清单。目标是判断你是否真正理解了 Java 特性与 Flink 场景之间的关系。

建议按以下方式完成：

1. 先关闭答案区域，独立作答。
2. 每道题不仅给结论，还要说出原因。
3. 代码题先判断是否能编译，再判断运行时是否可靠。
4. 完成后对照解析，将答错的问题链接回对应章节复习。

评分参考：

| 分数 | 状态 | 建议 |
| --- | --- | --- |
| 0-14 | 基础仍不稳定 | 按 README 顺序重新学习 |
| 15-22 | 可以开始 DataStream 入门 | 边练习边回查笔记 |
| 23-27 | Java 基础已比较扎实 | 开始状态、时间和窗口 |
| 28-30 | 理解较完整 | 进入实战并持续查漏补缺 |

每题 1 分。回答出结论但无法解释原因，最多算半分。

## 2. 第一组：概念口述题

先回答，再展开解析。

### 题目 1

`Order second = first;` 是否创建了新的订单对象？修改 `second` 会不会影响 `first`？

<details>
<summary>查看解析</summary>

不会创建新对象。`first` 和 `second` 保存的是同一个对象引用。

```java
Order first = new Order("u-1", 20.0);
Order second = first;
second.setAmount(80.0);
```

此时 `first.getAmount()` 也会得到 `80.0`。

这也是为什么不应该反复修改并返回同一个事件对象。

复习：[[01-类、对象、封装与不可变性]]
</details>

### 题目 2

不可变对象通常更安全，为什么 Flink 1.17 的事件对象又常写成有无参构造方法和 setter 的 JavaBean？

<details>
<summary>查看解析</summary>

不可变对象更容易推理，也更适合并发读取。但 Flink 1.17 要高效识别普通 POJO，通常需要公开无参构造方法和可写字段。

反序列化可以粗略理解为：

```java
Order order = new Order();
order.setUserId("u-1");
```

因此，事件对象常使用 JavaBean。降低风险的关键是：不要不必要地共享和复用同一个可变对象。

复习：[[01-类、对象、封装与不可变性]]、[[06-POJO、JavaBean、Tuple与序列化]]
</details>

### 题目 3

`MapFunction<String, Order>` 中的两个类型参数分别代表什么？

<details>
<summary>查看解析</summary>

第一个是输入类型，第二个是输出类型。它描述：

```java
Order map(String value)
```

即输入一条字符串，输出一个订单对象。

复习：[[02-接口、抽象类、继承与多态]]
</details>

### 题目 4

`map`、`filter` 和 `flatMap` 最核心的区别是什么？

<details>
<summary>查看解析</summary>

看一条输入产生多少条输出：

| 算子 | 输出数量 |
| --- | --- |
| `map` | 恰好一条 |
| `filter` | 零条或一条 |
| `flatMap` | 零条、一条或多条 |

一行文本拆成多个单词用 `flatMap`；订单提取用户 ID 用 `map`；只保留大额订单用 `filter`。

复习：[[03-Lambda、函数式接口与方法引用]]
</details>

### 题目 5

`keyBy(Order::getUserId)` 是否已经完成了金额聚合？

<details>
<summary>查看解析</summary>

没有。`keyBy()` 只负责按照 key 重新分区，使相同用户的数据进入同一个逻辑分组。

还需要后续聚合算子：

```java
orders
    .keyBy(Order::getUserId)
    .reduce(...);
```

复习：[[03-Lambda、函数式接口与方法引用]]
</details>

### 题目 6

Java Stream API 与 Flink DataStream API 都有 `map()`，它们是否只是运行位置不同？

<details>
<summary>查看解析</summary>

不只是运行位置不同，执行模型也不同。

- Java Stream 通常处理当前 JVM 中已有的有限集合。
- Flink DataStream 描述分布式数据流计算，数据可以持续到达，并由 `env.execute()` 触发执行。
- Flink 还涉及网络传输、状态、Checkpoint、事件时间和并行执行。

复习：[[05-集合、Stream-API与DataStream的区别]]
</details>

### 题目 7

Java 泛型擦除是什么？为什么 Flink 特别关心这个问题？

<details>
<summary>查看解析</summary>

Java 泛型主要服务于编译期。运行时，很多泛型参数会被擦除：

```java
List<String>
List<Integer>
```

运行时通常都只是 `ArrayList`。

Flink 需要知道准确类型，以选择序列化器、进行网络传输、保存状态和恢复 Checkpoint。因此复杂泛型结果有时需要显式补充 `TypeHint`。

复习：[[04-泛型、类型擦除与Flink类型信息]]
</details>

### 题目 8

实现了 `java.io.Serializable`，是否意味着 Flink 一定会把类识别为 POJO？

<details>
<summary>查看解析</summary>

不意味着。

`Serializable` 表示对象允许使用 Java 序列化机制处理。Flink POJO 识别还有自己的规则，例如公开类、公开无参构造方法、字段可写等。

如果不符合规则，Flink 可能把它当作通用类型并回退到 Kryo。

复习：[[06-POJO、JavaBean、Tuple与序列化]]
</details>

### 题目 9

为什么外部数据库客户端常放在 RichFunction 的 `open()` 中创建，而不是在客户端提前创建后通过 Lambda 捕获？

<details>
<summary>查看解析</summary>

提前创建后捕获客户端对象，会让 Flink 尝试将其随函数一起序列化并分发。客户端通常包含连接、线程池或 Socket，不适合序列化。

在 `open()` 中创建，意味着资源在真正执行算子的 TaskManager 端初始化。通常还要在 `close()` 中释放。

复习：[[07-异常处理、脏数据与资源管理]]、[[08-内部类、static、final与闭包捕获]]
</details>

### 题目 10

为什么普通 `HashMap<String, Double>` 不适合替代 Flink State API 保存用户累计金额？

<details>
<summary>查看解析</summary>

普通 `HashMap` 只存在于当前 JVM 内存中：

- 故障后无法自动恢复。
- 不会自动进入 Checkpoint。
- 调整并行度时无法按 key 迁移。
- 多个 TaskManager 之间不会自动共享。

业务状态应使用 Flink 托管状态。

复习：[[09-并发、线程安全与Flink状态意识]]
</details>

## 3. 第二组：判断代码是否可靠

### 题目 11

下面的代码是否可靠？

```java
public class ParseOrder
        implements MapFunction<String, Order> {

    private final Order reusable = new Order();

    @Override
    public Order map(String line) {
        String[] fields = line.split(",");
        reusable.setUserId(fields[0]);
        reusable.setAmount(
            Double.parseDouble(fields[1]));
        return reusable;
    }
}
```

<details>
<summary>查看解析</summary>

不推荐。每次返回的是同一个可变对象引用。后续数据到达时，旧对象内容会继续变化，可能污染下游正在使用的数据。

更清晰的写法：

```java
return new Order(
    fields[0],
    Double.parseDouble(fields[1])
);
```

复习：[[01-类、对象、封装与不可变性]]
</details>

`Integer` 自动拆箱为 `int` 时，相当于调用：

### 题目 15

下面的类一定会被 Flink 1.17 识别为 POJO 吗？

```java
public class Order {
    private final String userId;
    private final double amount;

    public Order(String userId, double amount) {
        this.userId = userId;
        this.amount = amount;
    }
}
```

<details>
<summary>查看解析</summary>

通常不会被识别为标准 Flink POJO。它没有公开无参构造方法，字段为 `final`，也不可通过 setter 写入。

不可变设计本身没有问题，但需要意识到它不符合 Flink 1.17 常规 POJO 识别方式，可能走其他序列化路径。

复习：[[06-POJO、JavaBean、Tuple与序列化]]
</details>

### 题目 16

下面的代码是否意味着所有并行子任务共享一个全局统计 Map？

```java
private static final Map<String, Double> TOTALS =
    new HashMap<>();
```

<details>
<summary>查看解析</summary>

不是。

`static` 只保证在当前 JVM 和当前类加载器范围内属于类。多个 TaskManager JVM 仍会拥有不同副本。它也不会自动进入 Checkpoint。

复习：[[09-并发、线程安全与Flink状态意识]]
</details>

### 题目 17

下面的 Lambda 捕获方式有什么风险？

```java
SomeClient client = new SomeClient();
orders.map(order ->
    client.query(order.getUserId()));
```

<details>
<summary>查看解析</summary>

Lambda 捕获了 `client`。Flink 分发函数时，需要处理被捕获对象。客户端对象可能不可序列化，也不应该直接从提交作业的机器搬到 TaskManager。

应使用 RichFunction，在 `open()` 中初始化。外部调用耗时较长时还要考虑 Async I/O。

复习：[[08-内部类、static、final与闭包捕获]]
</details>

### 题目 18

下面的写法是否精确表示十进制金额 `0.1`？

```java
BigDecimal amount = new BigDecimal(0.1);
```

<details>
<summary>查看解析</summary>

不推荐。`0.1` 先被表示为二进制浮点数，再传给 `BigDecimal`，浮点误差会被保留下来。

更合适：

```java
BigDecimal amount = new BigDecimal("0.1");
```

复习：[[13-容易漏掉但高频的Java细节]]
</details>

### 题目 19

下面代码中，`open()` 在整个作业生命周期中只执行一次吗？

```java
public class EnrichOrder
        extends RichMapFunction<Order, Order> {

    @Override
    public void open(Configuration parameters) {
        ...
    }
}
```

<details>
<summary>查看解析</summary>

不是。它通常在每个并行算子实例初始化时调用一次。

如果并行度是 4，通常会存在 4 个算子实例，各自调用自己的 `open()`。故障恢复或重新部署时，也可能再次初始化。

复习：[[02-接口、抽象类、继承与多态]]
</details>

### 题目 20

下面的 `split()` 为什么可能漏掉最后一个空字段？

### 题目 27

下面代码输出什么？

final List<String> users = new ArrayList<>();

```

<details>
<summary>查看解析</summary>

输出：

1
```

### 题目 28

下面代码中，为什么可能需要 `.returns(...)`？

```java
lines.map(line -> Tuple2.of(line, 1));
```

<details>
<summary>查看解析</summary>

返回值是带泛型参数的 `Tuple2<String, Integer>`。受 Java 类型擦除和 Lambda 类型提取限制影响，Flink 有时无法在运行时可靠推断完整类型。

可以显式补充：

```java
.returns(
    new TypeHint<Tuple2<String, Integer>>() {}
)
```

复习：[[04-泛型、类型擦除与Flink类型信息]]
</details>

### 题目 29

下面代码能否保证线程安全？

```java
private volatile int count = 0;

public void increment() {
    count++;
}
```

<details>
<summary>查看解析</summary>

不能。

`volatile` 主要保证可见性，但 `count++` 包含读取、加一和写回多个步骤，不是原子操作。多线程同时执行时仍可能丢失更新。

可以根据场景考虑 `synchronized` 或 `AtomicInteger`。

复习：[[09-并发、线程安全与Flink状态意识]]
</details>

### 题目 30

为什么只写下面代码通常不会真正启动 Flink 作业？

```java
DataStream<String> result =
    source.map(String::toUpperCase);
```

<details>
<summary>查看解析</summary>

这通常只是在构建计算拓扑。还需要触发执行：

```java
env.execute("job-name");
```

Flink DataStream API 的链式调用主要用于描述数据如何处理，`env.execute()` 才负责启动或提交作业。

</details>

## 6. 最终实战题

不要立刻看解析。先独立设计。

### 题目 31：设计一个订单解析与统计流程

输入：

```text
o-1,u-1,PAID,20.50
o-2,u-2,CREATED,80.00
bad-line
o-3,u-1,PAID,40.00
```

要求：

1. 只统计 `PAID` 订单。
2. 金额不能使用 `double` 表示真实结算值。
3. 脏数据不能悄悄丢弃。
4. 按用户累计金额。
5. 说明事件对象、业务状态和外部资源分别如何管理。

<details>
<summary>查看参考解析</summary>

可以采用以下设计：

1. 使用 `Order` POJO 表示事件，提供公开无参构造方法、getter 和 setter，便于 Flink 1.17 识别。
2. 使用 `OrderStatus` 枚举表示状态，而不是任意字符串。
3. 金额使用以分为单位的 `long`，或者使用 `BigDecimal`。如果使用 `long`，`20.50` 解析为 `2050L`。
4. 使用 `ProcessFunction` 或合适的解析逻辑将脏数据发送到侧输出流，同时记录异常原因和指标。
5. 使用：

```java
orders
    .filter(order ->
        order.getStatus() == OrderStatus.PAID)
    .keyBy(Order::getUserId)
```

6. 简单累计可使用 `reduce()`；复杂逻辑使用 keyed state，例如 `ValueState<Long>`。
7. 不要使用普通 `HashMap` 保存累计金额。
8. 如果需要查询外部系统，使用 RichFunction 的 `open()` 初始化客户端，`close()` 释放资源。慢请求进一步使用 Async I/O。

这道题串联了对象设计、枚举、金额精度、异常处理、侧输出流、`keyBy()`、状态和资源生命周期。
</details>
