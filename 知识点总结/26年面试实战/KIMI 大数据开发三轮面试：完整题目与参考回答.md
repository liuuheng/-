## 补充面试回答

以下使用可直接展开回答的表达方式。带“可采用”“参考设计”的内容是方案推演；涉及本人经历的题目给出回答方法与取证要求。

### B1 自我介绍、最深项目与职责边界

自我介绍围绕目标岗位组织：当前负责什么业务和系统，做过哪个能说明能力的项目，自己完成了哪些模块，这次希望承担什么工作。介绍项目时交代数据从哪里来、服务谁、为什么原方案不满足要求，再说明本人设计、编码、上线和维护的部分。团队成果和个人贡献分别说清，例如“我负责采集与处理链路，查询服务由同事负责，我参与接口契约和联调”。没有独立承担的模块，不用“主导”代替“参与”。

讲最深项目时，选能经得住追问的案例。以血缘系统为例，可以从某次表变更导致下游任务失败切入，解释原来为什么找不全依赖、如何补充运行时证据、怎样处理误报和链路延迟。难点必须落在具体冲突上，例如增加运行时采集覆盖会带来性能和稳定性成本；随后说明选项、取舍、验证和剩余缺口。只说“数据量大、需求复杂”无法说明判断能力。

“工程建设还是数据治理”不必二选一。工程建设指采集、处理、存储、服务、监控等实现；治理指资产责任、口径、质量、安全和成本规则。回答应说明交付了哪套工程能力，它执行了哪些治理规则，结果由什么指标验收。主要做离线或实时，也应按实际投入、独立负责模块和故障经验回答，避免把接触过的组件都称为精通。

准备面试前至少核实这些事实：负责范围及协作人，线上版本，数据范围与统计日期，优化前后同口径结果，个人提交或设计记录，故障处理和后续维护。无法核实的数字可以明确说尚未统计；不要用原文数字填空。

### A12 真正负责什么？项目最困难的部分怎么回答？

参考回答方法：按可验证的模块边界讲自己的工作。例如确实负责语义检索，就讲清输入如何清洗、索引怎样构建、候选怎么融合、歧义怎么处理、结果交给谁，以及自己改过什么和怎样验证。平台整体架构可以介绍，但同事负责的意图识别、模型微调和前端界面要明确归属，不能把“接入过调用”扩成“独立建设整个系统”。

难点应选实际发生且有闭环证据的问题。可讨论的技术问题是“SQL 能运行，但关联扩行导致金额重复”，回答应包含错误如何出现、怎样定位到粒度与基数、如何修改语义约束、怎样补充反例并回归验证。若本人没有这段经历，就将它作为方案理解，不能照背为项目成果。

评价收益时区分意图识别、选表、SQL 可执行和结果语义正确，并给出测试集范围、分母、基线和失败样例。高可执行率不能证明正确取数；用模型评价也需要抽样人工复核。没有原始记录时，不能把别人的提升比例填进自己的项目回答。

追问实现细节时，最好拿一条脱敏运行记录讲清：本人负责的模块收到什么协议，产出什么结果，哪项校验由代码执行，哪项由模型判断，错误怎样进入下一轮。A0 可用于解释方案，但不能充当个人上线记录；如果只负责 Execute，就讲编译、鉴权、查询与结果契约，并明确 Plan 和语义维护由谁负责。

### A0 完整案例：为什么上周 GMV 下降

Plan 决定为回答问题还需收集什么证据，Execute 把这些步骤转成受约束的工具调用，Reflect 按原问题检查证据是否足够，Report 将已经验证的结论交给用户。语义层在这些节点之间持续约束指标、表字段、关联关系和时间，不能只在第一次检索时使用一次。

下面是为面试编写的完整教学案例，业务、表名、版本、运行记录和金额均为构造值。案例数值已用本地数据核对，但没有实际调用模型或远程数仓。它展示一套可采用的设计，不代表原文当事人或 Kimi 的实现。

#### 1．先把“上周”和“GMV”变成可以计算的约定

假设当前日期是 2026-11-16，用户问：“为什么上周 GMV 下降？”系统识别出这是指标变化分析，而非只查询一个数字。此时“下降”仍是用户的判断，必须先取数核实；“上周”也不能直接解释成最近七天。

检索返回两个候选：支付口径 `gmv_paid@v3` 与下单口径 `gmv_created@v2`。如果当前会话没有已确认的口径，系统先澄清：“按支付成功金额，比较上一个完整自然周和再前一周，可以吗？”假定用户确认后，确定时区为 `Asia/Shanghai`，比较期为 `[2026-11-09, 2026-11-16)`，基准期为 `[2026-11-02, 2026-11-09)`，两个区间均包含七个完整自然日。

本例的支付 GMV 是人民币支付成功订单的支付金额之和，不扣除后续退款；测试单已在上游标准事实层排除。退款后净额是另一个指标，不能在生成 SQL 时随意加减。渠道采用下单时已经确定的归因渠道；它决定如何分组，支付日期决定金额计入哪一周，两者的职责不同。

系统读取一个固定、已发布的教学快照 `demo_snapshot_20261116_0900`。数据就绪检查确认两周的日分区齐全，支付记录已按约定延迟到齐，金额无异常空值，订单粒度唯一。“分区存在”只是一项条件，不代表数据已经完整；真实系统还需要上游发布标记、源端对账和迟到数据约定。

#### 2．语义层给出定义、物理映射与校验条件

本例订单事实表 `dwd_order_paid_snapshot` 在同一租户、同一快照内一单一行，已经将重复回调与拆分支付整理为订单支付事实。`paid_amount_fen` 是整数分，`paid_date` 是由支付时间按北京时间派生的日期，分区 `dt` 与该日期一致。这些都是输入契约；如果拿到的是多次支付尝试流水，就必须先改变事实层处理，不能直接用同样的 SUM。

下面是本案例自定义的 YAML 协议，表示语义层可以保存哪些信息；它不是可直接复制到 dbt 的配置：

```yaml
semantic_version: commerce_semantics_v7
model:
  id: order_paid
  table: dwd_order_paid_snapshot
  grain: one_row_per_paid_order_per_tenant_per_snapshot
  unique_key: [tenant_id, snapshot_id, order_id]
  time_dimension:
    field: paid_date
    derived_timezone: Asia/Shanghai
    partition_field: dt
    partition_contract: dt_equals_paid_date
metrics:
  gmv_paid@v3:
    expression: SUM(paid_amount_fen)
    storage_unit: CNY_fen
    display_unit: CNY_yuan
    display_divisor: 100
    fixed_filters: {payment_status: SUCCESS, currency: CNY}
    refund_policy: do_not_subtract_later_refunds
  paid_orders@v1:
    expression: COUNT(*)
    fixed_filters: {payment_status: SUCCESS, currency: CNY}
    cohort: same_filtered_order_set_as_gmv_paid
    prerequisite: order_unique_key_validated
  paid_aov@v1:
    expression: gmv_paid@v3 / paid_orders@v1
    storage_unit: CNY_fen_per_order
    display_unit: CNY_yuan_per_order
    display_divisor: 100
    zero_denominator: return_null
dimensions:
  order_channel:
    source_field: channel_id
    attribution: captured_at_order_creation
    label_model: dim_channel_snapshot
    label_version: channel_v2
    join_type: left
    join_keys: [tenant_id, channel_id]
    cardinality: many_orders_to_one_channel
    unmatched_label: 未知渠道
checks:
  - data_release_and_reconciliation_passed
  - order_key_unique_and_amount_not_null
  - channel_key_unique_within_tenant_and_label_version
  - channel_breakdown_reconciles_to_total
```

指标、维度和实体关联可以组织为可查询的语义模型图；dbt 的语义模型与 Join 规则提供了现有实现的参照，但这里选用的字段协议是教学设计。[dbt 语义模型](https://docs.getdbt.com/docs/build/semantic-models)、[dbt Join 约束](https://docs.getdbt.com/docs/build/join-logic)

语义服务将用户说的“GMV”绑定到 `gmv_paid@v3`，将“渠道”绑定到 `order_channel`，再返回允许使用的物理字段和维表版本。检索只负责找到候选定义，不能凭相似度决定两个口径等价。代码还要验证关联键唯一、金额单位一致以及查询范围有权限。

本例 Join 渠道维表只为取渠道名称，必须限定 `channel_v2`，保证一笔订单最多匹配一条名称。若事实表已经包含正确名称，就可以省去这次 Join。维表出现两条相同键时，应让数据校验失败，不能用 `DISTINCT` 掩盖金额被放大的问题。

#### 3．Plan：保存目标，再生成可以分阶段执行的 Playbook

Plan 的输入包括原问题、已经确认的口径和时间、服务端注入的授权范围，以及语义服务返回的定义。输出有两层：查询意图描述“要什么”，Playbook 描述“怎样取证”。[[知识点总结/26年面试实战/KIMI 大数据开发三轮面试：完整题目与参考回答#A2 自然语言如何转成结构化协议？Playbook 怎么设计？|A2 的 JSON]]给出了本例的协议对象。

计划第一版先执行 `s1` 数据就绪校验和 `s2` 两周总量比较，再进入检查点。它从一开始就保存三个验收要求：变化是否真实存在，变化贡献是否能对账，业务原因是否有证据或明确缺口。后续分支尚未执行，不代表已经取消；若查出 GMV 没有下降，应直接纠正前提，不能继续编造下降原因。

Playbook 的步骤依赖用稳定 ID 表达，例如 `s2` 依赖 `s1` 通过；只有确认下降后，才展开渠道分解。查询次数、总时限和反思次数有预算，同一步重试保留 attempt 与查询引用。一个步骤修改 SQL 或口径后，旧结果不能直接当作新步骤结果复用。

#### 4．Execute：语义绑定后编译 SQL，返回带证据的结果

Execute 收到的是指标与维度 ID，不能直接相信模型输出的表名。编译器根据同一个语义版本绑定表字段、补入指标固定条件，执行网关再注入租户权限、快照与扫描范围。语法解析、只读检查、字段和关联校验通过后，才把 SQL 交给数仓；扫描超过预算或缺少权限时，应返回可分类错误。

首次查询完成后，工具输出需要带 `step_id`、状态、结果引用、结果 Schema、金额单位、查询引用、语义版本、快照、质量检查和缺口。Report 不应只拿到“GMV 下降了”这段自然语言，因为它无法据此追查分母、金额单位和数据版本。结果集可以保存在受控存储中，节点间只传引用与必要摘要。

假定 `s2` 返回基准期 GMV 100 万元、支付订单 10000 单，比较期 GMV 80 万元、支付订单 8000 单；两期支付客单价均为 100 元。到这里，只能确认 GMV 下降 20 万元，即 20%。`s2.status=succeeded` 表示这条查询成功，不表示整次问题已经回答完成。

#### 5．Reflect：为什么第一次要继续取数，第二次仍不能声称找到根因

第一次 Reflect 将原目标与证据逐项比对：数据就绪已确认，总量下降已确认，但没有维度贡献，因而输出 `decision=needs_more_evidence`、`gap=missing_breakdown`。它把这个缺口交给 Plan，要求追加渠道分解；不是再次询问模型“你觉得答案好吗”。确定性程序负责日期、单位、加总和字段检查，模型负责判断回答是否回应了用户的问题。

收到这个缺口后，Plan 第二版增加 `s3` 渠道分解，继续复用相同语义版本和数据快照。下面是这一步可以编译出的完整 Spark SQL 3.5 教学示例；表结构由本节定义，示例没有在 Spark 集群执行：

```sql
WITH scoped_orders AS (
    SELECT
        order_id,
        channel_id,
        paid_amount_fen,
        CASE WHEN paid_date < DATE '2026-11-09'
             THEN 'baseline' ELSE 'current' END AS period
    FROM dwd_order_paid_snapshot
    WHERE tenant_id = 'demo_shop'
      AND snapshot_id = 'demo_snapshot_20261116_0900'
      AND dt >= '2026-11-02' AND dt < '2026-11-16'
      AND paid_date >= DATE '2026-11-02'
      AND paid_date < DATE '2026-11-16'
      AND payment_status = 'SUCCESS'
      AND currency = 'CNY'
)
SELECT
    o.period,
    COALESCE(c.channel_name, '未知渠道') AS channel,
    SUM(o.paid_amount_fen) AS gmv_fen,
    COUNT(*) AS paid_orders,
    ROUND(SUM(o.paid_amount_fen) / 100.0, 2) AS gmv_yuan,
    ROUND(SUM(o.paid_amount_fen) / 100.0
          / NULLIF(COUNT(*), 0), 2) AS paid_aov_yuan
FROM scoped_orders o
LEFT JOIN dim_channel_snapshot c
  ON o.channel_id = c.channel_id
 AND c.tenant_id = 'demo_shop'
 AND c.version = 'channel_v2'
GROUP BY o.period, COALESCE(c.channel_name, '未知渠道');
```

租户和快照是服务端选定的教学常量，不由模型任意填写。真实环境要参数化并使用执行端权限控制。只有已验证 `dt` 跟随支付日期时，上面的分区过滤才完整；如果 `dt` 表示入库日期，必须重新规划扫描范围，覆盖迟到支付记录。

`gmv_fen` 保留整数精度用于对账，元和客单价只在展示时舍入。编译器也不能把支付 GMV 随意改成 `SUM(DISTINCT paid_amount_fen)`：不同订单恰好金额相同是正常情况。

第二次 Execute 在相同快照中得到以下结果。渠道分类互斥且覆盖全部订单；未知渠道也应参加统计，本例恰好为零。

| 渠道 | 基准期 GMV（元） | 比较期 GMV（元） | 基准期订单数 | 比较期订单数 | 两期客单价（元） |
|---|---:|---:|---:|---:|---:|
| 广告 | 600000 | 400000 | 6000 | 4000 | 100 |
| 自然 | 400000 | 400000 | 4000 | 4000 | 100 |
| 合计 | 1000000 | 800000 | 10000 | 8000 | 100 |

渠道差额加总为 −20 万元，与总差额一致。广告渠道自身下降 `20 / 60 = 33.33%`，同时解释了本次总净降幅的 `(-20) / (-20) = 100%`；这两个百分比的分母不同。自然渠道没有贡献净变化，不能把它写成“自然流量表现很好”，因为案例并没有查询流量。

接着按 `GMV = 支付订单数 × 支付客单价` 分解。固定使用 `ΔGMV = (N1−N0)×A0 + N1×(A1−A0)`，订单量项为 −20 万元，客单价项为 0。若订单量和客单价同时变化，分解顺序会决定交互变化分配给哪一项，需要提前固定规则；它始终是算术解释，不能证明某个动作导致了变化。

第二次 Reflect 可以确认“净下降集中在广告渠道的支付订单量”。但它仍不知道订单量为什么下降：曝光减少、访问减少、转化变化、归因迁移和数据异常需要各自的证据。系统检查可用资产目录后，假定当前没有可用的广告曝光、花费和访问转化数据，于是记录 `missing_upstream_funnel_evidence`，不再生成不存在的表名，也不能从“广告”一词推导出“公司减少投放”。

完成分支时，证据摘要可使用下面的对象。所有引用都是教学逻辑 ID；真实系统应映射到确实存在、可鉴权访问的查询与结果：

```json
{
  "request_id": "req_gmv_001",
  "plan_revision": 2,
  "workflow_status": "ready_to_report",
  "answer_status": "partial",
  "causal_status": "not_established",
  "semantic_version": "commerce_semantics_v7",
  "snapshot_ref": "demo_snapshot_20261116_0900",
  "evidence": [
    {"step_id": "s1", "status": "succeeded", "result_ref": "quality_001"},
    {"step_id": "s2", "status": "succeeded", "result_ref": "weekly_001"},
    {"step_id": "s3", "status": "succeeded", "result_ref": "channel_001"}
  ],
  "verified_claims": [
    "gmv_down_200000_yuan_and_20_percent",
    "ads_channel_explains_net_decline",
    "paid_order_count_component_down_and_aov_component_zero"
  ],
  "gaps": ["missing_upstream_funnel_evidence"],
  "stop_reason": "no_available_authorized_data_for_next_branch"
}
```

Reflect 交接时的 `workflow_status=ready_to_report` 表示证据检查已经结束，可以生成报告；此时还不能声称整个流程完成。`answer_status=partial` 表示用户追问的业务原因尚未完全回答，渠道贡献子目标的完成不能替代因果调查。达到预算、数据缺失和权限不足也应分别记录，不能统一包装为“分析成功”。

#### 6．Report：交付可核对的结论及下一步证据需求

Report 读取通过检查的结果集和证据摘要，在固定模板里填入数值、口径、比较区间及限制。差额与比例最好由确定性计算工具产出，模型负责解释含义，不能在生成语言时悄悄改写数字、把相关性升级为因果关系。

本例可以向用户交付：“按北京时间完整自然周、人民币支付成功金额口径，上周 GMV 为 80 万元，前一周为 100 万元，下降 20 万元，即 20%。净降幅全部集中在广告渠道：该渠道 GMV 从 60 万元降至 40 万元，支付订单从 6000 单降至 4000 单，两期客单价均为 100 元；自然渠道 GMV 保持 40 万元。当前已定位下降贡献，但尚不能确定广告渠道订单为何减少。需要补充同口径的曝光、访问、转化及归因变更记录，才能继续核查业务原因。”

报告中的数字与引用核验通过、并成功交付后，编排器才把 `workflow_status` 更新为 `completed`；`answer_status=partial` 和 `causal_status=not_established` 保持不变。报告生成失败时保留失败状态或按预算重试，不能提前记录完成。

Report 还应提供用户有权查看的查询或结果引用。面向业务用户不必展示全部内部节点与 JSON；面向调试与审计则保存计划版本、生成 SQL、执行记录、反思缺口和最终回答，便于判断错误发生在哪一层。

#### 7．异常发生时，节点怎样重新配合

如果执行后发现渠道维表同一键有两条记录，Execute 返回 `dimension_key_not_unique`，停止发布渠道金额。Reflect 将它归为结果不可信，Plan 可以改用已验证的维度版本，或者先只交付总量并注明渠道分解受阻；不能让模型选一条看起来合理的记录继续计算。

如果数据尚未到齐，任务应处于等待或部分回答状态，明确缺失日期；如果用户把口径改为退款后净 GMV，必须重新绑定指标和生成计划，不能复用支付 GMV 的结果；如果查询超时，只能按剩余预算做有界重试或缩小已获用户认可的范围，不能悄悄改成抽样结果冒充全量。

语义定义在运行期间更新为 v8 时，本次仍绑定 v7，避免前一条查询按旧口径、后一条查询按新口径。若 v7 被判定存在错误，则将本次运行失效并显式重启到新版本；“固定版本”并不意味着继续信任已知错误。

#### 8．面试时如何用两分钟讲这个案例

可以这样回答：“我会把用户的‘为什么上周 GMV 下降’保存为分析目标，先确认支付口径和两个完整自然周。语义层提供指标版本、订单粒度、支付时间、渠道映射和金额单位，Plan 据此先安排数据就绪检查与总量核实。Execute 通过受控编译器生成 SQL，并返回带快照和查询引用的结果。首次只发现 GMV 从 100 万降到 80 万，Reflect 按完成条件指出还缺下降贡献，于是 Plan 增加渠道拆解。第二轮发现广告渠道少了 20 万，订单从 6000 降到 4000、客单价不变，且渠道加总能与总量对账。Report 可以交付这些已验证事实；因为缺少曝光和转化证据，会明确业务根因仍未查明。这套设计把需求理解、取数、证据检查和对外表述分开，同时让所有步骤受同一语义版本约束。”

这些可以只是一个编排器里的工作流节点；如果分析分支能独立取证，才考虑让不同 Agent 并行处理。区别取决于谁决定下一步和工具调用方式，不能仅按节点名称判断。[工作流与 Agent 的定义边界](https://www.anthropic.com/research/building-effective-agents)

### A1 LLM 与 SQL 生成解耦是什么意思？

参考回答：我会把需求理解和 SQL 编译分开。LLM 将自然语言转成受约束的查询意图，明确指标、维度、时间、过滤、排序和分析目标；语义解析器将这些业务对象绑定到经过审核的表字段，再由编译器生成目标引擎的 SQL。这样能分别排查理解错、绑定错和生成错，也能集中执行权限、分区范围和资源限制。

解耦不等于完全禁止 LLM 输出 SQL。对于暂不支持的分析，可以让模型产生候选 SQL，但必须经过语法解析、表字段白名单、只读检查和语义测试。只做到“模型返回 JSON，其中一个字段装 SQL”，并没有把业务语义和 SQL 生成分开。

放到 A0 案例里，LLM 只需确认“支付 GMV、两个自然周、按渠道解释下降”，编译器负责把它绑定为 `SUM(paid_amount_fen)`、支付日期范围与合法渠道映射。金额单位、固定过滤和允许的关联由语义对象决定。如果模型建议改用下单金额，必须重新绑定或澄清，不能只因为 SQL 可执行就通过。

### A2 自然语言如何转成结构化协议？Playbook 怎么设计？

参考回答：协议分成查询意图和 Playbook。前者保存要分析的业务目标、指标、时间、维度和缺失条件；后者保存步骤、依赖、输入输出引用与预算。两者分开后，Reflect 可以要求补一个分析分支，而不用让模型重新解释整句需求，也能避免重规划时悄悄改变口径。

下面是 A0 完整案例的初始协议，用户已确认支付口径和两个完整自然周。这是自定义教学协议，不是某个框架的标准 API；租户与授权范围由服务端会话注入，没有交给模型决定：


### A3 Plan、Execute、Reflect、Report 是节点还是 Agent？

参考回答：这些名字描述职责，不决定部署形态。我会先把它们建成工作流节点：Plan 生成步骤和验收条件；Execute 调用检索、编译、执行和计算工具；Reflect 检查结果与证据缺口；Report 根据已经验证的结果生成回答。节点可以是普通函数、模型调用，也可以调用独立服务。只有模型在循环中自主选择工具和下一步，才有理由称其为 Agent；四个名称不意味着四个独立 Agent。[Anthropic 对工作流与 Agent 的区分](https://www.anthropic.com/research/building-effective-agents)

每次交接都传版本化对象，至少包含状态、产物引用、证据、错误类型和未解决问题。Execute 失败时返回可分类错误，Reflect 不能把异常信息当作查询结果。重试必须有上限，超出预算时交付已知结果和缺口，不让反思循环无限执行。

实现时还要有一个编排器保存运行状态：Plan 的产物是带版本的 Playbook，Execute 的产物是结果集与执行证据，Reflect 的产物是通过项、缺口和下一步决定，Report 的输入是已经核验的事实与未解决事项。语义层是这些节点共同调用的服务或模块。节点能否独立部署，与它是不是 Agent 是两个不同问题；A0 展示了同一请求经过两轮计划与执行后怎样结束。

### A4 Reflect 如何判断回答完整？为什么 GMV 下降不能只报下降幅度？

参考回答：在 Plan 阶段就建立完成条件，Reflect 按条件核对结果。对于“为什么下降”，只返回两周 GMV 和环比仅完成了现象确认。还要检查数据是否到齐、比较窗口是否等长、退款与币种口径是否一致，再分解下降来自哪些渠道、类目或客群，以及相应的订单量和客单价变化。

先固定 GMV 定义。如果采用支付成功金额，可以按支付订单量与平均支付订单金额拆解；若要引入访问人数、转化率，需要统一用户或会话口径，并检查这个乘法关系是否严格成立。分渠道的绝对差额可用于衡量各渠道对总差额的贡献，但不同维度之间通常有重叠，不能把渠道贡献和类目贡献直接相加。

Reflect 要核对“每个结论是否对应结果集、拆解是否与总量对账、是否还有无法解释的差额”。SQL 能运行、结果非空和语言流畅，都不能证明问题已经回答。促销结束与 GMV 同时下降只能形成待验证解释；要声称促销导致下降，还需要实验、合理对照或其他足够的因果证据。

确定性检查负责日期、加总、空值、数据就绪和证据引用，模型负责审查表述与问题是否对应。离线评估保存真实任务、执行轨迹和最终产物，多次运行并统计错误类型；不能只让同一个模型评价自己的回答。[Anthropic 的 Agent 评估方法](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

检查目标要分层。A0 首轮查询成功，但缺少渠道贡献，因此必须继续；第二轮贡献已经对账，但没有投放与转化证据，因此只能部分回答业务原因。可以把日期、单位、唯一键、渠道加总和数字引用写成程序断言，再让模型核对解释是否回应原问题。任何一层检查失败，都应回传明确缺口，不能靠另一次自然语言评价把失败覆盖成成功。

### A5 语义层存什么？表与表的关联关系如何确定？

参考回答：语义层保存能约束计算的业务定义。指标包括稳定 ID、定义、聚合方式、去重对象、固定过滤、金额单位和版本；维度包括业务含义、数据类型、枚举或取值来源；时间定义包括业务时间字段、时区、统计粒度与窗口规则。物理映射保存表字段、分区、主键或逻辑唯一键、表粒度以及更新和删除语义。

表关联必须记录两端键、关联类型、基数、有效时间和允许的过滤方式。例如订单明细关联商品维表，必须确认商品 ID 在指定版本中唯一；若维表是拉链表，还需要按订单时间命中对应有效区间。字段同名只说明它们看起来相似，不能证明可以关联。候选关系可从 DDL、SQL 血缘和查询历史中发现，再通过唯一性、空值、匹配率、关联前后行数与金额核对确认。

YAML 适合维护可读、可版本管理的定义；线上服务可以将其编译成关系存储和检索索引，不必让每次请求遍历文件。dbt Semantic Layer 的语义模型、实体和关联图是可参考实现，但这里的协议不是其直接配置格式，使用时还需绑定实际版本。[dbt 语义模型](https://docs.getdbt.com/docs/build/semantic-models)、[dbt 关联逻辑](https://docs.getdbt.com/docs/build/join-logic)

Query Example 需要携带适用指标、参数、引擎方言、预期结果及审核状态，避免把过期 SQL 当作权威答案。字段值检索要分级：低基数枚举可索引，高基数值按需查询或建立独立服务，敏感值不应无条件写入向量库。

A0 的 YAML 将抽象对象落到了具体字段：指标引用支付金额，时间绑定支付日期，渠道记录归因时点和一对多风险，校验规则要求订单与维度键唯一。语义层不仅是供模型阅读的说明书，还应给编译器提供可执行约束、给检查器提供验收规则、给 Report 提供单位与业务名称。自然语言描述不能替代这些机器可检查字段。

### A6 如何保证 YAML 正确并自动更新？

参考回答：格式校验只是入口。我会把定义变更放进版本管理与审核流程，依次检查 Schema、表字段存在性、类型与分区映射、关联基数、指标样例和历史问答回归。业务负责人确认指标含义，数据负责人确认物理映射和数据质量。

DDL、调度配置和血缘变化可以自动触发差异检测，定位受影响指标、查询模板和检索文档，生成更新候选。新增字段不能自动等价为新增指标，模型也不应自行决定 GMV 从支付口径改为下单口径。变更通过审核后发布新版本，重建相关索引，并保留旧版本和生效时间，使历史回答能够复现。

维护成本高时，先治理高频、易错和价值明确的业务域，明确每个对象的负责人、最后核验时间和废弃条件。能由数据目录、Schema 和血缘同步的事实自动同步；业务定义保留人工责任。衡量维护效果要看定义覆盖、过期比例、问答失败率和变更回归结果，不能用 YAML 文件数代替质量。

例如将 `gmv_paid@v3` 改为扣退款后的净额，影响的不只是检索文案，还包括金额来源、退款事件时间、比较窗口和历史结果。应发布新指标或版本，保留有效期，并用同一套基准数据比较预期差异。语义目录与检索索引也要按版本发布；运行中的请求固定自己的版本，不能一次查询读到 v7、下一次因索引更新读到 v8。

### A7 BM25 与向量检索如何融合？混合召回有什么缺点？

参考回答：BM25 按分词后的词项匹配排序，适合表名、字段名、指标简称等有辨识度的词，但它仍受分词和分析器影响，不能笼统称为“精确匹配”。向量检索补充同义表达和语义相近的问题，但可能召回业务相似而统计对象不同的表。两路召回分别保留来源和排名，再合并为候选集合。[Elastic 混合检索](https://www.elastic.co/docs/solutions/search/hybrid-search)

融合可以使用 RRF，按各路排名累加 `1 / (k + rank)`，避免直接相加两个量纲不同的原始分数。融合后还应按业务域、指标口径、粒度、权限、时间覆盖和关联可达性筛选，必要时重排。RRF 分数只是排序信号，不能当成“这张表有 95% 概率正确”。[Elastic RRF 定义](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)

混合召回增加了索引维护、查询延迟和调参成本，任何一路的噪声也可能进入最终集合。词面吻合但业务语义不符时，需要核对统计对象、口径和可用维度，不能因为 BM25 排名高就直接执行。用真实问题分别评估关键词、向量和混合方案的 Recall@K、排序质量，以及最终选表与结果正确率，再决定参数与方案。

实际检索可以先按授权业务域限制候选，再对“GMV 下降、成交额变少”等表达分别做关键词与向量召回。BM25 可能同时命中支付 GMV 与下单 GMV，向量也可能把收入或净收入召回；融合后仍需检查统计对象、业务时间、退款口径和可用维度。A0 中两个 GMV 候选的歧义需要用户上下文或一次明确澄清，重排分数高本身不能解决业务定义冲突。

### A8 多候选、无结果、错误召回和表达模糊如何处理？

参考回答：先用已知上下文缩小业务域，再检查候选是否满足查询要求。多候选若只是同一指标的等价副本，可以依照明确的主数据源策略选择；若分别代表支付 GMV 和下单 GMV，就要向用户确认口径。澄清问题应指出会改变结果的差别，例如“这里的 GMV 按支付时间还是下单时间统计？”

无候选时区分确实没有数据、索引未更新、权限不足和检索词没匹配，可以受控查询目录或扩展同义词，但不能编造表名。召回错误一旦被字段、粒度或口径校验发现，就返回重检索或澄清；多次失败后应说明可支持范围。检索后仍需服务端鉴权，避免模型通过换一种问法获得原本无权访问的数据。

闲聊与取数意图可采用规则加分类器或模型路由，输出意图与缺失槽位，同时考虑上下文中的省略表达。系统只有取得必要的统计对象、指标、时间和权限后才进入执行。“GMV 是什么意思”通常是解释请求，“那上周呢”可能承接前文进入取数，单靠关键词无法区分。路由评估需同时看误触发取数和漏掉取数请求。

状态应该能区分 `needs_clarification`、`blocked_by_data`、`blocked_by_permission` 与合法的零结果。没有检索到广告曝光表，不能写成曝光为零；没有权限，也不能通过缓存的其他租户结果补答案。A0 缺少上游漏斗证据时，Report 仍可交付已核验的渠道下降贡献，同时把原问题标为部分回答。

### A9 为什么采用多 Agent？

参考回答：如果查询流程明确，我会优先使用单一编排器和受约束工具。只有任务存在可并行的独立分析、上下文隔离或不同工具权限时，才考虑多个 Agent。例如渠道和商品分析可分别取证后汇总，但它们必须共享同一个指标版本、时间范围和过滤条件。

多 Agent 的代价是交接遗漏、重复查询、结论冲突和更多模型开销。工作流中的多个角色不自动构成多 Agent，也不能保证独立纠错。是否采用它，要在同一评估集和相近资源约束下比较结果正确率、延迟与成本；多 Agent 研究系统的收益不能直接移植成 Text2SQL 项目的收益。[Anthropic 多 Agent 研究系统的适用场景与代价](https://www.anthropic.com/research/multi-agent-research-system)

若把 A0 扩成多个分析 Agent，可以让渠道与商品分支并行，但都必须接收相同的指标、快照、授权与时间对象；结果交接还要包含粒度、单位和未解释差额。渠道和商品是同一批订单的不同切面，不能把两个分支计算的下降贡献相加。并行只能减少可并行部分的等待时间，不能自动提高结论可信度。

### A10 为什么窗口 SQL 难？模板有什么限制？先生成计划有什么用？

参考回答：窗口问题难在多层语义同时成立：统计对象和分组粒度、先过滤还是先计算、`PARTITION BY`、排序和并列规则、窗口边界、去重位置、跨表关联是否扩行。例如“每个用户最近一笔订单的金额排名”和“按用户累计金额排名”都出现用户与排名，计算顺序却不同。

固定模板适合口径稳定、参数范围明确的查询，但维度组合、跨事实表计算、嵌套窗口和临时分析会使模板数量膨胀。生成逻辑计划可以显式表达扫描、过滤、关联、聚合和窗口的依赖，逐步检查每一步的输入粒度、键和输出，再编译到不同 SQL 方言。

这里的逻辑计划是查询意图的受约束表示，不等于让 LLM 决定 Spark 的物理 Join 算法或 Task 数量，物理执行仍由引擎优化器负责。计划也会生成错，因此仍要用小规模反例、关联基数和结果对账检查；语法通过、执行成功和行数相同都不能证明业务等价。

逻辑计划还应保存每一步的粒度变化。例如先在订单粒度求金额，再关联一对多明细，可能把金额重复；先按用户筛最近订单，再做窗口，与先统计全部订单再筛行也会得到不同结果。A0 不需要窗口，就不应为了体现智能而增加窗口计算。计划的价值是明确必要运算及校验点，不是让中间步骤越多越好。

### A11 一个好的 Skill 应该如何定义？

参考回答：Skill 是针对一类任务的可复用操作知识。Description 要让模型知道它能完成什么、何时该用；正文写清输入、步骤、产物、核验和失败处理。Agent Skills 规范要求 `SKILL.md` 包含 `name`、`description`，并允许将脚本、参考资料和资源分文件维护。[Agent Skills 规范](https://agentskills.io/specification)

以“指标取数”为例，触发条件可以是用户要求计算已经登记的业务指标；边界要明确解释概念、修改指标口径和执行生产写入是否属于范围。执行步骤应落实到读取当前指标版本、补齐影响结果的条件、确认数据范围、生成并校验 SQL、只读执行、核对结果以及保存证据，而不是只写“理解需求并给出准确答案”。

步骤中要定义完成判据，例如结果包含口径版本、时间范围、查询引用和未解决问题。应同时准备正常输入、歧义输入、缺数据、权限不足及错误结果的样例，验证是否正确触发与停止。Skill 中声明工具权限不等于真实获得授权，实际权限仍由运行环境执行；没有证据时，Skill 也不能要求模型把推断写成事实。

如果把 A0 沉淀为“指标变化分析”Skill，Description 应覆盖“比较两个期间并定位变化贡献”等请求；正文要求先绑定指标和时间，再校验数据、核实变化、做允许的分解、核对差额并说明因果证据缺口。它可以调用现有查询工具，却不能自行获得数仓权限。测试样例应包含指标未下降、维表重复、数据未到齐和缺上游原因数据，观察是否走到正确分支。

### S1 Hadoop MapReduce 的完整过程

参考回答：客户端根据 `InputFormat` 生成逻辑 `InputSplit`，提交作业及配置。以 YARN 模式为例，ResourceManager 分配 ApplicationMaster 容器，ApplicationMaster 申请 Map、Reduce 容器并跟踪任务。一个 Split 通常对应一个 Map Task，Split 不等于 HDFS Block，能否拆分还受文件格式和压缩方式影响。

Map 端通过 `RecordReader` 把输入变成键值对交给 Mapper。Mapper 输出进入缓冲区，由 Partitioner 决定目标 Reduce 分区，再按键排序并在内存不足时溢写到本地磁盘，随后合并文件。Combiner 是可选的局部合并，调用次数不保证，不能把平均值等不可直接合并的计算原样放进去。

Reduce 端拉取各 Map 属于自己的分区，边拉取边归并排序；分组比较器决定哪些键属于一次 `reduce` 调用。Reducer 处理每组键和对应值，`RecordWriter` 写结果，提交协议负责发布成功输出。Map 输出通常在执行节点本地，最终输出的位置由输出格式和路径决定，不能说所有中间结果都写 HDFS。任务失败可以重试，所以自定义外部副作用仍要考虑重复执行。[Hadoop MapReduce Tutorial](https://hadoop.apache.org/docs/current/hadoop-mapreduce-client/hadoop-mapreduce-client-core/MapReduceTutorial.html)

### S2 Lambda 与 Kappa 如何选择

参考回答：Lambda 同时运行批处理和实时处理，服务层结合两路结果。它允许分别安排历史重算和实时服务，但必须维护两套逻辑的一致性，并处理批结果与实时结果的时间边界。Kappa 以可重放日志为输入，使用同一套流处理逻辑；逻辑变更时启动新版本回放历史，追平后切换输出。Kappa 减少两套实现的维护，但仍需要历史保留、回放资源和安全切换。[Jay Kreps 对两种架构的原始讨论](https://www.oreilly.com/radar/questioning-the-lambda-architecture/)

我的判断条件是：历史是否完整可重放，状态能否重建，回放能否赶上新增速度，以及输出能否隔离验证。日志只保留七天、业务要回算一年时，不能仅凭“用了 Kafka 和 Flink”就声称满足 Kappa 的重算能力。Lambda 也不天然意味着实时结果近似；准确性取决于两路计算语义和合并规则。

### S3 数据湖为何能更新，是否一定更快

参考回答：数据湖是围绕统一存储、开放数据格式和多种计算方式组织数据的体系；行级更新能力来自 Hudi、Iceberg 等表格式及执行引擎配合，不能归因于“文件放进了数据湖”。Parquet 通常不会原地改几个字节来更新一行。Copy-on-write 会重写受影响文件，merge-on-read 会保存变更并在读取或后续合并时应用，提交新版本的元数据决定读者能看到哪些文件。[Hudi 表类型](https://hudi.apache.org/docs/table_types/)、[Iceberg 写入与更新](https://iceberg.apache.org/docs/latest/spark-writes/)

“更新一列”是逻辑结果只改变该列，物理上仍可能重写包含其他列的数据文件；部分列输入如何与旧行合并，还取决于具体表格式、记录合并规则和连接器。增量读取也应区分变更行、某段提交影响的记录和完整 changelog，不能把它们都叫 CDC。

数据湖查询可能因列裁剪、分区裁剪、统计过滤、合理文件大小和增量处理而少读数据；这些收益有条件。与同样采用列式存储、合理布局的数仓比较时，数据湖未必更快，对象存储请求、小文件、合并日志和元数据规划也会增加成本。我会对齐查询、数据范围、快照、缓存状态和计算资源，再比较扫描字节、耗时、资源与维护开销。[Iceberg 的快照与原子提交](https://iceberg.apache.org/docs/latest/reliability/)

### S4 Hudi 底层与 Timeline

参考回答：Hudi 以表路径组织数据，表可以分区，分区内用 File Group 标识一组持续演进的数据。File Group 包含多个版本的 File Slice；在常见布局里，一个 File Slice 包含可选的 Base File 和相关 Log File，Base File 常用 Parquet。CoW 更新后生成新 Base File；MoR 可以先把更新写进日志，查询合并基文件与日志，Compaction 再把它们合成新的基文件版本。记录键、分区路径和索引决定怎样定位已有记录，合并规则决定多版本记录怎样取舍。[Hudi 存储布局](https://hudi.apache.org/docs/storage_layouts/)

Timeline 记录表状态的变化及其动作、时间和状态，包括 `REQUESTED`、`INFLIGHT`、`COMPLETED`。`COMMIT` 表示原子写入基文件；`DELTA_COMMIT` 用于 MoR 写入，数据可能进入日志；`COMPACTION` 生成新的基文件视图，完成后在 Timeline 上表现为 `COMMIT`；`CLEAN` 按保留策略删除不再需要的旧 File Slice。它们不等价：Compaction 处理读放大，Clean 回收历史存储。[Hudi Timeline](https://hudi.apache.org/docs/timeline/)

读取时还要说明查询类型。MoR 的 snapshot 查询需要包含尚未合并的变化；read-optimized 查询只读基文件，可能看不到最新日志。Cleaner 的保留策略会限制可读历史，不能同时承诺无限时间旅行和持续删除旧文件。[Hudi 查询类型](https://hudi.apache.org/docs/table_types/)

### S5 Doris 与 Spark、Hive 与 Spark

参考回答：Doris 是面向分析服务的数据库，Spark 是通用分布式计算引擎。Doris 管理表数据、索引、更新和持续查询服务；Spark 常负责大规模 ETL、复杂计算和离线重算，数据通常由外部存储或表格式承载。两者能配合：Spark 加工后写入 Doris，由 Doris 对下游提供查询；是否这样选取决于吞吐、延迟、并发和数据维护成本。

在 Doris 存算一体部署中，FE 接收请求、解析与规划 SQL、管理元数据和节点；BE 存储数据并执行计划。存算分离部署还涉及共享存储和元数据服务，不能把“所有数据永久存放在 BE 本地盘”写成通用结论。Doris 的查询加速来自 MPP 并行、列式读取、批量向量化执行以及分区、分桶、索引等减少读取的手段；能省多少扫描还要看谓词、数据布局和计划。[Doris 架构](https://doris.apache.org/docs/3.x/gettingStarted/what-is-apache-doris/)、[Doris 向量化执行](https://doris.apache.org/docs/4.x/key-features/vectorized-execution/)

Hive 提供 SQL 数仓能力及相关元数据体系，Spark 提供计算运行时，比较前要问 Hive 实际使用什么执行引擎。Hive on MapReduce、Hive on Tez、历史上的 Hive on Spark，与使用 Hive Metastore 的 Spark SQL 是不同组合。共享 Metastore 只代表共享某些元数据，不代表优化器、执行器、事务支持和 SQL 语义相同。[Hive 介绍](https://hive.apache.org/docs/latest/introduction-to-apache-hive/)、[Hive on Spark](https://hive.apache.org/docs/latest/user/hive-on-spark/)

Spark 比传统多轮 MapReduce 快，常见原因是 DAG 调度可以把连续窄依赖计算流水执行，复用 Executor，SQL 优化和代码生成减少处理开销，需要复用时还能缓存数据。Spark 仍然会读写磁盘：Shuffle 产生中间文件，排序和聚合内存不足会 Spill，缓存也可以选择包含磁盘的存储级别。不能把“基于内存”解释为“全部数据必须装进内存”或“不落盘”。[Spark Shuffle 与持久化](https://spark.apache.org/docs/3.5.6/rdd-programming-guide.html)

### S0 完整案例：一张地区 GMV 日报的血缘怎样产生

静态 SQL 解析回答“这版代码声明要读写什么”，Spark 运行时采集补充“这次运行实际解析和执行了什么”，Flink 将分散的事件关联为可查询的证据，字段血缘说明每个输出值及其行集受哪些输入影响。四者保存的是不同层次的信息，不能用一条没有来源和状态的连线代替。

下面继续使用订单业务，构造一个“按客户地区统计支付 GMV”的日任务。表、运行 ID、事件与数据均为教学输入；示例查询与事件归并规则做了本地验证，没有实际接入 Spark Listener、运行 Flink 作业或验证线上采集覆盖。

#### 1．固定输入、SQL 与预期结果

任务 `region_gmv_daily` 的代码版本为 `v3`，业务日期为 `2026-11-15`，授权租户为 `demo_shop`，订单读取快照 `demo_snapshot_20261116_0900`。订单事实 `spark_catalog.dw.dwd_order_paid_snapshot` 在同一租户和快照内一单一行，支付日期按北京时间派生，金额单位为分。这里只统计人民币支付成功金额，不扣后续退款；分区 `dt` 与支付日期一致。

构造订单如下。各行来自同一租户与快照，日期同时表示本例的 `paid_date` 与 `dt`。

| order_id | customer_id | paid_amount_fen | payment_status | currency | 日期 |
|---|---|---:|---|---|---|
| O1 | U1 | 10000 | SUCCESS | CNY | 2026-11-15 |
| O2 | U2 | 20000 | SUCCESS | CNY | 2026-11-15 |
| O3 | U3 | 30000 | SUCCESS | CNY | 2026-11-15 |
| O4 | U4 | 40000 | FAILED | CNY | 2026-11-15 |
| O5 | U9 | 5000 | SUCCESS | CNY | 2026-11-15 |
| O6 | U1 | 7000 | SUCCESS | USD | 2026-11-15 |
| O7 | U1 | 6000 | SUCCESS | CNY | 2026-11-14 |

客户日快照 `spark_catalog.dim.dim_customer_daily` 在 `(tenant_id, dt, customer_id)` 上唯一。本日 U1、U2 属于华东，U3 属于华南，U4 属于华北；U9 没有匹配记录。日报采用客户本日快照中的地区，不声称还原下单时地区；若业务要求历史归属，应改用订单内归属或按有效时间关联的维表。

下面是调度参数已经展开后的 Spark SQL 3.5 教学示例。假定目标表已按 `dt` 分区创建，非分区字段依次为 `region`、`gmv_yuan`、`paid_orders`；两条语句在同一 SparkSession 执行。

```sql
CREATE OR REPLACE TEMP VIEW paid_orders AS
SELECT order_id, customer_id, paid_amount_fen
FROM spark_catalog.dw.dwd_order_paid_snapshot
WHERE tenant_id = 'demo_shop'
  AND snapshot_id = 'demo_snapshot_20261116_0900'
  AND dt = '2026-11-15'
  AND paid_date = DATE '2026-11-15'
  AND payment_status = 'SUCCESS'
  AND currency = 'CNY';

INSERT OVERWRITE TABLE spark_catalog.dm.dm_region_gmv_daily
PARTITION (dt = '2026-11-15')
SELECT
    COALESCE(c.region, 'UNKNOWN') AS region,
    CAST(SUM(CAST(o.paid_amount_fen AS DECIMAL(20, 0)))
         / 100.0 AS DECIMAL(20, 2)) AS gmv_yuan,
    COUNT(o.order_id) AS paid_orders
FROM paid_orders o
LEFT JOIN spark_catalog.dim.dim_customer_daily c
  ON o.customer_id = c.customer_id
 AND c.tenant_id = 'demo_shop'
 AND c.dt = '2026-11-15'
GROUP BY COALESCE(c.region, 'UNKNOWN');
```

过滤后留下 O1、O2、O3、O5，金额合计 65000 分。Join 后 O1、O2 汇成华东 300 元、2 单；O3 汇成华南 300 元、1 单；O5 保留为 UNKNOWN 50 元、1 单，最终都写入 `dt=2026-11-15`。O4 因支付状态排除，O6 因币种排除，O7 因日期排除；UNKNOWN 行不能因为没匹配到地区而被静默丢掉。

订单 ID 非空，因此本例 `COUNT(order_id)` 等于有效订单行数。这个写法有明确的 ID 字段依赖；如果改成 `COUNT(*)`，应记录对行集的计数，不能为了画图而声称它直接读取了 `order_id`。

#### 2．发布前静态解析：从语句结构走到可解析的资产关系

静态采集先保存原 SQL 模板、展开后的 SQL、任务与代码版本、参数、SQL 方言及 Catalog/Schema 版本。抽象语法树 AST 说明语句中的读取、投影、过滤、Join、聚合与写入结构；它识别出 `paid_orders` 是临时视图、第二条语句读取该视图并写地区日报。但只做字符串匹配或只得到 AST，还不能完整确定每个列名属于哪张表。

解析器需要将别名 `o` 绑定到本会话的 `paid_orders`，再追到订单事实；将 `c` 绑定到客户日快照，并核对字段与目标 Schema。第一条视图输出只有订单 ID、客户 ID 和金额，支付状态与币种虽然不输出，仍影响保留哪些订单。第二条语句里的 `SUM`、`COUNT`、`COALESCE` 和分组表达式则决定字段如何形成。

因此发布时就可以保存 v3 的声明依赖：订单事实和客户快照是输入，地区日报是输出，中间经过会话内的临时视图。临时视图的标识要带 `session_id`，不能把不同任务里同名的 `paid_orders` 合并成全公司同一张持久表。跨会话没有该视图定义时，应标记待解析，不能凭名字猜它的来源。

静态信息还应保存目标分区由参数 `biz_date` 形成。本例是静态分区写入，目标 `dt` 的值来自展开后的常量，不是从源表 `dt` 原样投影；源表 `dt` 只是过滤依赖。如果使用动态分区，静态分析能识别分区表达式，实际写了哪些分区仍需运行或写入证据补充。

这里生成的是 `declared` 关系，即该版本代码声明的计算依赖。即使发布后的任务从未运行，声明关系也有用于变更影响分析的价值；它不能证明本日数据已经生产成功。`SELECT *` 还依赖当时的 Schema，动态 SQL 则依赖实际展开结果，二者都不适合只留一份脱离上下文的 SQL 文本。

#### 3．Spark 运行时采集：把本次计划与本次运行绑定

调度系统为逻辑业务运行分配 `run_id=region_gmv_20261115`。第一次尝试 a1 失败，第二次尝试 a2 重跑成功；每次都记录代码版本、参数、Spark Application/Attempt 和 Session。a2 的目标写查询以教学编号 `query_execution_id=7`、`sql_execution_id=42` 标识，其下可能产生 Spark Job 31、32。它们是不同实体的编号，不能把 SQL Execution、QueryExecution 和 Job 当成一个概念，也不能假设一个 SQL 只产生一个 Job。

静态 SQL 与 DataFrame API 最终都可能形成 Spark 逻辑计划。采集器读取已经解析的关系和表达式，得到本次绑定到的订单表、客户表、临时视图展开关系及输出字段。字段追踪主要依靠表达式关系；物理计划可补充实际扫描、Join 和写入执行信息。某个字段被列裁剪、过滤下推或聚合优化处理后，仍需按其值与控制作用保留血缘语义，不能只在物理计划文本里搜字段名。

Spark 的 `QueryExecutionListener.onSuccess/onFailure` 可以取得相应查询动作的 `QueryExecution`，供读取逻辑与物理计划；接口可能被多线程调用。它不覆盖所有 SQL、DDL 或自定义写入路径，具体能力需要针对版本与入口验证。普通 `SparkListener` 则观察 Job、Stage 等生命周期，采集器需要利用 SQL 执行上下文将它们关联起来，不能按时间接近强行拼接。[Spark 3.5.7 QueryExecutionListener](https://spark.apache.org/docs/3.5.7/api/java/org/apache/spark/sql/util/QueryExecutionListener.html)、[SQLExecution 源码](https://raw.githubusercontent.com/apache/spark/v3.5.7/sql/core/src/main/scala/org/apache/spark/sql/execution/SQLExecution.scala)

OpenLineage 的 Spark 集成是一个可参考的现成采集器，通过 Listener 及计划依赖提取信息；它不等于 Spark 原生自动提供完整字段血缘。其字段实现使用计划内的 `ExprId` 连接输入、输出和中间表达式；`ExprId` 的作用域是相关计划，不能当作跨任务、跨版本永久字段 ID。[OpenLineage Spark 集成](https://openlineage.io/docs/integrations/spark/)、[字段血缘实现](https://openlineage.io/docs/integrations/spark/spark_column_lineage/)

回调中只提取必要上下文并进入有界队列，独立发送线程再投递 Kafka；大计划的序列化、深度解析和远程请求不能无限堆在监听回调里。队列满或 Kafka 不可用时，要有丢弃/缓冲策略、指标和可行的补采来源。异步降低主链路等待，不等于没有 CPU、内存和事件丢失成本。

`onSuccess` 证明的是所观察查询动作成功，能否同时证明目标写入已经提交，要由该写入入口与连接器协议决定。本例额外约定由写入适配层提供分区提交确认，再将 a2 标为“已确认产出”；a1 保留失败与计划证据，不发布为成功产出。失败也不自动证明任何外部副作用都没有发生。

#### 4．字段血缘：区分值来源与行集影响

本例的输出字段可以落到以下关系。表中关系是我们要验证的语义，不保证任意版本采集器都能自动输出这些全部分类。

| 输出字段 | 值来源及运算 | 其他影响 |
|---|---|---|
| `region` | 客户表 `region` 经 `COALESCE` 形成，未匹配时使用常量 UNKNOWN | 两端 `customer_id` 决定匹配；客户租户与日期限定维度版本 |
| `gmv_yuan` | 订单 `paid_amount_fen` 聚合，再从分换算成元 | 订单过滤、客户匹配基数和地区分组决定哪些行参加每组 SUM |
| `paid_orders` | 对订单 `order_id` 执行 COUNT | 同样受过滤、Join 与地区分组影响 |
| 分区 `dt` | 调度参数 `biz_date` 展开成的静态常量 | 源表与维表日期过滤限制本次输入范围，但不是该常量的值来源 |

`paid_amount_fen` 是 GMV 的直接值来源，`payment_status` 和 `currency` 则决定哪些订单进入 SUM。它们不出现在 SELECT 输出里，但修改过滤条件会改变 GMV，影响分析不能只收集直接来源。Join 两端的客户键以及分组用的地区同样需要记录。

OpenLineage 将值派生区分为 DIRECT，并进一步标识 IDENTITY、TRANSFORMATION、AGGREGATION 等；对选择或组织行集的影响可用 INDIRECT 的 FILTER、JOIN、GROUP_BY 等表达。规范和具体采集器对间接依赖存放位置存在版本与配置差别，因此下方采用自定义证据协议，不冒充某个版本的原始 OpenLineage 消息。[字段血缘与转换类型规范](https://openlineage.io/docs/spec/facets/dataset-facets/column_lineage_facet/)

例如保存 GMV 血缘时，可将直接来源记录为 `dw.dwd_order_paid_snapshot.paid_amount_fen`，运算保存为聚合和单位换算；在同一查询的控制依赖集合保存支付状态、币种、日期、租户、快照过滤，以及客户键和地区分组。这样用户查询“修改支付状态口径会影响哪里”时，也能找到地区日报的 GMV，而不是只返回把状态原样输出的表。

字段血缘描述计算依赖，不是每条结果记录的完整逐行来源清单。华东 300 元由 O1 和 O2 组成是本例可手算验证的事实；若生产系统要逐笔解释某个聚合结果，还需要额外保存明细证据或执行可重现的追溯查询，不能仅凭字段图直接列出全部来源订单。

#### 5．采集事件怎样交给 Flink

本例采集器把 Spark 和调度/写入适配层的证据投到 Kafka 的教学 Topic `lineage.raw`，Flink 消费的是血缘事件，不是在重新执行上面的订单聚合 SQL。各生产者按协议提供稳定事件 ID；网络重发沿用相同 ID，事件确实被修正时增加其修订号。

下面只展示 a2 的查询完成消息。所有编号和引用都是教学值；`run_id`、`attempt_id`、`revision`、`commit_evidence` 等是本例自定义字段，不能直接当成原生 Spark Listener 或 OpenLineage 的固定返回格式。

资产标识同时保存环境、Catalog、数据库、表与字段，避免将测试库同名表合并进生产图。Flink 可以按 `environment + tenant_id + task_id + run_id + attempt_id` 组成 `run_key` 分区，在该键下再用 `application_id + application_attempt_id + session_id + query_execution_id` 组成 `query_key` 保存子执行。这样同名测试任务以及同一次业务尝试中的多个 Spark 应用不会因局部编号相同而碰撞。一个业务运行含多条 SQL 时，不能收到任意一条查询的 COMPLETE 就宣布整个业务任务完成；本例发布的是明确的目标写查询 q7 的证据。

Keyed State 保存已见 `(producer, event_id, revision)`、各查询的上下文、结束事实、提交证据及缺口。相同事件同修订重发应幂等；同修订不同内容属于冲突；修订号只能按生产者定义在相应事件范围内比较。它不能代替 START、COMPLETE、FAIL 的生命周期规则。同一 `(producer, event_id)` 的更高修订替换该来源的旧断言，并重算受影响查询的证据集合；不能把修正前后的字段边永久取并集。若旧集合已发布，还需使其失效或发布新的有效修订。不同事件的生命周期事实则按各自含义合并。[Flink 2.3 Keyed State](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/dev/datastream/fault-tolerance/state/)

#### 6．用乱序、重复与失败重试走一遍状态变化

本例约定只有查询成功、必要计划关系已取得、目标写提交已确认且无冲突时，才发布该尝试的成功产出证据。实际连接器若在 COMPLETE 内已经提供可信的完整提交信息，可一次满足条件，不需要机械等待另一条 START。

| 到达顺序 | 收到的事件 | Flink 状态与服务可见内容 |
|---|---|---|
| 1 | a1 的 `QUERY_START` | 保存声明版本与计划上下文，查询状态为运行中 |
| 2 | a1 的 `QUERY_FAIL` | 保存失败；本次输入输出关系可作为失败尝试证据，不发布成功产出 |
| 3 | a2 的 `QUERY_COMPLETE` 先到 | 保存完成事实；本例尚缺计划内容与提交证据，保持待补齐 |
| 4 | a2 同一完成事件重发 | 识别为重复，不增加第二组证据边 |
| 5 | a2 的 `QUERY_START` 迟到并补齐计划 | 合并上下文，保留已收到的完成事实，不退回运行中 |
| 6 | a2 的 `WRITE_COMMIT_CONFIRMED` 到达 | 目标分区与查询对应一致，发布 a2 已确认产出证据 |
| 7 | a1 的旧失败事件再次到达 | 只更新/去重 a1 的记录，不覆盖 a2 的成功事实 |

`WRITE_COMMIT_CONFIRMED` 是本例写入适配层事件，不是 Kafka、Flink 或 OpenLineage 保证必然存在的固定事件名。提交凭据怎样取得，需针对 Hive 文件提交、表格式 Snapshot 或其他目标的实际协议实现。如果采集器只能看到查询成功，服务就应标记“执行成功，提交未独立确认”，不要编造更强证据。

状态更新采用事实合并，而非把最后到达的消息状态覆盖到表上。a2 的 START 迟到，只补上下文；a1 失败与 a2 成功分开保存。若同一个查询出现无法解释的成功/失败冲突，应核对权威来源、尝试边界与修订记录，标记冲突待核验，不能规定“成功永远覆盖失败”。

去重状态会占空间，可按业务允许的迟到和重放范围设置保留期；Flink 2.3 的常规 State TTL 使用处理时间。过期后的历史事件仍可能再次到来，所以持久层还应使用稳定证据键，例如 `(run_key, query_key, edge_fingerprint)` 幂等写入，不能把有限 TTL 当作无限历史精确去重。

Checkpoint 恢复 Flink 状态与输入进度，但不会自动将任意图数据库 HTTP 请求纳入同一事务。本例可先按稳定键写完某次查询的全部证据边，再用关系数量/摘要校验并发布该集合的可见标记；读服务只读已完整发布的集合。后端若支持事务，可在事务内完成，否则需要可恢复的发布协议。仅让重复写覆盖同一键，还不足以防止读者看见半组边。[Flink 2.3 Checkpointing](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/dev/datastream/fault-tolerance/checkpointing/)

#### 7．最终存什么，怎样用于变更影响和故障溯源

定义存储保存 `environment + tenant_id + task_id + code_version` 对应的完整声明关系；运行存储保存 run、attempt、查询、状态、提交证据与观察到的字段关系。关系边保留来源方法、解析状态和证据引用。`declared`、`runtime_observed`、`write_confirmed` 是本例的不同证据标签，不是一个由低到高必然正确的准确率分数：运行观察和写成功也不能代替字段映射验证。

查询“订单金额字段改动影响哪里”，可以沿直接金额依赖找到地区日报 `gmv_yuan`；查询“支付状态枚举变化影响哪里”，还应遍历控制依赖。排查“本日地区日报为什么没更新”，则查看该业务日期的运行尝试和提交状态，不能因为静态图上一直有依赖边，就断言数据今天已产出。

假定未来 v4 把地区直接固化到订单事实，不再读取客户日快照：发布新定义时，用 v4 的完整关系集合生成当前定义视图，客户表依赖在 v4 中失效，但 v3 与本次历史运行的关系仍可查询。不能仅凭最新到达的一条运行消息删除旧边，也不能让所有版本的边永远累加。若其他任务仍依赖该客户表，还应保留它们各自的关系依据。

“分钟级更新”要从运行事件产生计时，到服务可查到对应完整证据集合为止，包含采集队列、Kafka、Flink、持久提交和索引刷新；它不意味着一天运行一次的业务任务变成每分钟生产一次数据。覆盖率、字段准确率和更新延迟要分开验收，S8 给出相应分母与检查方法。

#### 8．遇到 explode、UDF、RDD 与 API 时怎样保持诚实

若同一订单任务新增明细展开 `explode(items)`，结果中的商品字段可以追到 `items` 或可解析的嵌套字段，同时记录一单变多行。展开后再 SUM 订单总金额会因重复而放大；血缘关系能提示风险，但还需要粒度与金额对账发现错误，不能因为画出了字段边就认定计算正确。

若将地区改为 `normalize_region(c.region)`，可记录参数字段、UDF 名称与版本，以及已知的处理描述。若 UDF 内部还读了一个外部字典，而计划与声明中均未暴露，就标记外部依赖未知；“看见 UDF 参数”不等于已经理解全部函数语义。

如果有人绕过 SQL 用 RDD 闭包或 API 读取另一份地区映射，RDD 依赖图最多说明已有的计算依赖，未必保留业务表和字段。可以通过读写 SDK 埋点、显式输入输出声明和连接器适配补齐；只能取得表级证据时就保存表级，并标记字段未解析。Flink 不会凭后续事件处理自动恢复源头从未采集到的字段语义。

#### 9．面试时如何讲清这条链路

可以这样回答：“我会把血缘的定义关系与运行证据分开。以地区 GMV 日报为例，发布时解析 SQL，并结合 Catalog、临时视图和参数得到订单表、客户表到日报的声明依赖。Spark 运行时再采集已解析计划、SQL 执行和 Job 关联，补充这次尝试到底解析和执行了什么。字段层面，金额聚合生成 GMV，客户地区生成分组名称；支付状态、日期、Join 键还作为控制依赖保存。采集事件异步进入 Kafka，Flink 按运行与尝试关联上下文，处理重复与乱序；失败重试分开记录，在满足目标写提交条件后发布成功产出证据。这样既能在发布前做变更影响分析，也能按具体业务日期追查失败。遇到 UDF、RDD 或 API 的不可解析部分，就保留已知粒度与缺口，通过适配或声明补齐，不把未知字段关系伪装成完整采集。”

### S6 血缘系统建设的业务问题与架构

参考回答：血缘记录数据资产之间的依赖及形成依据，能支持变更影响分析、故障溯源、敏感数据传播追踪和下线检查。建设前应选一个可验收的问题，例如字段变更前能否识别受影响报表；仅展示一张关系图不足以证明业务价值。

可采用的设计是：采集层接入调度定义、SQL、引擎计划和运行事件；处理层解析、统一资产标识、串联合并运行关系并保留证据；存储层保存资产、依赖边、版本和来源；服务层提供上游追溯、下游影响、变更检查及权限过滤。依赖边至少带源/目标、任务与运行 ID、解析方法、有效时间、表或字段粒度、可信程度。开发语言可以是 Java，也可以混合多种语言，不能从架构倒推出原项目一定使用 Java。

资产标识要包含环境、Catalog、数据库和表，避免测试表与生产表同名后误合并；文件路径还要统一协议和路径表示。任务重跑、失败尝试、重试成功也应分开保存。发布代码声明的预期关系与本次成功运行观察到的关系可以并存，查询时标明来源，避免失败任务的计划被展示成已经发生的数据生产事实。是否采用图数据库，应由多跳遍历、更新量和运维能力决定，关系表加索引同样可以实现不少血缘服务。

项目价值应报告有统一口径的前后对比，如规定范围内影响分析的人工作业耗时、能定位根因的故障比例、过期血缘数量。节约工时、避免事故数量必须有样本和记录；原文“覆盖率从约 80% 到 95%”仍是待解释的经历，不能直接作为当前候选人的成果。

在 S0 的日报案例里，可以将交付物具体说成：发布前能从订单/客户字段追到地区日报，运行后能查询某个业务日期的失败尝试、重试和提交证据。工程链路与服务接口解决“采到、存下、查到”，治理验收则回答字段变更是否真的找到受影响资产、失败日期能否准确溯源。这两类成果需要分别举证。

资产关系与运行事实建议分开建模。定义关系以环境、租户、任务和代码版本为范围；运行证据再包含逻辑运行、调度尝试、Spark Application/Attempt、Session 和查询身份。表资产按完整限定名归一，临时视图按会话隔离，字段沿 Schema 版本解释。仅存 `source_table,target_table` 无法说明这条关系是哪版代码、哪次运行、什么方法得到的。

面对“你用 Java 做了什么”这类追问，应讲自己实现的采集插件、消息契约、解析适配、状态归并或查询接口及对应测试。S0 中的 Flink 是血缘事件处理层，订单计算仍由 Spark 执行；不能把接入 Flink 消费 Kafka 描述成重构了全部业务计算。

### S7 SQL、DataFrame、RDD、API 怎样采集血缘

参考回答：静态 SQL 适合在发布前解析 AST，但需要结合 Catalog 解析别名、`SELECT *`、视图和字段归属。动态 SQL 要采集参数展开后的实际语句；临时表、临时视图要结合会话与运行 ID 追踪中间节点；动态分区要从执行计划或写入结果补充实际目标，不能只靠源代码字符串推断。

DataFrame 通常能从 Spark 逻辑计划提取输入、输出和表达式依赖。OpenLineage 的 Spark 集成使用 Listener 及 RDD、DataFrame 依赖信息，字段级血缘进一步解析逻辑计划中的表达式关系。这并不代表任何版本、任何连接器或任意用户代码都能自动得到完整字段血缘。[OpenLineage Spark 集成](https://openlineage.io/docs/integrations/spark/)、[字段血缘实现](https://openlineage.io/docs/integrations/spark/spark_column_lineage/)

RDD 的转换依赖图能说明计算依赖，却不必然包含业务表名、字段名和任意闭包内部逻辑。API 任务也可能只暴露输入输出资源。对此可包装读写 SDK、使用显式血缘上报接口、补充开发者声明或连接器插件；暂时只能知道表级关系时，就记录表级并标识缺口，不能伪造字段关系。

`explode(items)` 的输出元素依赖原数组字段，行数会增加，字段依赖不要求输入输出一一对应。UDF 至少可记录其参数字段及 UDF 标识；若 UDF 访问外部资源或生成不能追溯的值，要额外声明或标为未知。`WHERE`、`JOIN` 中的字段可能影响哪些行被保留，而不直接生成某个输出值，应区分直接转换依赖和间接控制依赖。[OpenLineage 字段血缘规范](https://openlineage.io/docs/spec/facets/dataset-facets/column_lineage_facet/)

静态解析可以拆成语法识别和语义绑定两步。AST 识别读取、写入、Join、聚合等结构；结合 Catalog、当前库、临时对象定义和参数，才能把别名及列引用绑定到实际资产。S0 中 `o.paid_amount_fen` 要先经过临时视图才能回到订单事实。Schema 或临时视图上下文缺失时，应留下未解析节点，不能用同名字段猜来源。

Spark 运行时计划让采集器看到本次实际解析的字段和关系，尤其能补上动态 SQL 展开结果和部分 DataFrame 场景；它仍需要适配已使用的引擎、连接器与读写入口。QueryExecution 的计划内表达式标识只适合该计划的依赖追踪，跨作业字段身份需要完整资产名与 Schema/字段版本。运行时采集并不自动替代静态关系，两者可互相核验并保留证据差异。

字段准确性应检查值来源与控制作用。S0 的 `gmv_yuan` 直接依赖金额聚合和单位换算，支付状态与币种影响参加聚合的订单；目标分区 `dt` 则来自参数常量，而非源日期列的直接复制。`COUNT(order_id)` 在非空前提下有明确 ID 参数，`COUNT(*)` 统计行集，不能为了补一条字段线而虚构直接 ID 依赖。

提升采集覆盖时，先归类当前无法解析的实际任务，再为动态 SQL、临时对象、特定连接器或 SDK 读写添加适配，并用有正确答案的案例核对。`explode`、UDF、RDD 与 API 的能力边界见 S0 第 8 节；未知依赖需要明确标记，避免“接入了任务”被误写成“字段血缘完整”。

### S8 异步采集、分钟级更新与准确性评估

参考回答：Listener 回调只采集必要标识和计划摘要，事件进入有界队列，由独立线程或旁路进程发送 Kafka，Flink 消费后做标准化、去重、关联和增量写入。事件应有稳定唯一标识，重试后仍能幂等；同一任务的新旧版本要按运行时间或版本处理，不能让晚到旧事件覆盖新关系。Flink 在这里处理血缘事件，并不意味着业务计算本身也必须改成 Flink。[SparkListener 接口](https://spark.apache.org/docs/3.5.6/api/java/org/apache/spark/scheduler/SparkListener.html)

异步不等于零影响。采集会消耗 Driver CPU、内存和队列资源；Kafka 不可用时，要在阻塞、丢弃和本地持久缓冲之间明确选择。业务主链路优先时，旁路故障通常不应拖死计算，但丢失事件必须可观测，并能够通过 Event Log、调度记录或补采恢复。这里是参考设计，是否能补采取决于实际保留的证据。

“分钟级”应定义为业务运行事件产生，到血缘服务可查询的端到端延迟，并监控其 P95/P99、Kafka 积压、处理失败和落库延迟。某批任务一天才运行一次，事件管道一分钟更新并不能让该表每天的新依赖提前出现。

覆盖率和准确率要分开算。任务覆盖率可以定义为“规定范围内产生合格血缘的任务数 / 应覆盖任务数”；表、字段、连接器分别统计。边精确率是“被人工确认正确的上报边 / 被抽检的上报边”，召回率需要另有正确关系基准，不能用“任务接入率”替代。提升 80% 到 95% 前先固定分母、时间范围和合格标准，再分析未覆盖任务属于动态 SQL、RDD、自定义连接器还是采集失败，按缺口补适配，使用同一分层样本回归。

验证集应覆盖别名、多层视图、CTE、窗口、聚合、Join、`UNION`、临时表、UDF 和写入失败等语义不同的场景；逐条检查应有边与不应有边。只检查“图上有线”容易漏掉错误关联。字段重命名、表重建与任务下线还要检查旧关系如何失效，防止只增不删造成覆盖率看似上升、影响分析范围却不断膨胀。

S0 的七步事件序列给出了一个可实现的处理闭环：同一运行的不同尝试分开保存，查询完成先到时保留待补齐上下文，重复事件不增加证据边，迟到 START 不把完成事实降回运行中。更高修订替换同一事件的旧断言并重新生成证据集合，不能把错误旧边一直累加。跨应用的查询局部编号也必须放进完整身份范围后使用。

持久化还需区分“记录幂等”和“完整结果可见”。稳定证据键可以消除重复写，但一次运行的边写到一半，读服务仍可能看到不完整图。本例通过完整集合的校验与发布标记控制可见性；真实后端可用事务或可恢复的发布协议实现。Checkpoint 只覆盖其实际纳入的一致性边界，外部写入必须有对应的提交或幂等设计。

假设教学范围内固定有 1000 个应采集任务，800 个产生合格血缘，覆盖率为 80%；补齐 150 个后是 95%。这里仍需说明“合格”要求表级还是字段级、证据时效和成功/失败运行如何计入。即使任务覆盖达到 95%，字段边也可能有误报；要用独立人工或规则基准分别算正确边比例、缺失边比例，并记录暂不可解析部分。事件延迟缩短则是另一项指标，不能用分钟级更新证明覆盖率或准确率提高。

### S9 Parquet 结构、排序与统计过滤

参考回答：一个 Parquet 文件包含多个 Row Group；每个 Row Group 保存一批行，并为每个叶子列组织 Column Chunk；Column Chunk 再分成 Page。Footer 的文件元数据记录 Schema、Row Group 和列块位置等，读者先读元数据，再定位需要的列块。Row Group 是逻辑水平分组，Column Chunk 是某列在该组的数据，Page 是编码、压缩的单位；它们不等于 HDFS Block，也不能直接等同 Spark Task。[Parquet Concepts](https://parquet.apache.org/docs/concepts/)、[Parquet 文件布局](https://parquet.apache.org/docs/file-format/)

排序字段应从真实查询选择：常用且有选择性的范围过滤列、时间列或经常组合过滤的列可能适合，具体顺序取决于过滤分布和查询比例。低基数字段聚集后可能形成更长重复段，时间或递增字段相邻差值可能更小；排序还可能让不同 Row Group 的值域更集中。多列排序时，后续列的局部有序性受前缀列影响，不能声称每列都同样受益。

例如时间过滤条件与某个 Row Group 的时间范围完全不相交，读取器可以跳过该组；如果各组都同时覆盖整月数据，月内一天查询就难以靠该统计跳过大量数据。需要同时满足 Writer 写出可用统计、谓词能够被下推、Reader 支持相应裁剪，才可能减少 I/O。Page Index 是可选的细粒度索引，支持它的 Reader 可进一步跳 Page；仅看到执行计划含过滤条件，不足以证明实际读取字节下降。[Parquet Page Index](https://parquet.apache.org/docs/file-format/pageindex/)

### S10 编码、ZSTD 与“深度优化”怎样回答

参考回答：编码先利用值的分布减少表示成本，压缩再处理编码后的字节。字典编码适合列块内重复较多、字典成本可控的值；高基数、长且近乎唯一的字符串容易让字典得不偿失，Writer 可能退回普通编码。RLE 适合长重复序列，字典 ID 也可以用 RLE/位打包表示；Delta 适合某些整数序列或有共同前缀等结构的数据，但支持哪些编码取决于类型和 Writer，不能把三个编码当成任意字段都可手动切换的同层开关。[Parquet 编码规范](https://parquet.apache.org/docs/file-format/data-pages/encodings/)

ZSTD 级别提高通常会增加压缩 CPU、内存消耗，并可能进一步减小文件；收益随数据和实现变化，不保证逐级平滑。约 11 级只能是某次基准测试的选择，回答中必须提供当时的数据、机器、Writer 版本和测量结果。不能用“11 级压缩率最好”替代证据。[Zstandard 级别说明](https://github.com/facebook/zstd/blob/dev/programs/zstd.1)、[Zstandard 官方选型讨论](https://engineering.fb.com/2016/08/31/core-infra/smaller-and-faster-data-compression-with-zstandard/)

如果被问“深度优化具体做了什么”，可按已做事项回答：在相同数据与资源下，分别测试文件和 Row Group 大小、排序布局、字典及编码设置、压缩算法与级别；观察产出字节、写入墙钟时间与 CPU、峰值内存、代表查询的读取字节和延迟，再做字段值与行数的等价性核验。只有实测过的配置才能称为成果；未做实验时，把它说成候选方案，并说明准备用什么指标验收。

文件变大能减少文件枚举和请求次数，也可能降低并行度；Row Group 变大会改变缓冲内存和裁剪粒度。排序本身还有 Shuffle、磁盘和延迟成本，所以收益应按完整链路计算。冷数据很少查询、保留时间很长时，可以接受更多压缩 CPU 来省存储；频繁写入、需要赶 SLA 的热数据，则要约束写入耗时。不能只展示压缩后文件变小，就断言整个作业更快或总成本更低。

### B2 商品中台与统一资产接入

商品中台通常沉淀多个业务共用的商品身份、基础属性、类目、品牌、规格和扩展特征；统一资产接入则解决不同来源如何按统一契约接进来、验收并提供给下游。面试时先解释项目中的“资产”具体是商品、图片、标签还是数据集，再谈平台功能，避免把资产接入直接等同于建几张表。

可采用的设计是：接入登记保存来源、负责人、主键、更新方式、Schema、权限和 SLA；采集层处理全量与增量衔接；标准化层统一身份映射、单位和枚举；质量层检查唯一性、完整性与新鲜度；发布层提供版本、查询接口或数据订阅。商品与 SKU 的对应关系、删除和下架语义、乱序更新优先级都需要成为明确契约。接入成功应同时满足数据写入成功、质量验收通过、权限配置生效和下游可用。

是否开发服务接口取决于使用方式。数仓批量分析可以通过表交付；业务页面点查需要稳定 API、超时、限流和权限；变更通知可以使用消息。不能根据“做中台”推断自己一定写过 Java 服务，必须说清实际交付物。

### B3 图片识别和标签回写

图片二进制适合放对象存储或现有媒体存储，数仓维护图片元数据和识别结果。元数据可包含 `asset_id`、业务实体 ID、`object_uri`、`object_version`、`content_hash`、格式、尺寸、来源、采集时间和可用状态。`asset_id` 表示逻辑资产，版本或内容摘要区分图片更新；同一商品有多张图时，还需要图片角色和顺序，不能只用商品 ID 区分结果。

批处理先生成输入清单，再按批次读取图片、校验格式和大小、调用模型、校验结构化输出并落库。结果记录输入资产与版本、`model_version`、提示词或配置版本、标签体系版本、标签值、置信度及状态。关联应依赖稳定 ID 和版本，不能依赖返回顺序。一个可复用的幂等键是“资产版本＋模型版本＋识别配置版本”；具体是否按内容摘要跨资产复用结果，要由业务授权和上下文是否相同决定。

调用端根据模型吞吐和限额控制并发、批大小及重试，临时失败使用退避重试，永久错误进入待处理队列。批次中部分图片成功时，只重试失败项；任务超时后重试可能再次产生模型费用，结果写入幂等不等于外部调用只发生一次。回写后核对输入、成功、失败、跳过数量及版本对应关系，不以任务“结束”代替验收。异步批量识别和结果写入对象存储是现有视觉服务支持的模式，但单批限制应以选定服务为准。[Cloud Vision 离线批处理](https://docs.cloud.google.com/vision/docs/batch)

多模态模型通常直接接受图片或图片引用，内部自行编码，不要求业务先把图片转换成向量。只有模型接口明确要求预计算特征，或者另有相似图检索、聚类、向量召回任务，才需要单独计算和存储向量。图片向量本身不能替代模型需要的完整视觉输入。

### B4 宽表和主题域

宽表通常在明确业务粒度下，把分析经常一起使用的事实、维度属性和派生字段组织到一张表中，减少下游反复关联。判据包括“一行代表什么、哪些字段描述同一对象或事件、如何处理一对多、服务哪些稳定查询”，不能只看列数。几十列的订单分析表可能是宽表，几百列但没有稳定粒度的临时结果也不一定是合格的公共宽表。

例如订单粒度宽表关联订单明细时，一张订单有多个商品，会改变行数和金额可加性。应选择订单明细粒度、先按订单聚合，或把一对多内容作为明确的集合字段；不能将重复金额留给下游自行理解。普通明细表也可能物理上很宽；临时表与公共宽表的差异还在于是否有稳定口径、负责人、质量和生命周期。

若为 Kimi 规划主题域，可把用户与账号、获客与流量、会话与交互、模型调用与推理、订阅交易、内容资产、服务质量等作为候选，再根据真实业务过程、责任组织和数据复用关系确定边界。这是设计示例，不是对 Kimi 内部架构的描述。模型调用域可以记录调用和计费事实，质量域可以基于同一调用记录形成延迟、错误和评估结果，原始事实的归属与跨域分析可以并存。

一张表同时有埋点、广告和营销字段时，应按主要业务过程和粒度判断。一次广告曝光归广告投放过程，一次站内访问归流量过程，一次优惠券发放归营销过程；其他域字段可作为关联属性。若一张表混合了曝光、访问和优惠券事件且没有统一粒度，应拆分基础事实，再构建跨域应用表，不能靠给表挑一个目录解决建模问题。

### B5 怎样衡量好的数仓

好的数仓要在约定成本下，按时交付口径明确、质量可核验、权限可控制的数据。建模看业务过程与粒度是否一致、公共维度和指标是否复用；成本看存储、计算及闲置浪费，并结合业务规模比较；SLA 看约定时间前可用比例、新鲜度和恢复耗时；质量看主键、完整性、金额对账及异常闭环；权限看最小授权、敏感字段保护、审计和撤权是否落实。

这些指标必须给出分母和统计窗口。“质量通过率 99%”需要说明是规则、表、分区还是记录通过率，是否按业务风险加权；“存储下降 30%”要确认数据保留范围、压缩口径、副本和备份是否一致。“有分层、有规范、有治理平台”只能说明采取了措施，不能直接证明下游数据可信或成本合理。

### B6 标签回流为何从 T+3 改到 T+1

先拆清原来三天花在哪里：原始数据何时到齐、标签何时加工、质量何时验收、何时等待统一发布、何时被下游拉取。若某个输入直到 T+2 才产生，单纯增加计算资源不能获得同口径 T+1 结果。回答改造效果时应同时说明数据覆盖时间和可用时间，“T+1+2 小时”必须解释相对于哪一时刻增加两小时。

可采用的优化是让接入、特征加工、标签计算、质量验收和发布通过版本化数据契约衔接，完成一个独立批次就向后推进，不再等待所有标签共同结束。大标签按数据量、扫描范围和耗时单独调度，小标签尽早完成和发布；资源隔离后仍需验证存储、网络和调度队列是否共享瓶颈。拆分后要提供同版本快照或明确新鲜度，防止下游把不同时间的标签拼成一个未经说明的用户或商品画像。

窄表/高表可用“实体 ID＋标签 ID＋生效版本”保存一条标签值，并带上类型、时间和来源，适合标签数量变化快、更新范围不一致的场景。代价是行数膨胀，多标签组合分析可能需要多次关联或透视，因此可以按服务场景再生成稳定宽表或查询索引。不能用一个字符串列无约束地承接所有值，仍需统一值类型、空值、删除和版本语义。

结果是否进入 Doris 取决于查询模式、数据规模和更新特征。批量人群或商品圈选更关注扫描与聚合；单实体取若干标签更关注主键访问、数据布局、并发及接口开销；大规模批量回流可通过文件或消息交付。先说访问路径，再解释存储选择，不能仅用“Doris 查询快”回答系统设计。

### B7 下游交付、集群规模、QPS 和 TP90/TP99

推送适合约定批次的结果交付，API 适合按需点查，消息适合传播增量变化。它们可以组合使用，但都要定义实体 ID、版本、删除、重复和重放行为。下游怎样使用 Doris，要讲清由谁提交 SQL、是否经过服务层、查询命中哪张表、结果如何转成业务响应；存到 Doris 只回答了链路中的一个环节。

QPS 是否足够需要在真实查询分布、数据规模、并发、缓存命中率和写入负载下验证，并同时报告错误率和延迟。“压测达到某 QPS”还要说明是发送速率还是成功完成速率，持续多久，是否发生排队。集群节点数、CPU、内存、磁盘、副本和版本是测试条件，不存在能脱离工作负载直接推荐的统一规模。

TP90 和 TP99 分别表示约 90% 和 99% 的观测请求耗时不超过该值。应区分 API 端到端耗时、Doris 查询耗时和标签新鲜度；前者包含鉴权、排队、网络和序列化。多实例总体分位数需要合并兼容的分布再计算，不能直接平均各实例 P99；Prometheus 的 histogram 和 summary 在能否跨实例聚合分位数方面不同。[Prometheus 分位数与聚合](https://prometheus.io/docs/practices/histograms/)

### B8 1600 亿行加工为 400 亿行并满足 10 点 SLA

这组数字是原文追问，现有资料不足以还原当事人方案。参考回答应先确认输入与输出的粒度、时间范围、去重及聚合规则、文件字节量、Join 基数和上游就绪时间。1600 亿到 400 亿只能说明记录数变化，不能说明过滤有效、业务等价或性能达标。

定位时建立完整依赖和关键路径，区分等待资源、扫描、Shuffle、计算与写出时间。若慢在主链路之外，优化它不会提前总体完成时间；若输入未到齐，提前启动还要定义迟到数据如何补齐。选择改写、资源调整或调度拆分之后，用相同数据范围比较总耗时、关键阶段长尾、资源成本和结果等价性，再验证高峰日是否能在 10 点前交付。广播和倾斜治理的具体做法应接着绑定真实执行计划与 Task 证据说明。

### B9 Java 和 Python 如何选择

Java 适合已有 JVM 工程体系中的长期运行服务和 Flink/Spark 扩展，静态类型、依赖管理和成熟的服务治理便于团队维护。Python 适合数据探索、自动化脚本、模型调用与训练生态，开发和验证成本通常较低。但计算重不等于必须 Java：Python 调用 NumPy、Arrow 或模型框架时，大量工作在本地库或加速器上运行；Java 服务调用远程模型时，也可能主要等待网络。

选型应比较热点代码在哪里运行、并发模型、延迟要求、内存、依赖生态和团队维护能力。传统启用 GIL 的 CPython 对 CPU 密集的纯 Python 多线程有约束，可以考虑多进程或本地计算库；CPython 从 3.13 起还提供可选的 free-threaded 构建，不能把 GIL 描述成所有 Python 运行环境的固定限制，依赖兼容性也需核实。[Python free-threading 文档](https://docs.python.org/3/howto/free-threading-python.html)

### B10 公司数据规模、来源与平台技术栈怎么回答

参考回答方法：分别说明总量和每日增量的统计日期、存储层与口径，例如逻辑记录数、压缩后文件字节数、是否包含副本与历史版本。再区分车端传感器、业务库 CDC、埋点、销售与商城等来源，说明各自占比依据；没有统计就明确尚未统计。

Spark 是计算引擎，HDFS 是分布式文件系统，Iceberg 是表格式，三者可以同时出现在一条链路，不能把它们当互斥选项。自研平台通常指提交、调度、元数据、权限、监控或服务层等具体能力，并不意味着底层存储与计算也全部自研。原文没有给出当事公司的真实规模、来源分布和部署架构，无法从这些追问反推出答案。

### C1 collect_set、collect_list、SUM 与窗口函数

参考回答：`collect_list` 收集元素并保留重复值，`collect_set` 去掉重复元素；两者返回数组，不能依赖 Shuffle 后的数组顺序，也不把输入的 NULL 元素收进结果。需要稳定展示顺序时，应定义业务排序规则，再对收集结果排序；按值排序和按事件时间排序是两回事。大分组会积累大数组，去重也不能消除全部内存风险。[Spark 内置函数](https://spark.apache.org/docs/3.5.7/api/sql/index.html#collect_list)

在 Spark SQL 中，`SUM`、`collect_set`、`collect_list` 可以作为聚合窗口函数使用。`collect_set(v) OVER (...)` 不等于 `COUNT(DISTINCT v) OVER (...)`，不能因前者可用就推断所有 DISTINCT 窗口聚合都支持。窗口保留输入行，每一行附加该行窗口内的结果；普通 `GROUP BY` 则收缩为每组一行。带 `ORDER BY` 时要写清窗口边界，避免默认 frame 与预期不同。[Spark 窗口语法](https://spark.apache.org/docs/3.5.7/sql-ref-syntax-qry-select-window.html)

```sql
SELECT
    user_id,
    event_seq,
    amount,
    SUM(amount) OVER (
        PARTITION BY user_id ORDER BY event_seq
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS cumulative_amount,
    SORT_ARRAY(COLLECT_SET(category) OVER (
        PARTITION BY user_id
        ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
    )) AS categories
FROM VALUES
    (1, 1, 10, 'A'),
    (1, 2, 20, 'A'),
    (1, 3, 30, 'B')
AS events(user_id, event_seq, amount, category);
```

这里 `event_seq` 在用户内唯一，因此累计金额对应 10、30、60；类别数组每行都是 A、B。若排序键并列，`ROWS` 的逐行结果还需要额外稳定排序键。

### C2 concat_ws 的语义与使用边界

参考回答：`concat_ws(separator, value1, value2, ...)` 用分隔符拼接字符串，也可处理字符串数组。它跳过 NULL 值，但不跳过空字符串；分隔符为 NULL 时返回 NULL。例如 `concat_ws('|', 'A', NULL, '')` 得到 `A|`。[Spark concat_ws](https://spark.apache.org/docs/3.5.7/api/sql/index.html#concat_ws)

它适合展示文本，不适合未经设计就生成唯一键或行级校验串。`('A', NULL, 'B')` 与 `('A', 'B', NULL)` 会产生相同拼接结果，字段值内还可能含分隔符。行级校验应固定字段顺序、数据类型、NULL 表示和转义规则，或采用保留结构与空值的序列化；哈希碰撞和重复行还需要单独处理。

### C3 每天均匀抽取 12% 日志

参考回答：先确认抽样单位是日志行、事件、用户还是会话，以及要求每天约 12% 还是精确 12%。按用户 ID 抽样会保留被选用户的全部日志，不能声称每条日志独立均匀。对于每天约 12% 的事件样本，可以在限定日期分区后，对非空、稳定、区分事件的 ID 做哈希取模；这样同一事件重跑时仍作同样选择。

```sql
SELECT event_id, event_time, user_id, event_type
FROM dwd_event_log
WHERE dt = '2026-11-15'
  AND event_id IS NOT NULL
  AND PMOD(XXHASH64(event_id, 'sample-v1'), 10000) < 1200;
```

这里约定 `dwd_event_log` 是日分区日志表，`event_id` 稳定且非空；NULL 记录必须先修复或按另行约定的标识处理，不能悄悄丢掉后声称覆盖全表。哈希方法依赖键和哈希分布，比例只有近似保证。要每小时、每个渠道都有接近 12% 的代表性，可以按这些维度分层并检查各层偏差；小分层仍可能波动。抽样条件通常不能让文件扫描量直接降至 12%。`xxhash64` 从 Spark 3.0 提供，Spark 2.4 可评估 `hash` 等替代函数，但样本集合会变化。[Spark xxhash64](https://spark.apache.org/docs/3.5.7/api/sql/index.html#xxhash64)

如果要求每天精确取 `floor(N * 0.12)` 行，可先计数，再按哈希值与唯一 ID 的稳定全序取前若干行；分层精确抽样则按层计数并排名。这会引入排序和 Shuffle。只有业务确实需要精确数量时，才支付这部分成本。`rand(seed)` 可以做随机抽样，但不能把固定种子等同于跨不同分区布局和执行计划仍抽到相同事件。

### C4 两张大表 Join、热点 Key、Broadcast 与加盐

参考回答：先分清总量大和分区不均。所有 Task 都有较大输入、耗时接近，偏向整体规模或资源问题；少数 Task 的输入、Shuffle Read、Spill 和耗时远高于其余 Task，才支持倾斜判断。还要把 Task 绑定到实际 Join 阶段，排除失败重试、读文件慢和机器异常。对热点键抽样或按键计数，确认 NULL、空串、默认值及多对多关联是否造成大分组或输出爆炸。

对整体规模问题，先做分区裁剪、列裁剪和安全的过滤下推，再检查是否可以在 Join 前聚合、改为半连接或减少重复计算。这些改写都要以所需输出粒度和业务语义为前提，不能为了减数据擅自去重。更新统计信息、选择合适 Shuffle 并行度、治理小文件、验证排序合并连接或分桶复用，通常比直接给所有键加盐更可控。分桶能否省 Shuffle，要以引擎版本、桶兼容条件和实际物理计划为准。

以常见的 Sort Merge Join 为例，上游读取分区，按 Join 键计算分区号并写出 Shuffle；下游读取对应分区，排序后合并匹配。相同等值键必须到同一个对应分区才能完成匹配，热点键因此集中。Spark 的 Task 不必机械对应传统 MapReduce 的 Map/Reduce 进程，具体是否出现 Exchange 和 Sort 要看物理计划。

热点 Inner Join 可拆为热点与普通键两条互斥路径：热点侧大表每行分配一个稳定盐值 `s`，另一侧仅将相应热点键的行复制为 `s=0..S-1`，再按原键与盐值匹配，最终去掉盐列，用 `UNION ALL` 合并普通路径。双方各自随机加盐会漏匹配；双大表若将一侧全量复制，会带来很高成本。Outer、Semi、Anti Join 还需单独验证未匹配行和重复语义，不能套用 Inner Join 方案。

原题“加盐后为什么还需要去掉前缀并再次聚合”存在前提：只有做了两阶段聚合，才需按原键合并局部结果，例如局部 SUM 再 SUM，AVG 则保存局部 SUM 与 COUNT。单纯 Join 加盐后，移除盐列即可，额外聚合可能改变重复行。相同键之间本来存在的多对多结果不会因为加盐消失。

小表使用 Broadcast Join，是为了把可容纳的构建侧分发到执行器，减少大表按键 Shuffle。能否广播要看过滤后的体积、Driver 构建与收集负担、执行器内存和广播时间，行数少不自动代表安全。Spark 3.x 的 AQE 可在条件满足时拆分倾斜 Shuffle 分区；是否生效需看开关、阈值和最终计划，Spark 2.4 不能直接套用这套能力。[Spark Join 与 AQE 调优](https://spark.apache.org/docs/3.5.7/sql-performance-tuning.html#optimizing-skew-join)

任何优化验收都要同时记录运行时间、资源消耗和结果等价性。行数相同还可能字段值不同，可在相同输入快照下做双向 `EXCEPT ALL` 并核对字段、NULL、重复及金额；先确定 SLA 是否从数据到齐开始计算，再判断单条 SQL 的加速能否缩短完整链路。

### C5 Kafka 重复数据如何在 Flink 去重

参考回答：Kafka 的位点标识消息位置，不等于业务事件 ID。同一事件被上游重复发送到两个 offset，恢复一致性也不会自动合并它们。先定义重复键和保留规则，例如按 `event_id` 保留第一条，或按 `(order_id, version)` 只处理一次；CDC 同一主键的不同版本是有效变更，不能全部当重复删除。

精确的有限范围去重可以 `keyBy(event_id)`，用 `ValueState` 保存是否处理或事件版本，未见过才输出并更新状态。生产中要处理空键、重复冲突和乱序；窗口结束或明确的重放边界到达后才清理状态。若按业务实体维护多个事件 ID，可使用 `MapState`，状态量与保留期内去重键数量相关。[Flink Keyed State](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/dev/datastream/fault-tolerance/state/)

State TTL 限定的是去重记忆的寿命。TTL 过后相同事件可能再次输出，因此不能同时声称“有限状态”和“无限历史精确去重”。Flink 2.3 常规 State TTL 使用处理时间；若业务要求按事件时间到期，应设计事件时间定时器、watermark 与迟到处理。`OnCreateAndWrite`、`OnReadAndWrite` 会改变重复访问是否续期，逻辑过期也不等于磁盘立刻释放。[Flink State TTL](https://nightlies.apache.org/flink/flink-docs-stable/docs/dev/datastream/fault-tolerance/state/#state-time-to-live-ttl)

布隆过滤器用较小内存判断“肯定不存在”或“可能存在”，可能误报。如果把“可能存在”直接丢弃，会丢掉未出现过的新事件。严格去重可把它当作精确存储前的预筛选，并让精确集合决定最终保留；此时仍要解决集合容量与并发一致性。下游主键 upsert 能让最终存储保持一条逻辑行，但不能撤销中间重复计数、外部调用或消息副作用，而且覆盖写需要定义版本顺序。

Checkpoint 恢复处理状态和 Source 进度，使失败后的重放从一致位置继续；端到端结果还取决于 Sink 的事务提交或幂等实现。要分别核对上游业务重复、作业恢复重复和最终写入重复，不能用一个“exactly-once”概括所有层。[Flink 状态与一致性](https://nightlies.apache.org/flink/flink-docs-stable/docs/concepts/stateful-stream-processing/)

### C6 每个商品的累计状态、窗口、Checkpoint 与 TTL

参考回答：对商品事件 `keyBy(product_id)`，用 `ValueState` 保存累计值，每次读取旧值、按事件含义计算新值，再更新并输出。如果输入是带版本的库存快照，应按版本替换或计算正确增量；如果输入是订单变更，要处理取消、退款与更新的撤回语义。对所有记录直接相加，只适用于去重后的真实增量输入。

按小时统计时，可以选事件时间滚动窗口，明确时区与对齐规则，使用 watermark 表达允许的乱序。watermark 越过窗口结束时间后触发计算；允许迟到的数据可能再次触发更新，超过允许迟到范围的数据需要侧输出或补算。使用滑动窗口会让一条事件进入多个窗口。下游收到的是最终一次结果还是多次修正，必须与 append、upsert 或 changelog 的处理方式一致。[Flink 窗口、触发与迟到数据](https://nightlies.apache.org/flink/flink-docs-release-2.3/docs/dev/datastream/operators/windows/)

恢复时使用完成的 Checkpoint，把算子状态和 Source 进度恢复到一致快照，并从相应位置重放。部署变更需要稳定的算子 UID、兼容的状态序列化与可恢复的 checkpoint 存储；Sink 的提交和重试机制决定外部结果如何保持一致。单有 Checkpoint 开关，无法保证任意 HTTP 调用只发生一次。

“终身累计”与“长时间不活跃就清掉累计值”是不同口径。若累计值只存在 State 中，直接加 TTL 会让商品再次活跃时从零开始。需要终身累计时，可将完整历史沉淀到可恢复的持久层，或明确冷热迁移与回载协议；短周期累计则按窗口结束清理。先定义保留期和恢复来源，再讨论状态规模。

### C7 网吧用户对 SQL：明确时间条件与去重粒度

原题没有给表结构，“上下线相差不超过 10 分钟”也可能指上线、下线都接近，或仅要求某类事件接近。以下采用一个明确口径：每行是一段完整会话，同一家网吧内，两名不同用户的上线时间差和下线时间差都不超过 600 秒；至少在三个不同网吧满足一次。现实中这只能定义题目中的关系标签，不能证明两个人一定认识。

约定输入表 `cafe_session` 包含 `user_id`、`cafe_id`、`login_s`、`logout_s`，后两列是同一时间基准下的整数秒。SQL 保留每家网吧一次证据，不把同一家网吧的多次会话累计成三家。

```sql
WITH valid_sessions AS (
    SELECT DISTINCT user_id, cafe_id, login_s, logout_s
    FROM cafe_session
    WHERE user_id IS NOT NULL
      AND cafe_id IS NOT NULL
      AND login_s IS NOT NULL
      AND logout_s IS NOT NULL
      AND logout_s >= login_s
), pair_cafe AS (
    SELECT DISTINCT
        a.user_id AS user_a,
        b.user_id AS user_b,
        a.cafe_id
    FROM valid_sessions a
    JOIN valid_sessions b
      ON a.cafe_id = b.cafe_id
     AND a.user_id > b.user_id
     AND ABS(a.login_s - b.login_s) <= 600
     AND ABS(a.logout_s - b.logout_s) <= 600
)
SELECT user_a, user_b, COUNT(*) AS cafe_count
FROM pair_cafe
GROUP BY user_a, user_b
HAVING COUNT(*) >= 3;
```

`a.user_id > b.user_id` 同时去掉自己与自己的配对，并只保留 `(A,B)` 与 `(B,A)` 中一种方向，换成 `<` 也可以。只写 `!=` 会保留镜像用户对。要确保 ID 的比较规则稳定；字符串 ID 按字符串次序比较也能消除对称，不要求它必须代表数值大小。

若输入是一行一次上线或下线事件，必须先按真实会话标识配对，不能把相邻上线与下线随意拼接。若题目确认只看上线，就删去下线条件；若要求会话区间重叠，则应改用区间条件。大网吧的自连接可能形成平方级候选，可按时间桶生成候选并涵盖相邻桶，随后保留精确秒差条件；按日期强行拆开会遗漏跨午夜的 10 分钟边界。

### C8 无重复字符的最长子串

参考回答：维护一个没有重复字符的滑动窗口，记录每个字符最近出现的位置。右端遇到字符时，如果它上一次出现的位置还在窗口内，就把左端移到那个位置之后；每次更新最大长度。左端只能向前走，所以要用 `max(left, previous + 1)`，否则 `abba` 这类输入会让窗口倒退。

下面返回 Unicode 码点数量，避免把一个普通 emoji 的 UTF-16 代理对算成两个字符。它不处理多个码点组成的完整字素，例如家庭 emoji；若题目只给 ASCII 输入，这个实现也适用。设 n 为码点数量，时间复杂度为期望 O(n)，空间复杂度为 O(输入中不同码点数)。

```java
import java.util.HashMap;
import java.util.Map;
import java.util.Objects;

public final class LongestSubstring {
    public static int lengthOfLongestSubstring(String s) {
        Objects.requireNonNull(s, "s");
        Map<Integer, Integer> last = new HashMap<>();
        int left = 0;
        int best = 0;
        int index = 0;
        for (int offset = 0; offset < s.length(); index++) {
            int cp = s.codePointAt(offset);
            offset += Character.charCount(cp);
            Integer previous = last.put(cp, index);
            if (previous != null) {
                left = Math.max(left, previous + 1);
            }
            best = Math.max(best, index - left + 1);
        }
        return best;
    }
}
```

例：`abcabcbb` 返回 3，`bbbbb` 返回 1，`abba` 返回 2，空串返回 0，`😀a😀` 返回 2。这里维护的是子串的连续窗口，不是可以跳过字符的子序列。
