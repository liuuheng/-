##### MySQL 与 Redis

##### MySQL 存储引擎与适用场景

Q：MySQL 有哪些常见存储引擎？InnoDB 和 MyISAM 有什么区别，项目中怎么选？
A：生产业务库我默认选 InnoDB，因为它支持事务、行级锁、MVCC、崩溃恢复和外键，适合订单、支付这类并发读写。MyISAM 不支持事务，主要是表级锁，崩溃恢复能力弱，过去在只读或全文检索场景出现较多，但现代业务通常没有理由优先选它。实际排查时我会先用 `SHOW TABLE STATUS` 或 information_schema 确认引擎，再看事务隔离、索引和锁等待；不能只说“InnoDB 支持事务所以更好”。例如批量导入慢，要进一步检查二级索引、redo/binlog、提交批次和磁盘，而不是换成 MyISAM。Memory 引擎数据在内存、重启丢失，适合非常有限的临时场景，也不能替代 Redis。

##### 知识点补充

InnoDB 使用聚簇索引组织数据，主键叶子节点保存整行；二级索引叶子保存主键。它通过 redo log 保证崩溃恢复，通过 undo log 和 Read View 实现 MVCC，并用 buffer pool 缓存页。

##### 事务隔离级别与 MVCC

Q：MySQL 的事务隔离级别有哪些？InnoDB 如何实现可重复读，幻读怎么处理？
A：四个标准隔离级别是读未提交、读已提交、可重复读和串行化。InnoDB 默认可重复读：普通一致性读通过 undo log 和 Read View 读取快照，同一事务多次查询通常看到同一版本；读已提交则每条语句生成新的 Read View。实际更新、`SELECT ... FOR UPDATE` 属于当前读，会读取最新版本并加锁。范围当前读为了防止别的事务插入满足条件的新行，会使用记录锁加 gap/next-key lock。排查“查询看不到刚提交数据”时先确认事务边界和隔离级别；排查锁等待则看 `performance_schema.data_locks`、事务持锁 SQL 和索引是否命中，避免无索引范围扫描扩大锁范围。

##### 知识点补充

MVCC 主要解决读写并发，不代表所有操作无锁。可重复读中的快照读通过版本链避免普通幻读；SQL 标准意义的幻读与 InnoDB 当前读、next-key lock 的讨论要区分场景。

##### 联合索引与最左前缀

Q：联合索引 `(a,b,c)` 在哪些查询条件下能命中？为什么有时“用了字段”仍不走索引？
A：B+Tree 按 `(a,b,c)` 字典序排列，因此 `a`、`a,b`、`a,b,c` 的等值或从左开始的范围通常能利用索引；只查 `b` 或 `c` 通常不能直接定位。若 `a` 使用范围，后续列可能只能做索引条件下推而不能继续缩小扫描边界。实际判断不用背口诀，我会执行 `EXPLAIN ANALYZE`，看 chosen key、rows、filtered、是否 covering、回表次数和实际耗时。还要排除隐式类型转换、对索引列做函数、前导 `%like`、低选择性以及统计信息过旧。设计索引时根据高频 where、join、order by 和选择性安排列顺序，并检查是否能覆盖查询，不能每个字段各建一个索引期待自动合并。

##### 知识点补充

MySQL 8 可能使用 skip scan 或 index merge，但不能把它们当成合理联合索引设计的替代。联合索引同时影响排序与分组能力，新增索引还会增加写放大和存储。

##### MySQL 与 Redis 一致性

Q：MySQL 和 Redis 如何保证数据一致？更新数据库、删除缓存不是原子操作，失败时怎么办？
A：我先明确数据库是事实源，缓存只用于加速，目标一般是可控的最终一致。写流程采用“更新数据库成功后删除缓存”，删除失败进入可靠重试：在本地事务中写 outbox，或者订阅 binlog CDC 生成缓存失效事件；消费者按业务键幂等删除，并监控重试和积压。读流程 cache miss 后查库并回填，热点 key 加互斥或 singleflight 防止并发回源；缓存值携带版本号，旧请求不能覆盖新版本。对余额、库存等不能容忍短暂旧值的操作不走普通 cache-aside，而由数据库事务或专用一致性服务处理。线上通过缓存命中率、版本落后量、删除失败和抽样库缓存比对验证，而不是说“设置 TTL 就一致”。

##### 知识点补充

延迟双删能缩短并发回填旧值的窗口，但延迟时间难以精确，不能替代可靠消息和版本控制。TTL 是兜底，不是正确性机制。

##### Redis 数据结构与 Set 实现

Q：Redis 有哪些常用数据结构？Set 底层如何实现，项目中怎么选择？
A：String 用于计数、缓存对象和分布式锁的令牌；Hash 适合字段级更新的对象；List 适合简单队列但可靠消息优先 Stream；Set 用于去重和集合运算；ZSet 用于排行榜和延迟队列；Bitmap、HyperLogLog、Geo、Stream 分别解决位状态、近似基数、地理位置和消费组消息。Set 在元素全为整数且数量较小时可用整数集合，超出条件后转为哈希表，成员查询平均 `O(1)`。实际选型会估算元素数、单元素大小、过期粒度和操作复杂度；例如百万用户标签集合要评估内存，UV 若只要近似值用 HLL 更合适。通过 `MEMORY USAGE`、slowlog、bigkeys/scan 和命中率监控，禁止在大 key 上直接执行昂贵集合运算。

##### 知识点补充

Redis 内部编码会随版本和数据规模变化，不应把具体编码名称当永久接口。大 key 会造成网络、主线程阻塞、复制和删除抖动，可用 UNLINK、分片和紧凑结构治理。

##### 缓存穿透、击穿与雪崩

Q：缓存穿透、击穿和雪崩有什么区别？各自怎么处理？
A：穿透是请求的数据根本不存在，缓存和数据库都 miss；我会校验参数、缓存短 TTL 空值，并在高基数恶意请求前放 Bloom Filter。击穿是单个热点 key 失效，大量并发同时回源；用逻辑过期加后台刷新、互斥锁或 singleflight，旧值可接受时先返回旧值。雪崩是大量 key 同时失效或 Redis 整体不可用；过期时间加随机抖动、热点预热、限流降级、主从/集群和数据库保护一起做。实际演练会模拟节点故障和批量过期，观察回源 QPS、数据库连接池、P99 和恢复时间；只回答“加锁、加随机值”而不说明锁超时、失败降级和监控是不够的。

##### 知识点补充

Bloom Filter 有假阳性但无假阴性，删除困难；空值缓存需防止恶意构造大量不存在 key 占满内存。互斥锁必须设置过期和唯一令牌，避免误删他人锁。

##### Redis 容量治理与淘汰策略

Q：Redis 容量接近上限时会发生什么，如何治理？
A：达到 `maxmemory` 后行为由淘汰策略决定：noeviction 会让新增写失败；LRU/LFU/随机/TTL 类策略会从全部 key 或带过期 key 的集合中近似淘汰。排查我先看 used_memory、RSS、碎片率、keyspace、过期数和大 key/热 key，确认是业务数据增长、过期失效还是内存碎片。治理包括给缓存 key 设置合理 TTL、拆分大 key、压缩结构、按业务分实例、扩容分片，并在扩容前验证热 key 是否仍集中。Redis 作为权威状态存储时不能随意开淘汰，需使用 noeviction 并做容量告警；缓存则要设计回源限流，防止批量淘汰击穿下游。

##### 知识点补充

`used_memory` 与进程 RSS 不完全相同，fork 做 RDB/AOF rewrite 时还会有写时复制峰值。容量规划必须给复制、持久化和故障切换留余量。

##### Hive、HBase 与 Redis 场景对比

Q：Hive、HBase、Redis 各自适合什么场景，为什么不能互相替代？
A：Hive 是离线 SQL 数仓入口，适合扫描大分区、批量聚合和低成本历史存储，单条随机查询延迟高；HBase 是分布式宽列存储，适合按 RowKey 的高吞吐读写和大规模稀疏表，但任意多维查询弱；Redis 是内存键值系统，适合热点缓存、计数器、短状态和亚毫秒访问，容量成本高且复杂分析能力有限。例如实时维表全量可放 HBase，最热部分放 Redis/本地缓存，历史分析落 Hive。选型时量化访问键、QPS、P95、数据量、更新频率、一致性和保留期，不用“快慢”一个维度下结论。

##### 知识点补充

同一业务可分层组合多种存储，但必须定义权威数据源、缓存失效、补数和容灾路径，避免三套数据互相对不上。

##### GaussDB 的定位与使用边界

Q：了解 GaussDB 吗？它与普通 MySQL 或分析型数仓有什么区别？
A：GaussDB 是华为云数据库产品族，回答前我会先确认面试官指分布式关系型 GaussDB 还是 openGauss 生态，避免把不同产品混为一谈。分布式关系型场景强调 SQL 兼容、事务一致性、高可用和水平扩展，适合核心交易或大型关系数据；它仍不是用来替代所有离线湖仓扫描。迁移时要评估 SQL/存储过程兼容、分布键、跨分片事务、索引、数据同步与容灾切换，用真实 TPS、P95、故障恢复和一致性校验做 POC。若项目只接触过外围读取，我会明确实际使用深度，不虚构运维参数。

##### 知识点补充

产品能力和参数会随具体版本、部署形态变化。面试中应说明实际版本与职责边界，不能把 PostgreSQL/openGauss/GaussDB 的特性直接互换。

##### Redis 写入触发与缓存更新边界

Q：实时项目中哪些地方会写 Redis，如何避免无边界写入？
A：我只把明确需要低延迟读取的数据写 Redis，例如用户首次访问标记、短期去重标记、热点维度缓存和实时告警状态；长期明细、全量画像和可离线重算的历史不全部塞入。写入触发可以是 CDC 维度更新后的缓存失效、Flink 首次识别后的 `SET NX`、窗口结果更新后的带 TTL upsert。每类 key 都定义命名、数据结构、TTL、最大基数、权威源和失败补偿；批量/管道写减少网络往返，Lua 保证多步原子性。上线监控 key 数、内存、命中率、热 key、淘汰和写失败，容量超阈值时降级回源而不是无限扩张。

##### 知识点补充

Redis 是共享外部状态时，Flink checkpoint 不会自动快照它。重放和并发更新必须依赖确定性 key、版本或原子脚本保证幂等。

##### MySQL 索引类型与锁范围

Q：MySQL 有哪些常见索引？行锁和表锁在实际执行中如何判断？
A：InnoDB 常见的是聚簇主键索引和二级 B+Tree 索引，也有唯一、联合、全文等形式。二级索引先找到主键再回表，覆盖索引可省掉回表。InnoDB 的锁加在索引记录上，不是简单的“where 一行就锁一行”：唯一等值通常锁记录，范围查询在可重复读下可能有记录锁和间隙锁；没有合适索引时扫描、锁定范围会很大。排查时我会看执行计划、隔离级别、锁等待和死锁日志，并缩短事务、给更新条件建立有效索引。

##### 知识点补充

普通 select 通常是 MVCC 一致性读，`select ... for update` 和更新是当前读。锁表现象还可能来自元数据锁或非 InnoDB 引擎，不能只看 SQL 字面条件。

##### Redis Cluster 分片与扩容

Q：Redis Cluster 如何分片？节点数和扩容方案怎样设计？
A：Cluster 把 key 映射到 16384 个 hash slot，各主节点负责部分槽，客户端根据 MOVED/ASK 重定向找到节点。生产至少三主三从并跨故障域部署；节点数根据容量、QPS、单节点内存和恢复时间测算。扩容时加入新主节点，再在线迁移一部分槽和数据，监控延迟、网络及复制积压，客户端必须支持拓扑刷新。多 key 操作尽量用 hash tag 放同槽，但不能让大量 key 集中成热点槽。

##### 知识点补充

Cluster 用 gossip 维护拓扑，并由多数主节点完成故障判断。复制默认异步，因此故障切换不能承诺绝对不丢最近写入。

##### Redis RDB 与 AOF

Q：RDB 和 AOF 有什么区别？生产环境怎样组合使用？
A：RDB 是时间点快照，紧凑、恢复快，但两次快照之间可能丢数据；AOF 记录写命令，everysec 通常最多损失约一秒，但文件更大、恢复更慢。我通常启用 AOF everysec，并保留周期性 RDB 做备份和快速恢复，同时监控 fork、写时复制内存、AOF rewrite 和磁盘延迟。恢复前在隔离环境校验文件和恢复点，再切换流量，不能把开启持久化等同于零丢失。

##### 知识点补充

持久化、主从复制和异地备份解决的问题不同；误删命令也会传播到副本，必须有独立备份与恢复演练。

##### Redis Hash 的价值

Q：Redis 已经是 key-value 数据库，为什么还需要 Hash 类型？
A：普通 String 适合把整个对象序列化为一个 value，每次修改字段通常要读写整块；Hash 可以在一个业务 key 下按 field 存多个属性，用 HGET/HSET 局部读写，并减少大量短 key 的重复元数据。例如 `user:123` 下保存 name、level、city。字段较少、值较小时编码紧凑，但超大 Hash 会形成热 key，迁移和单线程操作耗时也会增加。我会根据访问模式选择 String 还是 Hash，并给整个 key 设置 TTL；Redis 原生不能给每个 field 独立 TTL 时需额外建 key 或维护过期索引。

##### 知识点补充

Hash 不是关系表，缺少复杂查询和字段级事务约束。对象需要整体版本控制时，序列化 String 反而更简单。

##### Redis 原子操作、锁与顺序处理

Q：多个客户端同时操作 Redis 是否需要加锁？Redis 能否保证顺序消费？
A：单条 Redis 命令在服务端原子执行，例如 INCR、HSET 不需要客户端再加锁；但“先读再判断再写”的多命令流程仍有竞争，我会用 Lua、事务或带条件的 SET 合并为原子操作。跨服务互斥可用 `SET key token NX PX ttl`，释放时用 Lua 校验 token，长任务还需续期和 fencing token，不能简单 DEL。Redis List/Stream 可按单 key 保持入队顺序，但多生产者实际先后、失败重试和消费者并发会改变业务完成顺序；严格顺序要单分片、单消费者并处理幂等和阻塞代价。

##### 知识点补充

Redis Cluster 中多 key Lua/事务要求 key 位于同一 slot。分布式锁只能提供协调，不能替代数据库唯一约束和业务幂等。

##### MySQL 一条 SQL 的执行链路

Q：一条查询 SQL 在 MySQL 中经历哪些步骤？
A：客户端通过连接器完成认证和会话建立，Server 层解析 SQL、做语义检查并由优化器选择索引、Join 顺序和访问方式，执行器再调用 InnoDB 接口取行；InnoDB 通过 Buffer Pool、B+Tree 和 MVCC 返回可见版本，缺页时从磁盘读取。执行前我用 EXPLAIN/EXPLAIN ANALYZE 看估算与实际行数、访问类型和回表情况，执行后结合慢日志、锁等待与 Buffer Pool 命中判断瓶颈。更新语句还涉及 undo、redo、binlog 和两阶段提交，不能用查询流程概括全部写入一致性。

##### 知识点补充

MySQL 8 已移除旧查询缓存。优化器选择依赖统计信息，估算失真时可能选错索引；应先更新统计和改 SQL/索引，而不是强制 hint 作为长期方案。

##### MySQL 视图与高可用边界

Q：MySQL 视图有什么作用？单节点数据库怎样提升可用性？
A：普通视图保存查询定义，不保存结果，可用于封装复杂 SQL 和限制暴露列，但性能仍取决于展开后的执行计划，不能当物化结果使用。高可用方面，生产不会只依赖单节点：通常用主从复制或 InnoDB Cluster 等方案，代理/VIP 负责故障切换，备份与 binlog 提供时间点恢复。读写分离前要接受复制延迟，强一致读取回主库；切换必须防双主写入，并演练 RPO/RTO。高可用不等于备份，逻辑误删仍会复制到从库。

##### 知识点补充

视图权限可简化访问控制，但复杂嵌套视图会降低可维护性。具体 HA 选型取决于 MySQL 版本、跨机房延迟和一致性目标。
