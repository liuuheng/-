##### 连续登录问题

Q：表 `usr_login(userid, dt)` 中一天可能重复登录，如何求连续登录 N 天的用户，并返回连续段的第一天？
A：我会先确认四个口径：一天多次登录是否按一天算、连续 N 天的 N 是否参数化、统计区间按自然日还是最近 24 小时、一个用户有多段连续记录时返回全部还是最早一段。实现上先 `select distinct userid, cast(dt as date)` 去掉同日重复，再按用户和日期做 `row_number`；用 `date_sub(dt, rn)` 生成连续段分组键，因为连续日期减连续序号得到相同基准日。随后按 `userid, grp` 聚合，`count(*) >= N`，`min(dt)` 和 `max(dt)` 分别是连续段起止日。上线前会用同日重复、跨月、断一天、多段连续和窗口边界五组数据验证；Hive、Spark SQL 和 MySQL 的日期函数语法不同，但分组思路不变。

```sql
WITH d AS (
  SELECT DISTINCT userid, CAST(dt AS DATE) AS dt
  FROM usr_login
  WHERE dt >= date_sub(current_date, 29)
), tagged AS (
  SELECT
    userid,
    dt,
    date_sub(dt, row_number() OVER (PARTITION BY userid ORDER BY dt)) AS grp
  FROM d
), streak AS (
  SELECT userid, grp, min(dt) AS start_dt, max(dt) AS end_dt, count(*) AS days
  FROM tagged
  GROUP BY userid, grp
  HAVING count(*) >= 3
)
SELECT userid, start_dt, end_dt, days
FROM streak;
```

##### 知识点补充

不同引擎日期函数语法不同：Hive/Spark SQL 常用 `date_sub(dt, n)`；部分数据库需写成 `dt - n * interval '1 day'`。必须先按天去重，否则 `row_number` 会被同日多次登录打乱。窗口范围也应按题目给定的自然日边界确定，不能机械依赖系统当前日期。

##### 分组 TopN 与前百分比用户

Q：如何求每个分组的 TopN？如何找销售总额排名前 10% 的用户？
A：我先按业务粒度聚合，再用窗口函数排名。分组 TopN 通常用 `row_number() over(partition by 分组 order by 指标 desc)`，需要并列则根据题意改用 `rank` 或 `dense_rank`。前 10% 用户要先按用户汇总销售额，再用 `ntile(10)`、`percent_rank` 或计算总人数后取 `ceil(count*0.1)`；三者对并列和小样本的边界不同，面试时必须说明口径，而不是只写 `limit 10%`。

##### 知识点补充

`row_number` 强制唯一序号，`rank` 并列后跳号，`dense_rank` 并列后不跳号。若要求“销售额达到前 10% 分位”而非“人数前 10%”，应使用分位数阈值，业务含义完全不同。

##### 15 分钟内 UID-IP 去重

Q：有 `uid、time、ip`，如何保证 15 分钟内同一 UID 的 IP 不重复？
A：先确认“15 分钟”是固定窗口还是从每条事件开始的滚动有效期。固定窗口可按 `uid、ip、窗口起点` 分组，只保留最早一条；真正滚动 15 分钟去重更适合流式状态：按 `(uid, ip)` keyBy，状态记录最近一次通过时间，若当前事件与记录时间差小于 15 分钟则丢弃，否则输出并更新时间，同时配置略大于 15 分钟的 TTL。若存在乱序，要基于事件时间和 watermark 延迟清理，不能直接用机器当前时间。

##### 知识点补充

固定滚动窗口会在边界处重复，例如 10:14 和 10:16 落在两个窗口但只相隔 2 分钟。严格滑动去重需要逐 key 状态或分析函数比较上一条有效事件，状态 TTL 还要覆盖允许迟到时间。

##### 外连接过滤与 FULL JOIN

Q：`LEFT JOIN`、`FULL JOIN` 后的过滤条件怎么写，才能避免把外连接写成内连接？
A：我先明确要保留哪一侧。LEFT JOIN 中，右表参与匹配的条件写在 ON；如果把 `right.status='valid'` 写进 WHERE，未匹配行的 right.status 是 NULL，会被过滤掉，左表全量就保不住。FULL JOIN 要保留两侧未匹配记录时，两边各自的过滤最好在关联前子查询完成，关联后主键通常用 `coalesce(a.id,b.id)`，指标也要分别处理 NULL。实际排查会分别统计左表、右表、匹配、左未匹配、右未匹配数量，并检查 join key 是否重复导致多对多膨胀；不能只看最终行数“差不多”。

##### 知识点补充

内连接中 ON 与 WHERE 的部分条件结果等价，但执行器是否下推由优化器决定。外连接的三值逻辑会让 NULL 条件结果变为 UNKNOWN，这是语义变化的根源。

##### 窗口函数与 row_number 执行机制

Q：`row_number()` 怎么实现分组排序，它的底层执行代价是什么？
A：典型写法是 `row_number() over(partition by group_key order by score desc, id)`，外层过滤 `rn<=N`。逻辑上先按 partition key 把同组数据放到一起，再在组内按 order key 排序，最后顺序编号；在分布式引擎中通常意味着 shuffle 加分区内排序，所以大组和热点 key 会产生长尾与 spill。生产中我会先裁剪列、过滤分区、必要时预聚合，并给排序添加稳定的唯一键，避免同分记录每次结果不同。若只是全局 TopN，可用局部 TopN 再全局合并；若每组都很大，则评估引擎的 TopN 优化或分桶设计，而不是默认全量排序没有成本。

##### 知识点补充

`row_number` 不保留并列名次，`rank` 会跳号，`dense_rank` 不跳号。选择哪个取决于“取 N 行”还是“取前 N 个名次”的业务定义。

##### 留存、新访客与漏斗指标

Q：如何用 SQL 计算新访客、次日留存和转化漏斗？
A：新访客不能只看当天出现，我会先得到每个用户的首次访问日 `min(event_date)`，等于统计日的才算新增；若有可靠用户首次激活维表则直接使用，避免反复扫描全历史。次日留存以某日新增用户为 cohort，左关联次日活跃去重用户，分母固定为新增人数，分子是次日再次活跃人数。漏斗先统一用户、会话或订单粒度，再为曝光、点击、下单、支付取首个有效事件时间，要求后一步时间不早于前一步，并按业务规定限制转化窗口。每层同时输出人数和相对上一层、相对首层转化率，迟到数据通过重算窗口修正。

##### 知识点补充

留存必须说明自然日还是 24 小时、按设备还是账号、跨端如何合并。漏斗若不约束事件顺序，会把先支付后补发的异常日志错误计入转化。

##### 海量精确去重优化

Q：五千万订单做 `count(distinct order_id)` 很慢，如何优化并保证结果准确？
A：先判断订单表是否本来就以 order_id 唯一；若是，分区裁剪后的 `count(*)` 就够，不应重复去重。若确实有多版本或重复记录，我会按日期和 order_id 先做局部去重，再按 order_id 重分区做最终去重，减少单节点压力；Spark 可用 `dropDuplicates`/聚合配合合理分区，Hive 可用两阶段 group by，并检查热点空 key。只需要估算时才使用 HyperLogLog 等近似算法，并明确误差。精确结果还要用主键重复率、分区总数和抽样明细校验；如果频繁查询，应在 DWD 层建设按主键去重后的当前表或拉链表，而不是每次扫描五千万原始变更记录。

##### 知识点补充

`count(distinct)` 的执行计划因引擎版本不同而异。组合去重需明确是一个组合键还是多个独立 distinct，NULL 是否计数也要按业务定义处理。

##### 关注关系计数 SQL

Q：关注关系表包含 `followee` 和 `follower`，如何统计每个人的粉丝数？
A：如果一行表示 follower 关注 followee，就按 `followee` 分组，统计去重后的 follower：`select followee, count(distinct follower) follower_cnt from relation where status=1 group by followee`。例如 A 被 B 关注、B 被 C 和 D 关注、D 被 E 关注，结果中 B 是 2、D 是 1。生产表通常有关注和取消关注变更，我会先用 `row_number() over(partition by follower,followee order by event_time desc)` 取每对关系最新状态，再统计当前有效关系；如果源表已经是唯一当前快照，则不需要重复做窗口。最后校验自关注、重复消息、黑名单和删除账号是否应排除。

##### 知识点补充

粉丝数按 followee 聚合，关注数按 follower 聚合，字段名很容易看反。大规模在线展示通常维护增量计数，并定期用离线全量结果校准。

##### 登录首末时间与倒数第二次记录

Q：如何统计每个用户首次、末次、登录天数，并取倒数第二次登录的完整记录？
A：首次和末次可按用户聚合 `min(login_time)`、`max(login_time)`，登录天数用 `count(distinct to_date(login_time))`，不能直接 count 日志条数。取倒数第二次完整记录时先按 `uid` 分区、`login_time desc` 排序，用 `row_number` 编号后过滤 `rn=2`；若同一时间可能多条日志，要追加唯一 event_id 作为稳定排序键。没有第二次登录的用户按需求排除或返回 NULL。性别、部门等维度先把用户维表去重到一人一行再关联，否则会把登录天数乘倍。

##### 知识点补充

若业务要求第二个“不同登录时间”，需先按 uid、login_time 去重。日期统计必须统一时区，跨午夜日志不能直接截服务器本地时间。

##### GROUPING SETS 多维聚合

Q：`GROUPING SETS` 适合什么场景，与多次 `GROUP BY UNION ALL` 有什么区别？
A：当同一份明细需要按多个维度组合汇总时，例如分别计算“日期+地区”“日期+渠道”“日期总计”，可写 `group by grouping sets ((dt,region),(dt,channel),(dt))`，引擎一次逻辑扫描生成多组聚合结果，比分别写多条 SQL 更统一。结果中未参与某组的维度会是 NULL，若业务维度本身也允许 NULL，应使用 `grouping()` 标记区分“汇总行”和“真实空值”。实际会先在公共粒度预聚合，避免维度组合过多造成中间结果爆炸，并为输出添加 grouping_id 作为汇总类型。

##### 知识点补充

`ROLLUP` 生成层级小计，`CUBE` 生成所有维度组合，`GROUPING SETS` 明确指定组合。组合数增长会直接增加聚合数据量。

##### 周同比与周期对比

Q：SQL 如何计算周同比或本周与上周的指标变化？
A：先明确“周同比”是同比去年同周还是环比上周，国内口语经常混用。若比较上周，我先按 ISO 周或业务周聚合到 week_start，再用 `lag(metric,1) over(order by week_start)` 取得上一周，变化率为 `(current-prev)/prev`；去年同周则关联去年对应周，并处理跨年周编号。分母为 0 时返回 NULL 或按业务约定展示，不能直接除零。数据未完整的一周要与上周同期天数比较，避免周三拿半周数据对完整上周。日期维表提供 week_start、year_week 和同比映射，比分散使用字符串函数可靠。

##### 知识点补充

同比、环比必须同时说明对比周期、完整性和节假日口径。金额变化与变化率建议同时输出，防止小基数产生夸张百分比。

##### 客服会话响应指标

Q：消息表包含 from_id、to_id、msg_time，如何统计每个客服服务客户数、未完成对话数和平均响应时间？
A：先识别哪些 ID 是客服，并按客服与客户构造 conversation_key。服务客户数是发生过有效会话的去重客户数。响应时间不能把任意两条消息相减：对每条客户消息，用窗口或范围关联找到其后该客服的第一条回复，排除下一条客户消息前已被其他规则关闭的情况；`reply_time-client_time` 参与平均。截止统计时仍找不到回复的会话计入未完成，通常按会话而不是消息条数。海量数据我会先按会话和时间排序，用状态机扫描，避免客户连续发三条导致一条客服回复被重复匹配三次，并明确机器人消息、跨天和 SLA 时段。

##### 知识点补充

响应指标的关键是会话配对规则，而非简单 Join。平均值容易被长尾影响，生产报表通常同时展示 P50、P90/P95 和超时率。

##### 累计占比与二八分析

Q：用户资产表包含 user_id、money，如何找出累计掌握 80% 金额的用户及其人数占比？
A：先汇总每个用户金额并计算全体总额，再按金额降序做累计和：`sum(money) over(order by money desc, user_id)`，累计占比为 cumulative/total。若要找到覆盖至少 80% 的最小用户集合，保留累计前小于 80% 的用户，并额外包含第一条使累计达到或超过 80% 的记录；不能简单筛 `cum_ratio<=0.8`，否则会少最后一人。再用集合人数除以总用户数验证是否接近 20%，二八定律只是经验现象，结果不必恰好 20%。负金额、并列和总额为零要先定义处理规则。

##### 知识点补充

排序同值时加稳定键保证结果可复现；若并列用户必须整体纳入，最小集合可能超过阈值，需要在业务口径中说明。

##### 购买全部商品的用户

Q：Customer 表记录用户购买的 product_key，如何查询购买了 Product 表中全部商品的用户？
A：这是关系除法问题。常用写法按 customer_id 分组，`having count(distinct customer.product_key) = (select count(*) from product)`，并确保 Customer 中只统计 Product 表真实存在的 key，可先内连接 Product。另一种更严谨的双重 `NOT EXISTS`：不存在任何一个 Product，用户没有对应购买记录。前者直观且适合大数据聚合，后者语义清晰但执行计划要实测。重复购买必须 distinct；Product 为空时是否所有用户都满足需要业务定义，不能忽略空集语义。

##### 知识点补充

如果题目问购买了所有“在售商品”，Product 子查询还要带有效状态和时间条件。大表中可先对用户商品去重，减少聚合数据量。

##### 生效区间峰值计算

Q：店铺有生效日期和失效日期，如何求同时生效店铺数的峰值及对应时间段？
A：我用扫描线。每个开始日期产生 `+1` 事件，每个失效日期产生 `-1` 事件；先明确区间是 `[start,end)` 还是两端都包含，同一天事件的排序规则据此确定。按日期汇总 delta，再按日期累加得到当前有效店铺数，用 lead(date) 得到该数量持续到下一个事件日前的区间，最后取最大值对应的所有区间。若结束日期也算有效，可把 `-1` 放在结束日次日。这样无需展开每一天，复杂度由事件数决定，适合长时间范围。

##### 知识点补充

扫描线适合并发区间、在线人数和资源峰值。多个事件同日必须先聚合，否则中间顺序会制造不存在的瞬时峰值。

##### 每日热门 URL Top100

Q：一个月访问日志中，如何统计每天访问人数最多的 Top100 URL？
A：先按业务时区得到 dt，对 `dt,url,user_id` 去重，得到每个 URL 的日 UV；再按 `dt,url` 聚合 count，最后 `row_number() over(partition by dt order by uv desc,url)` 过滤前 100。若题目要访问次数而非人数，就不对 user_id 去重，必须区分 PV 与 UV。数据量大时先在分区内对 `(dt,url,user_id)` 做局部去重或 bitmap 聚合，避免单个热门 URL 的 distinct 成为瓶颈。输出同时保留 uv、排名和数据截止时间，同值是否全部保留则改用 rank 并接受超过 100 行。

##### 知识点补充

按月扫描时必须利用日期分区。URL 需先做规范化，去掉无业务意义的追踪参数，否则同一页面会被拆成大量不同键。

##### Bitmap 与精确去重

Q：Bitmap 能否用于精准去重，适合什么 ID 和查询场景？
A：Bitmap 用 bit 位表示整数 ID 是否出现，相同 ID 多次设置仍为 1，所以在 ID 已映射为稠密非负整数、Bitmap 实现无误差时属于精确去重；多个分区通过 OR 求并集后 count。用户 ID 是 UUID/字符串或数值极稀疏时，先维护稳定字典映射，或使用 RoaringBitmap 对稀疏区间压缩；字典本身要一致且可扩展。跨天 UV 保存每日 bitmap，任意周期做 union，不能把每日 count 相加。数据量过大且允许误差才使用 HLL。上线验证字典冲突、序列化兼容、基数和内存，并保护 bitmap 聚合的单 key 热点。

##### 知识点补充

Bloom Filter 只能回答“可能存在”，不能枚举或精准计数；Bitmap 可做集合交并差和精确基数，两者用途不同。

##### 高于各科平均分的学生

Q：如何查询每个科目中成绩高于该科目平均分的学生？
A：我会先按 subject 聚合 `avg(score)`，再按 subject 回连成绩明细并过滤 `score > avg_score`；也可用 `avg(score) over(partition by subject)`，外层过滤。窗口写法保留明细，但要留意超大分区；结果需要稳定展示时再按科目、分数降序和学生 ID 排序。空成绩默认不参与 avg，若业务要求按 0 分算要先显式处理。

##### 知识点补充

同一层 WHERE 通常不能引用窗口结果，需要子查询或 QUALIFY。若继续取名次，要明确并列时用 row_number、rank 还是 dense_rank。

##### 在线人数区间统计

Q：给出上线、下线时间，怎样计算每个时刻的在线人数和最大并发？
A：我把每条会话拆为上线 `+1`、下线 `-1` 两个事件，按时间汇总 delta 后做累计和。边界先约定：若下线时刻不再在线，同一时刻先处理 -1 再处理 +1；闭区间则相反。按分钟输出时用时间维表关联变化点，不把长会话展开成每秒明细。多端重复登录还要按会话 ID 去重，或按业务定义合并重叠区间。

##### 知识点补充

这是扫描线算法，最大并发是累计值最大值。窗口应显式写 `rows unbounded preceding`，避免相同时间下默认 RANGE 产生歧义。

##### 互相关注与无向好友数

Q：关注表中怎样找互相关注关系，并统计每个人的好友数？
A：把关注表 a、b 按 `a.user_id=b.follow_id and a.follow_id=b.user_id` 自连接，再加 `a.user_id < a.follow_id`，每对好友只保留一次。统计每人好友数时把每对关系展开成 `(u1,u2)` 与 `(u2,u1)`，按用户 count distinct friend_id。计算前按关注双方去重并过滤自己关注自己，防止重复事件放大计数。

##### 知识点补充

若题目问关注数而非好友数，不需要双向判断。超大关系表可先标准化、分桶，避免无条件的大规模自连接。

##### 连续多日单调下降

Q：怎样找出连续 7 天指标每天都下降的对象？
A：先把同一对象同一天聚合成日粒度，用 lag 同时取得前一天日期和值；仅当日期相差一天且当前值小于前值时标记下降，否则形成断点。再按断点累计分组，统计连续下降边数。连续 7 天对应 6 次相邻下降，不能误算成 7 次。缺失日期默认打断，除非业务明确要求先补零或前向填充。

##### 知识点补充

窗口前必须固定日粒度和业务时区，跨天重复记录会让 lag 结果失真。也可对不满足条件的行累计生成岛屿分组。

##### SQL 逻辑执行顺序

Q：SQL 的逻辑执行顺序是什么？对实际写查询有什么影响？
A：逻辑上通常先 FROM/JOIN 和 ON，再 WHERE、GROUP BY、聚合、HAVING、窗口、SELECT、DISTINCT、ORDER BY，最后 LIMIT；物理计划会优化，但语义仍受这个顺序约束。所以 WHERE 不能直接用本层 SELECT 别名或窗口结果，聚合后过滤放 HAVING，窗口结果放外层或 QUALIFY。优化时我会在不破坏外连接语义的前提下尽早过滤和裁剪列，降低 JOIN 与 Shuffle 数据量。

##### 知识点补充

左连接右表条件放 ON 与放 WHERE 语义不同，WHERE 过滤空扩展行可能把左连接变成内连接。内连接可被优化器重排，但不会随意改变可观察语义。

##### 每分钟访问 Top3 与当日峰值

Q：有城市、用户、页面和访问时间，怎样一分钟内计算当日峰值及每分钟 Top3 用户？
A：在 Flink 中先生成 Watermark，按 city/user 和一分钟滚动窗口聚合访问次数；窗口结果再按 city+windowEnd keyBy，用有界榜单状态或 TopN SQL 输出前三。城市每分钟 UV 先按 city+user+window 去重再计数，当日峰值把分钟结果按 city+日期维护 max。迟到更新用同一结果主键 upsert，跨天按业务时区清状态；不能把所有城市 keyBy 常量汇到一个并行度。上线前还要确认指标是 PV、UV 还是在线人数。

##### 知识点补充

Top3 的并列规则、允许迟到和修订语义必须写入口径。分钟结果可两阶段聚合，避免全局单点。

##### 第二高薪资

Q：如何查询第二高薪资，没有第二名时怎样返回？
A：如果按不同薪资档位取第二高，我对 salary 用 `dense_rank() over(order by salary desc)` 排名并取 2；也可取小于最大值的 max。若要求员工明细，就把排名结果回连员工表，第二高并列者全部保留。只有一个薪资档位时返回空或 null，按接口约定处理；不能直接用 row_number，否则同薪员工会被拆成不同名次。

##### 知识点补充

“第二高记录”和“第二高不同值”语义不同，写 SQL 前要确认。大表可利用 salary 索引或先做分区裁剪。

##### 两表对称差集

Q：两张表只要各自独有的数据，不要交集，SQL 怎么写？
A：支持 full outer join 的引擎可按业务键关联并过滤 `a.key is null or b.key is null`；MySQL 可用 A left join B 取 B 为空的行，与 B left join A 取 A 为空的行做 union all。前提是两边 key 唯一，否则一对多会放大结果，要先去重或明确比较整行。支持 EXCEPT 的引擎也能分别求 A-B、B-A 后合并。

##### 知识点补充

NULL 键不会按普通等号匹配，业务认为 NULL 相等时需 null-safe 比较。两部分已互斥可用 UNION ALL，避免额外去重。

##### 行列转换的生产写法

Q：学生科目分数怎样从多行转成一行，多列怎样还原为多行？
A：行转列按 student_id 分组，用 `max(case when subject='语文' then score end)` 为每科生成列；科目固定时最稳定，动态科目则由程序生成 SQL 或用 pivot。列转行可对每个科目列 select 后 union all，Hive 也可用 stack/explode。转换前先处理同一学生同科多条记录，明确取最新、最高还是求和，否则 max 只是掩盖重复；输出也要定义未知科目和空成绩规则。

##### 知识点补充

动态维度更适合保留长表，过宽 pivot 会导致 Schema 频繁变化。Hive 列转行还可用 `lateral view explode(array(named_struct(...)))` 或 `stack`；多个 explode 可能形成笛卡尔放大。Pivot 是展示形态，不应破坏事实粒度。

##### 不用窗口函数求分组 TopN

Q：每个地区取价格最高的 5 条，不使用窗口函数怎么写？
A：可以用相关子查询：对当前记录 a，统计同地区中价格比它高，或价格相同但唯一 ID 更小的记录数；数量小于 5 就保留。也可自连接后 group by 当前行并用 having count(b.id)<5。关键是加入稳定的 ID 处理并列，否则同价可能返回超过 5 条或结果不确定。这种写法在大表上通常是 O(n²) 级且优化困难，生产我仍优先窗口函数，并用分区裁剪、索引或预聚合；题目限制不用窗口时才展示该方案。

##### 知识点补充

如果业务要求并列全部保留，比较条件只统计严格更高价格；若严格每组 5 行，则必须定义 tie-breaker。

##### 时间戳、日期与小时差

Q：SQL 中如何把时间戳转日期，并计算两个时间相差多少小时？
A：先确认时间戳是秒还是毫秒以及业务时区。Hive 可用 `from_unixtime(ts)` 转字符串时间，毫秒时间戳要先除以 1000；小时差可把两端转为秒后相减再除 3600，或使用引擎的 timestampdiff。不能先截成日期再相减，否则丢失时分秒。结果需要整数时要明确向下取整、四舍五入还是不足一小时也算一小时，并处理负值、空值及夏令时。

##### 知识点补充

不同引擎的日期函数和参数顺序不同。跨时区计算最好先转 UTC 时间线，展示时再转业务时区。

##### 所有科目均达标的学生

Q：怎样查询每门课程都达到 80 分的学生？
A：如果成绩表只包含已选课程，可按 student_id 分组并用 `min(score)>=80`，同时确认空成绩处理；也可 `having sum(case when score<80 or score is null then 1 else 0 end)=0`。若要求达到课程目录中的“所有必修课”，还必须把学生成绩与课程表比较，校验 `count(distinct passed_course)=必修课数`，否则缺考学生会被错误判为全部达标。重复成绩先按考试规则取最终或最高版本，不能直接 count 行数。

##### 知识点补充

这是关系除法类问题。题目中的“所有”必须明确集合范围，是学生已考课程还是全校必修课程。
