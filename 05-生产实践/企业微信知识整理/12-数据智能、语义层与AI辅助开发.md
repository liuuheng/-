# 数据智能、语义层与 AI 辅助开发

返回：[[README|企业微信知识地图]]

## 1. Text2SQL 与语义层解决不同问题

Text2SQL 把自然语言翻译成 SQL，上限受模型代码能力、Schema 上下文、示例和提示词影响。它灵活，但可能选错表、join、口径或生成危险查询。

语义层把业务知识编码为 Model、Metric、Dimension 和规则。AI 不是自由翻译，而是选择已治理部件。它的灵活性较低，但常规指标更稳定、可审计。

复杂探索分析可以继续使用 Text2SQL；重复报表和标准指标优先语义层。两者不是替代关系。

## 2. NL → DSL → SQL 架构

让模型先生成受限 DSL，再由程序验证并生成 SQL：

```text
自然语言
→ 意图识别与澄清
→ 选择 Model/Metric/Dimension
→ 生成结构化 DSL
→ 权限、粒度、字段、时间范围校验
→ 确定性 SQL 编译
→ EXPLAIN/成本与安全检查
→ 执行和结果解释
```

这样做的原因：SQL 是高权限执行语言，直接生成容易全表扫描、越权或执行 DDL；DSL 可以只允许 SELECT、白名单字段和有限操作符。

## 3. AI 数据 Agent 的语义底座

Agent 要稳定回答数据问题，至少需要：

- 表描述、粒度、主键和更新方式。
- 字段业务含义、单位和枚举。
- 指标 ID、公式、过滤、时间和负责人。
- 表与指标血缘。
- 可用维度及兼容性。
- 示例问题与正确查询。
- 权限与敏感级别。

例如任务注释统一写：

```text
description: 合并 1.0/2.0 权益消耗流水，用于 SKU 归因和权限点分析
grain: 一次权益消耗流水记录
primary_key: record_id
update_mode: append/cdc-upsert
```

这不仅给 AI 使用，也改善人工接手、数据发现和质量规则生成。

## 4. Model 为什么是核心

如果 Model 中把“一对多”关系当成一对一，所有 Metric 都会因 join 放大。如果 Model 没声明时间有效性，历史事实可能关联当前维度。Metric 写得再准确，也无法弥补错误的数据骨架。

Model 应记录 join 类型、基数预期、关联键、有效时间、默认过滤和 fanout 风险。上线前用已知样本验证 join 前后行数和主键唯一性。

## 5. 指标兼容性

不是任何指标都能与任何维度组合。例如“用户数”可以按用户所属行业分组，但若行业是当前快照，历史用户数按行业可能被重写。订单项金额可按商品维度，但订单级优惠若直接 join 到商品项会重复。

语义层应维护 metric-dimension compatibility，必要时指定桥接模型和分摊规则，而不是让 Agent 任意拼接。

## 6. 查询安全

至少包含：

- 只读数据库账号和行列权限。
- SQL AST 校验，禁止 DDL/DML、多语句和危险函数。
- 强制时间范围、行数限制和查询超时。
- 执行前 EXPLAIN 与扫描成本门槛。
- 敏感字段脱敏和审计。
- 结果缓存与并发限流。

Prompt 中写“不要删除数据”不是安全边界；权限和解析器才是。

## 7. LangChain 基础概念

- Chat Model 接受带角色的 message 列表，返回 AIMessage。
- PromptTemplate 用占位符构造文本；ChatPromptTemplate 构造 system/human 等角色消息。
- Parser 将模型回复转换为字符串或结构化对象。
- Runnable 链常写成 `prompt | model | parser`。
- `invoke` 单次调用、`stream` 流式输出、`batch` 批量请求。

Memory 类只是应用层把历史消息重新放入 prompt，并不是模型拥有永久记忆。Buffer 全保留会持续增加 token；Window 只保留最近 N 轮；Summary 用模型压缩旧内容，可能丢细节。生产系统应把事实状态放数据库，把对话摘要视为可丢失辅助信息。

## 8. Embedding 与向量搜索

Embedding 把文本映射为向量，相似度表示语义接近程度。向量搜索通常返回 top-k，即使最高分很低也可能返回结果，因此应用层需要 score 阈值、重排序或“无匹配”策略。

推荐系统、语义检索和知识库都要区分：

- 召回：向量库找候选。
- 过滤：权限、时间、类型等结构化条件。
- 重排序：更精确模型重新评分。
- 答案生成：只能基于通过校验的内容。

不能把向量相似度直接当成事实正确率。

## 9. Batch Prompting 的边界

把多个独立问题合并到一个 prompt 可以摊薄固定指令 token 和请求开销，但前提是任务彼此独立、输出格式清晰、单次上下文不超限。问题之间可能互相干扰，某一项失败也会使整批重试。

工程上应测量吞吐、首 token 延迟、总延迟、准确率和失败恢复，而不是只根据理论上的 1/K 下降决定批大小。

## 10. Spec-Driven Development

SDD 先把目标、边界和验收标准写成规格，再实现。它适合 AI 辅助编程，因为模型可以根据明确约束生成代码，测试也有判定依据。

一份可执行规格至少包含：

- 背景与目标。
- 输入输出及示例。
- 正常流程、异常流程和边界条件。
- 不在范围内的内容。
- 性能、安全和兼容要求。
- 可自动验证的验收标准。

“实现一个 ES Source”不是规格；“每分钟发现截至 now-2m 的时间窗口，按 4 slices 分配，checkpoint 保存 search_after，允许重复但不得因正常恢复漏过已稳定窗口，下游按 id+update_time 幂等”才接近可实现规格。

## 11. AI 仍不能替代哪些数仓工作

当前 Data Agent 多集中在 ADS 到 BI 的最后一公里。以下工作仍需要强业务判断：

- 识别业务过程与事实来源。
- 定义粒度、历史语义和更新策略。
- 处理源系统从未保留的历史信息。
- 决定指标主体、时间锚点和风险。
- 建立数据质量、权限与责任机制。

AI 可以加速元数据整理、SQL 草稿、测试和文档，但不能从缺失数据中恢复事实，也不能代替业务方授权口径。

## 12. 密钥与配置安全

模型服务的 token、长期令牌和代理认证不能保存在聊天或普通 Markdown。推荐：

- 本地通过环境变量或系统 Keychain 注入。
- CI/CD 使用 Secret Manager，并限制读取范围。
- 日志和异常中自动脱敏。
- 一旦进入聊天/仓库立即轮换，而不是只删除历史消息。

配置示例只保留变量名，不提供真实值：

```json
{
  "env": {
    "MODEL_API_TOKEN": "${SECRET_FROM_MANAGER}",
    "MODEL_BASE_URL": "https://example.internal"
  }
}
```
